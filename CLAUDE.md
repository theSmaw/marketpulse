Work descends epic → story → task. Read the STORY.md before starting on a story: several carry **open decisions** (framework, UI library, hosting) that are deliberately unresolved and should be settled with the user rather than assumed.

We are building this in **small iterations**. Do not scaffold ahead of the current step: build the thin slice that is asked for, keep it working, then move on. Do not add infrastructure (databases, workers, WebSockets, agent plumbing) before the iteration that needs it.

Every package exposes `dev`, `build`, `test`, `lint`, `typecheck`, `clean` and they mean the same thing in each. `lint:fix` is an extra, not part of the convention — a local convenience with no root fan-out and no place in `verify`. **`apps/backend`'s `start` (Task 1.2.5), `apps/frontend`'s `preview` (Task 1.3.4) and `apps/frontend`'s `storybook` and `storybook:build` (Task 1.4.5) all have exactly the same status**: an extra, not a seventh verb — no root fan-out, no place in `verify`, and no obligation on the other packages. Both run the built output and build nothing themselves, so a stale or empty `dist/` is a stale or missing server and a stale page. Verified in Task 1.2.5 and again in 1.2.6: `pnpm run` waits for the script to finish and propagates both signals and the child's exit code, so `start` is a real process wrapper rather than a fire-and-forget one. `SIGTERM` to the pnpm process and `SIGINT` to the process group both give a clean exit 0 with the port released; a busy port gives exit 1 with the `EADDRINUSE` record intact. `test` is an `echo` placeholder in all three packages until Story 1.9 and is now the **only** placeholder left in the workspace — all three `dev` scripts are real as of Task 1.3.3.

**Storybook stays out of `pnpm dev`, and Task 1.8.2 confirmed it on a measurement rather than leaving it as an omission.** The suspicion was that its boxed startup banner would be mangled by pnpm's line prefix; it is not — the box survives the prefix intact, at **12 startup lines** against Vite's 3, and the workshop is as quiet as Vite afterwards. What decides it is the port: **Storybook does not strict-port**, and with 6006 busy it bound **6007** and said so in a line nobody reads. That is exactly the behaviour `strictPort: true` was chosen to prevent for 5173 and 4173, because a silently moved port fails later as a browser error naming neither the port nor the cause — so adding the workshop to the loop would put the rejected behaviour inside it. Beside that, the workshop and the application are different activities, so running both always leaves one bundler idling. The reversal trigger is a story being edited routinely in the same sitting as the application, and the port question has to be answered first.

**`vite preview` is not a static host, and mistaking it for one hides a real failure.** Its SPA fallback answers _any_ unmatched path with `index.html` and a 200 — `/assets/nope.js` included — so a missing asset arrives in the browser as a MIME-type error rather than a 404 naming the file. Measured against `python3 -m http.server`, which 404s both. Use `preview` to look at a build; use something dumb to prove one works.

**Now that there is a router, that generosity hides two acceptance criteria rather than one.** Task 1.5.5 served the built artefact from outside the workspace with `python3 -m http.server`: `/` is a 200 and `/investigations`, `/securities`, `/replay` and any made-up path are all **404**, while `vite preview` and the dev server answer every one of them — and `/assets/nope.js` — with the same 1101-byte `index.html`. So **deep-linking is a property of the host and not of the router**, and it is Story 1.11's to configure; hash routing was rejected as `/#/` permanently in every URL a user copies. The half that is easy to miss: **the not-found route rests on the same property.** `NotFound` is a real route, so it only renders if the host served `index.html` for the address that matched nothing — on a dumb host the user gets _Python's_ 404 page and React never boots. Do not record either criterion as met on local evidence. Three constraints are written into Story 1.11's STORY.md, and the non-obvious one is that the rewrite must **not** be a blanket catch-all, because one that answers every unmatched path with `index.html` recreates the missing-asset trap above in production.

**`clean` is the one verb that needs an explicit `run` when filtered, and this is a trap with teeth.** `pnpm clean` is a _built-in pnpm 11 command_ (alias `purge`) that removes `node_modules` from every workspace project. pnpm runs a `clean` script instead of the built-in only when the current project has one — which the root does, so root `pnpm clean` correctly runs `tsc -b --clean`. But `pnpm --filter <pkg> clean` dispatches to the built-in and fails with `[ERROR] Unknown option: 'recursive'` (exit 1), because `--filter` implies `--recursive` and the built-in takes no such flag. Verified in Task 1.2.6 for all three packages; the documented one-liner used to list `clean` alongside the other verbs and was simply wrong. **`pnpm --filter <pkg> run clean` works.** The failure is loud and deletes nothing, but do not "fix" it by dropping the root's `clean` script, which is the only thing shadowing a command that deletes `node_modules`.

**A green `pnpm test` means "no tests exist", not "tests pass".** All three placeholders exit 0, and Story 1.10 will put that tick in CI where it looks exactly like coverage. Don't describe it as passing tests anywhere — not in a commit message, not in a PR, not in this file.

**`pnpm dev` at the root is three real loops and eight processes.** `packages/shared` sits in `tsc -b --watch --preserveWatchOutput`; `apps/backend` runs `scripts/dev.sh`, which is a second `tsc -b --watch` plus `node --watch dist/index.js`, so the server's own JSON log lines appear prefixed with `apps/backend dev:`; `apps/frontend` runs `vite`. Ctrl-C takes all of it down and leaves no orphaned `node`, `tsc` or `vite` process, and releases both ports — verified in Task 1.2.6 and re-verified across all three packages in Task 1.3.5, counting survivors in the process group rather than trusting the supervisor.

**A clean Ctrl-C at the root is noisy, and the noise is not a failure.** pnpm reports each interrupted watcher as `Failed`, prints `[ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL] ... Command failed with signal "SIGINT"`, and adds a spurious `[WARN] Local package.json exists, but node_modules missing, did you mean to install?`. Nothing is missing — `node_modules` was checked immediately afterwards. Do not go looking for a broken install. **Task 1.8.2 tried to fix it and could not, and the package it blames is a race.** `pnpm -r` reports whichever watcher exits first, so the `Failed` line named `packages/shared` in three runs and `apps/frontend` in a fourth — there is nothing truthful for it to say. Every lever was measured: `--no-bail` drops the `ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL` block but prints **two** `Failed` lines, keeps the false warning, and stops a genuinely broken dev script aborting the run; `--loglevel error` drops the false warning and suppresses **every** child's streamed output, the server's log included; `--silent` prints nothing at all. The remaining option is a SIGINT-trapping shell wrapper per package, which is two new files in the part of this repository `pnpm verify` reads with nothing. So it stays, and Task 1.8.5 documents it.

`--preserveWatchOutput` is load-bearing rather than cosmetic: without it a `tsc --watch` clears the terminal on every rebuild and takes the other packages' output — including the server's log — with it. **Re-checked in Task 1.8.2 with a positive control, and the check needs a pseudo-terminal**: tsc only clears on a TTY, so a redirected log shows nothing either way. Under a real pty over a start and one rebuild, `tsc -b --watch` emits its clear sequence **twice** and `tsc -b --watch --preserveWatchOutput` emits it **zero** times. Note the sequence is `ESC[2J` followed by `ESC[H`, which is **not** Vite's — see the frontend baseline below. Two tools, two ways of clearing a screen, and a grep written for one reports zero for the other and reads as a pass.

**Editing `apps/backend/package.json` bounces the dev server**, which reads as a bug during unrelated work and is not one. That file is now both a TypeScript program input and a file the running process loads, because the health route imports it for `version` — so adding a dependency triggers a `tsc` rebuild _and_ a `node --watch` restart. Both observed, not reasoned about.

**Root `pnpm dev` builds `packages/shared` twice** — once in its own watcher, once through the backend's `tsc -b --watch` following the project reference. Harmless, and worth knowing because the symptom of it going wrong would be a corrupted `.tsbuildinfo` with no obvious cause.

Every command in this section was executed from a clean clone in Task 1.1.8, the backend's were re-run from a clean build in Task 1.2.6, and all of them again from a second clean clone with a cold pnpm store in Task 1.3.5. `README.md` carries the same set for humans; keep the two in step.

**The dev loop's restart timing has a baseline, so a regression is visible.** Edit to new listener is ~1.1s, of which `SIGTERM` to the new listener is ~100ms (Task 1.2.4 measured 140ms) and the rest is tsc's incremental compile. The drain itself is sub-millisecond. Seconds rather than milliseconds in the signal half means a route acquired a dependency that does not close promptly. Note also that a Ctrl-C in the dev loop now logs `signal received` / `shutdown complete` on the way out — a _silent_ Ctrl-C is the symptom, not the normal case.

**The frontend has its own baseline, and it is a different mechanism.** HMR edit-to-visible-update is **~100–140 ms warm**; the first edit after a server start is ~850 ms and is not the number to regress against (Task 1.3.3). **Re-measured in Task 1.4.6 with the styling pipeline in it, and the two kinds of edit are not the same number:** a **CSS-only** edit lands in **24–130 ms** (median ~72 ms) and a **component** edit in 177–280 ms, first-edit-after-start 977 ms. Both component figures are upper bounds — the measuring tab reported `visibilityState: "hidden"`, which throttles React's scheduler — so compare the two kinds of edit to each other rather than the component number to 1.3.3's. A cheaper way to prove it was HMR and not a reload than the counter below: check `performance.timeOrigin` is unchanged. Two notes on _how_ this is checked, because the obvious method is wrong twice over. First, **editing a heading and watching it change does not test HMR at all** — it passes identically on a full page reload. The check needs component state: add a counter, click it to a non-zero value, edit a _different_ line, and confirm the number survived (done again in Task 1.3.5, then removed). Second, `clearScreen` cannot be verified through a redirected log — Vite only clears on a TTY, so both settings look identical — and the clear sequence is `ESC[1;1H ESC[0J` rather than the `ESC[2J` a grep reaches for first, which reports zero either way and reads as a pass. That is **Vite's** sequence; tsc's is `ESC[2J ESC[H`, measured in Task 1.8.2, so the two tools need two different greps.

**The frontend dev server does not typecheck, and its two failure modes are opposites.** A **type** error is applied as an ordinary HMR update — no overlay, no console error, state preserved — and is caught only by the editor or `pnpm verify`. A **syntax** error fails the oxc transform loudly, logs source context, and leaves the page on its last good render. The first is the dangerous one: a green-looking dev server is not evidence of a compiling tree, which is why `build` runs `tsc -b` before `vite build`.

**Both frontend servers bind IPv6 loopback; the backend binds IPv4.** `vite` and `vite preview` listen on `[::1]`, so `curl http://localhost:5173/` works while `curl http://127.0.0.1:5173/` is connection-refused. `apps/backend` defaults to `127.0.0.1` and is the reverse. Both are "localhost" to a browser and are not to a script — measured in Task 1.3.5, and it matters for anything Story 1.10 or 1.11 writes as a health check.

**Three ports, two of which are decisions.** Backend 3000 and dev server 5173 were chosen; preview 4173 is Vite's default written down explicitly, because `preview` **inherits** `server.strictPort` but **not** `server.port` — measured both ways. `preview.strictPort` is deliberately absent for the opposite reason: it _is_ inherited, and a second copy is one more place for the two to disagree on an upgrade. `strictPort: true` means a busy 5173 or 4173 exits 1 rather than quietly binding the next port up, matching the backend's `EADDRINUSE` behaviour; the deciding reason was Story 1.12's CORS allowlist, which a silently moved port fails as a browser error naming neither the port nor the cause.

**Most root scripts do not fan out, and `build` is now the exception that proves the rule.** `typecheck` is still a single `tsc -b` over the root solution `tsconfig.json`, because the reference graph already orders the work — `pnpm -r run build` would build `packages/shared` three times. **Root `build` is no longer a bare `tsc -b`**: it is `tsc -b && pnpm --filter @marketpulse/frontend exec vite build`, because the frontend's TypeScript half is `noEmit`, so a plain `tsc -b` would typecheck the frontend, emit no bundle, and let `pnpm verify` pass without the bundler ever running. It names one package rather than fanning out, for the reason above — which means **a second frontend package would be silently missed**. Since Task 1.4.5 it names that package **twice**, because `storybook build` is a third clause on the same line, so there are now two places to miss it. Read the root `build` whenever a package is added; it is the one root script that hardcodes a package name. `lint` is a single root `eslint .` because each package's `eslint .` resolves the same root config, so a fan-out starts three ESLint processes each building its own typescript-eslint project service over the same solution. Only `test` and `dev` are genuinely per-package and use `pnpm -r`. Keep the per-package scripts for working on one package; the root ones are the direct call.

The root `tsconfig.json` is a solution file — `files: []` plus three `references`, compiling nothing itself. It does **not** extend `tsconfig.base.json`, and should not: inheriting compiler options would imply it has sources.

**`typecheck` and `build` are the same command on purpose.** Consumers compile against `packages/shared/dist/*.d.ts`, so typechecking this workspace _is_ building it; there is no cheaper correct pass, and a per-package `--noEmit` fan-out is exactly the thing that passes against stale declarations. Both names are kept because they can diverge later without a rename. `packages/shared`'s `typecheck` was `tsc --noEmit -p tsconfig.json` until Task 1.1.7 and is now `tsc -b` like everything else.

`verify` chains with `&&`, so the first failure is the exit code, and a failing package script propagates up through `pnpm -r` (verified: a package `test` exiting 3 gives root exit 3).

**`tsc -b --clean` deletes the output of the sources that currently exist, so a hand-deleted source orphans its output permanently.** Delete `src/routes/thing.ts` and `dist/routes/thing.{js,d.ts,js.map,d.ts.map}` survive every subsequent `pnpm clean` — the build state is not what drives the deletion. Measured in Task 1.2.6 after the reverse was written down as a guess; Task 1.2.5 found the residue and Task 1.2.6 found the actual mechanism. **Clean before deleting a source file, or delete its output by hand afterwards.** The symptom is stale files in `dist/` that look like a broken build and are not.

**That trap does not reach `apps/frontend`.** Its `dist/` is Vite's, not tsc's, so its `clean` is `tsc -b --clean && rm -rf dist` — and `rm -rf` is content-blind, deleting the directory whatever sources exist. The root's `clean` gained the same second half for the same reason. The worry that motivated re-checking it turned out to be moot anyway: **`build.emptyOutDir` defaults to true** when `outDir` is inside the project root, so Vite empties the directory on every build and hashed assets never accumulate. Measured in Task 1.3.4 after the opposite was assumed. It is a **default rather than a guarantee** — `emptyOutDir: false` brings the whole problem back.

**`apps/backend/dist` is not a runnable artifact on its own, for two independent reasons, and the first hides the second.** Copied elsewhere it fails at import time on `fastify`, before it ever reaches the health route's read of `../../package.json`; give it a reachable `node_modules` and it then fails on the manifest. Both are `ERR_MODULE_NOT_FOUND` before `listen`. The **package directory** — `dist` + `package.json` + `node_modules` — does run outside the workspace, verified. "Copy `dist/` to the server" is the obvious wrong move and the error message names only half the reason. Story 1.11 owns the real answer (`pnpm deploy --filter`).

**`apps/frontend/dist` is the opposite, and the asymmetry is the point.** It _is_ a runnable artefact on its own: **three files** since Task 1.4.2 (it was two until the first stylesheet; the token layer in Task 1.4.3 grew the stylesheet from 0.07 kB to 3.04 kB, the semantic layer in Task 1.4.4 to 6.22 kB and the components in Task 1.4.5 to 7.21 kB, none of them adding a fourth), no `package.json`, no `node_modules`, zero bare imports left in the bundle. Copied outside the workspace and served by `python3 -m http.server`, it renders. Two consequences for Story 1.11 that neither app implies on its own — the emitted asset path is **absolute** (`base` defaults to `/`), so a subpath deployment is a `base` change and a **rebuild** rather than a hosting setting (**one** edit since Task 1.6.5, not two — see below); and rebuilding `packages/shared` does **not** reach a built frontend, because the shared code is inlined at bundle time and the workspace symlink is not part of the artefact. Both measured in Task 1.3.4.

**`pnpm verify` no longer covers every file in the repository, and there are now two gaps.** `apps/backend/scripts/dev.sh` is checked by nothing: ESLint sees only JS and TS, Prettier has no shell parser and skips it silently, and `tsc` has no view of it. A typo there is not an error, it is a silent fallback to JSON in the dev loop. Re-dated 2026-09-01 in Task 1.7.7 and still accepted. The second is smaller and the same shape: two `clean` scripts now contain `rm -rf` fragments — unchecked shell inside a JSON string, and Task 1.4.5 added `storybook-static` to both. Not worth a `shellcheck` dependency and another `verify` step for one small file and two small strings — a known and dated choice (2026-08-30), not something CI quietly catches. Note `scripts/check-stories.mjs` and `scripts/check-env-example.mjs` are **not** further gaps: both are JavaScript, so ESLint and Prettier cover them. Story 1.10 carries the same note.

**And there is a third kind of gap that this list does not describe, found by Task 1.6.4 and worth more than the two above.** The gaps here are _files no tool reads_. The other kind is a file every tool reads carrying a guarantee that has quietly stopped being enforced: `apps/frontend`'s explicit `types` array was written down in three places as making `process` a compile error in browser code, and it stopped doing so in Task 1.4.5 — when `.stories.tsx` files entered the program and dragged `@types/node` in through a triple-slash reference — and stayed wrong for two stories. Nothing caught it, because nothing was checking; it was a stated invariant rather than a checked one. Two of this repository's checks now exist for exactly that reason — `env:check`, and the `no-restricted-globals` block over `apps/frontend/src/**`. **The general form: re-measure a stated invariant rather than citing it, especially one in this file.** Story 1.10 inherits this alongside the two gaps.

**Backend configuration is one module, hand-rolled on purpose, and `apps/backend/src/config.ts` is the only file in the workspace that reads `process.env`** — verified by grep, and the single occurrence is the default parameter of `loadConfig(env = process.env)`. Task 1.6.1 spiked Zod 4.5.4 and Valibot 1.4.2 to full parity and threw both away: a schema over `process.env` is a schema over strings, so blank-means-absent and a message quoting the value the operator typed have to be hand-written either way, `z.coerce.number()` reports `NaN` and loses the input, and `PORT=` parses as **port 0** rather than as the default. Recorded so nobody re-derives it: one single-key schema in the frontend bundle is **+74.88 kB for Zod** and +3.14 kB for Valibot, and Zod costs ~19 ms on every server start. Four things about the module. It **throws and never exits** — `index.ts` catches `ConfigError`, writes the plain stderr line and calls `process.exit(1)`, because a config module that exits cannot be tested. It **validates on call, not on import**, for the same reason `buildServer()` does not listen. It reports **every** bad key rather than the first, via an eleven-line accumulator whose two dead-at-runtime `undefined` checks exist to narrow types without a non-null assertion `strictTypeChecked` would reject. And it exports **`CONFIG_VARIABLES`**, a `{ key, required, default, description }` table that Task 1.6.6 walks to check `.env.example` — deliberately a table beside the readers rather than above them, so the two are kept in step by that check and not by a generic executor. It costs nothing measurable: start-to-listening is 76 ms median against 77 ms for the inline version it replaced. There are `readString`, `readInt` and — since Task 1.7.1 — **`readEnum`**, which Task 1.6.3 predicted `LOG_LEVEL` would bring and which `LOG_FORMAT` immediately reused. Its `allowed` array is the source of both the check and the error message, so a value added to a vocabulary cannot be accepted while the message still advertises the old set; the one cast in the file is its return, because `includes()` on a `readonly T[]` narrows nothing in TypeScript.

**Logging is Fastify's built-in pino, configured by two variables and nothing else so far (Task 1.7.1).** `LOG_LEVEL` admits pino's whole set — `fatal`/`error`/`warn`/`info`/`debug`/`trace` plus `silent` — deliberately rather than a curated subset, because a narrower list is a second vocabulary to keep in step with the logger's own. `LOG_FORMAT` is `json` (default) or `pretty`. `buildServer()` now **takes** `{ logLevel, logFormat }` rather than being argument-less: there is no default in `server.ts`, because a default there would be a second copy of `config.ts`'s and Story 1.9 wants `buildServer({ logLevel: "silent", logFormat: "json" })` explicitly. The `transport` key is set **only** for `pretty`, so the JSON path starts no worker thread. Four measurements: the transport costs **+6 ms** on the 73–74 ms start-to-listening median and **+1 ms** on the 2 ms SIGTERM-to-exit, the dev loop's edit-to-listener is unchanged at 805–973 ms either way (against the ~1.1 s baseline), and **5000 records followed immediately by `process.exit()` lost nothing** in either mode, to a file or to a pipe — so the worker-thread flush worry does not materialise here and Task 1.7.5 inherits that rather than a suspicion. `pino-pretty` is pinned at 13.1.3, is **12 packages and 448 kB**, and trips no install script — `esbuild` is still `allowBuilds`' only entry. It is a **`dependency` and not a `devDependency`**, against the first read of the house rule: nothing `import`s it, the target is resolved by name from a string at runtime, and a pruned tree turns the documented `LOG_FORMAT=pretty` into `ERR_MODULE_NOT_FOUND` at startup in the one environment that is hardest to debug. Note also that `pino` itself is **not** directly importable from `apps/backend` — it arrives transitively through Fastify and pnpm's strict linking hides it, so anything that wants a logger goes through `app.log`.

**Three consequences of the level that a reader will otherwise discover the hard way.** At `warn` and above a healthy server is **completely silent**, its `Server listening at …` line included, because nothing in a normal run emits above `info` — so a supervisor or health check waiting on that line hangs, which matters for Stories 1.10 and 1.11. `silent` is worse in the same direction and is in on purpose for Story 1.9's `app.inject()`. And **`LOG_LEVEL=debug` currently shows nothing `info` does not**, because Fastify's request logging is at `info` and this application emits below it nowhere; the variable is real and its lower half is empty.

**Every request carries a UUID correlation id, and it leaves the process (Task 1.7.2).** `genReqId` is `crypto.randomUUID()` — Fastify's default is a per-process counter starting at 1, which collides across every restart and across every instance Story 1.11 might run. An `onRequest` hook puts it on the reply as **`x-request-id`**, so it is present on a 404 and on a thrown 500 where no route code runs at all; that was verified on all three status codes rather than on `/health` alone. `apps/backend/src/request-id.ts` is the only place the header is spelled, and Task 1.7.3 is where that name may move to `packages/shared` beside the error shape — Story 1.12 must import it rather than writing the string out again. **An inbound `x-request-id` is honoured, validated against `^[A-Za-z0-9_-]{1,128}$`**, and a failing value is dropped rather than sanitised, because a repaired id is a different id. The pattern excludes whitespace, control characters, quotes and commas; a raw-socket attempt to close the JSON object and forge a record (`curl` refuses to send one) was rejected by the pattern, zero forged lines in the log. Two things not to undo: Fastify's own **`requestIdHeader` adopts the header with no validation at all** and defaults to `false` in 5.12.1, so turning it on is a regression dressed as a simplification; and a W3C `traceparent` was rejected as a propagation _format_ whose model Epic 10 should adopt whole rather than cargo-culting the header.

**The request record is now chosen rather than inherited, and narrowing it made the log smaller despite a 36-character id.** The `req` serialiser emits **`method` and `url` and nothing else**; `res` is deliberately left as Fastify's one-field default. `host` went because it is this server's own bind address; `remoteAddress` and `remotePort` went because behind Story 1.11's proxy they become the _proxy's_ address, so they would be **wrong** rather than absent — the privacy dimension is real but is not the deciding argument. `url` and not `path`, so the query string is logged, which rests on the standing rule that personal data never goes in a URL; that rule is load-bearing here now. The serialisers sit beside `level` and **outside** the conditional `transport` spread, so they apply in both formats — a serialiser added inside that spread would apply in `pretty` only. Measured, and re-measured in Task 1.7.7 against a Fastify instance running the same route on Fastify's own defaults: the JSON pair per request went **431 → 422 bytes** and `pretty` went **15 → 12 rendered lines**, so request logging is now _less_ likely to bury the `signal received` / `shutdown complete` pair the dev loop relies on. **Task 1.8.2 then took `pretty` to 2** — see the rendering paragraph below; the 12 is what the default rendering costs and is still what the serialiser is measured against. Two caveats on those numbers. **The byte figures are machine-dependent** — `pid` width, `hostname` length and `responseTime`'s digits all move them, which is why Task 1.7.2's 427 → 416 and this 431 → 422 are the same 9-byte saving measured on different pids; quote the saving, not the totals. **The line count is exact and Task 1.7.2's 9 does not reproduce** — it is 12, six per record (message, `reqId`, and a four-line `req` or a `res` plus `responseTime`). The finding that matters survives both corrections: the record got _smaller_ despite a 36-character id. `responseTime` is **fractional milliseconds over the request lifecycle** — confirmed against a route sleeping 250 ms, which logged 262.35. Id generation is 34 ns against the counter's 11 ns.

**`pretty` is configured, not defaulted, and it is two options (Task 1.8.2).** `singleLine: true` and `translateTime: "SYS:h:MM:ss.l TT"`, both on the transport, and nothing else in the workspace changed for them. `singleLine` is the whole of Story 1.8's legibility fix: a `GET /health` in the shared `pnpm dev` terminal went **12 rendered lines to 2** and a 404 **14 to 3**, with no field dropped and the severity floor untouched — the record is the same record, rendered flat. Task 1.8.1's controlled session (one page load, three requests, three frontend edits, one backend edit) went **47 lines to 16**. A restart went 8 lines to 7, because `signal received, shutting down` now carries its `signal` inline. Four things not to undo. **A stack is still multi-line** — that is pino-pretty's own behaviour and it was verified on the shipping server with a throwing route, so a 500 is two flat records with an indented `stack` between them and an `EADDRINUSE` at startup reads the same. **`SYS:` is load-bearing and its absence is silent**: without it `translateTime` formats in **UTC**, a clock that disagrees with tsc's and Vite's by a whole timezone while looking entirely plausible; with it the stream has two conventions rather than three, since pnpm stamps nothing. **Nothing is `ignore`d**, and dropping `reqId` and `pid` was measured and rejected — it takes the widest request line from 172 to 117 columns, which is the difference between wrapping and not, but `reqId` is the field that exists to survive interleaving and Story 1.12 is what introduces interleaving; `pid` is what distinguishes a restart from a reload. And **`messageFormat` was tried and rejected**: a template applies to every record and there is no per-record form, so `{req.method} {req.url}` reads well on the two records that have a `req` and leaves a run of spaces on `Server listening at …`.

**`LOG_LEVEL` was deliberately not the lever, and `pnpm dev`'s startup did not move.** The obvious quieter-dev-loop change is a lower level, and it costs the trap three paragraphs down: above `info` a healthy server is completely silent, its `Server listening at …` included, so a quiet loop and a failed start are the same terminal. Rendering has no such cost. Re-measured after the change: startup is **13 lines and 0.83 s warm** (1.8.1's 0.73 s; the difference is Vite's own `ready in` moving 114 → 173 ms between runs, not the transport), backend edit-to-new-listener is a **1016 ms median** against 963 ms, and a frontend component edit is a **486 ms median at `visibilityState: "hidden"`** against 1.8.1's hidden band of 483–666 — hidden against hidden, because an automated tab cannot be foregrounded and a hidden tab costs 4–6×. Ctrl-C is still eight processes to **zero survivors** with both ports released. One trap in re-checking that last one: `lsof -ti tcp:5173` briefly counts the **browser's** client socket, so look for a LISTEN state rather than for any holder.

**The API's error shape is one interface in `packages/shared`, it is flat, and `apps/backend/src/errors.ts` is the only file that constructs one (Task 1.7.3 defined it, Task 1.7.4 wired it).** `ApiError` is `{ code, message, requestId, details? }` — a **wire shape, not an `Error`**; shipping the contract unused for exactly one task was preferred to half-wiring a handler. Four decisions, each against a named alternative. **Flat rather than `{ error: { … } }`**, decided on one question rather than on taste: `requestId` is a property of the _response_ and not of the failure — the same id is on successful responses as `x-request-id` — so inside a wrapper it is misfiled and outside it the payload has two levels for four fields; the HTTP status has already done the wrapper's usual job. **RFC 9457 `application/problem+json` was rejected for the same reason `request-id.ts` rejected `traceparent`** — its discriminator is a `type` **URI** meant to dereference to documentation, and taking the field names without the URIs is the shape of the thing without the thing; its `title`/`detail` pair is also prose where `code` is a union. **`code` is a union whose every member is measured rather than anticipated** — it names a failure the server can be made to produce. Task 1.7.3 shipped `NOT_FOUND` and `INTERNAL_ERROR`; Task 1.7.4 added **`BAD_REQUEST`** under the same test, and its measurement is the counter-intuitive one — see below. SCREAMING_SNAKE unlike `AnomalyBand`'s lowercase, because those are names an interface renders and these are discriminators a client switches on. **`details` is `readonly string[]` and never a `Record<string, unknown>`**, because an open-ended object is the field a leak arrives through; every entry is a sentence already fit to show a user. Two fields are deliberately absent: `statusCode`, which Fastify's own default body has and which is a second place for the status to be wrong, and any `timestamp`, which the log record already has and the correlation id already joins. And it is a **transport** error and not a `Finding` — invariant 5's `CONFIRMED`/`SUPPORTED`/`POSSIBLE`/`UNKNOWN` and "not enough evidence" are a **successful** response, and conflating the two would be expensive to unpick.

**`REQUEST_ID_HEADER` moved to `packages/shared` with it, and only the name moved.** Generating an id and validating an inbound one are server behaviour with a threat model behind them, so they stay in `apps/backend/src/request-id.ts`, which now imports the constant. The rule the move buys: Story 1.12 and Epic 10 **import** the name rather than writing `"x-request-id"` out again, because a header-name typo is a compile error nowhere and silently disables correlation on the path it was added to. Note the contrast with Story 1.6, which declined to put the _configuration_ type here — the two apps share no environment variable, so that would have been a shared file with one consumer. Shared means both sides depend on the same fact, not "shared is where types go". The cost is real and is stated in the file: shared is consumed as **built output**, so changing the error shape means rebuilding before either app typechecks against the change; `pnpm build` and `pnpm verify` order that, a bare `tsc --noEmit` in an app passes against the previous shape.

**Task 1.2.3's deferred response-schema question is closed: Fastify's built-in JSON Schema, per route, no new dependency.** ajv and `fast-json-stringify` arrive with Fastify, so this is zero packages. Story 1.6's argument against a schema library does **not** transfer and was not reused — that was a schema over `process.env`, which is a schema over strings, and a response body is typed data. The reason to have one is not validation: Fastify serialises through `fast-json-stringify`, which **strips every property the schema does not declare**, measured on this route — a `secret` field added to the body vanished from the wire with the schema in place and was serialised verbatim without it. That is a mechanism behind "no internal detail reaches a client" rather than a habit of remembering. The schema is also not a tax: the same route over 20 000 `app.inject()` calls is **11.9 µs against 14.9 µs** without one.

**The silent-stripping hazard was closed rather than accepted, and the idiom is three lines and zero dependencies.** Add a field to `HealthResponse`, forget the schema, and it disappears at runtime with a green `tsc -b`, a green lint and a green build — a **fourth** silent-failure class beside the misspelled CSS Module class, the missing `.js` import extension and the unchecked router path. What closes it is declaring the schema's properties `satisfies Record<keyof HealthResponse, JsonSchemaProperty>`: a field on the interface and not in the schema is **TS1360** naming the missing property, verified in the real tree, and a property here that is not on the interface is an excess-property error. `required` is `Object.keys(properties)` so it cannot fall behind either. **Copy this idiom for every new route.** Deriving the type from the schema (`json-schema-to-ts` or a Fastify type provider) was the alternative and buys two more things this does not, at the price of a dependency: two gaps stay open and are **known and dated 2026-09-01** — a declared property whose JSON type disagrees with the TypeScript one is **coerced silently** (a `number` declared `"string"` went out as `"1.5"`), and a `required` property the handler omits is a **500 at runtime** with `"x" is required!` rather than a compile error. The first is the one worth watching.

**`exactOptionalPropertyTypes` finally bit in real code here, and `apiError()` is the shape of the answer.** The obvious constructor — `return { code, message, requestId, details }` with `details?: readonly string[]` as a parameter — is **TS2375**, because the parameter infers as `readonly string[] | undefined` and that is not an optional `readonly string[]`. So the function branches and builds the object two ways. That is not style: it is what makes an absent `details` genuinely absent rather than explicitly unknown, which is the domain distinction the setting exists for.

**Both of Fastify's failure paths are replaced, and they are two paths rather than one (Task 1.7.4).** `setErrorHandler` never sees an unmatched route — Fastify answers that through `setNotFoundHandler` — so registering only the first leaves "API errors use a single consistent shape" false the first time anyone mistypes a URL. Both are registered on the root instance inside `buildServer()`, which is what gives Story 1.9's `app.inject()` instances the contract for free; anything registered in `index.ts` would not be under test. The defaults they replaced were measured first, and their **field order differs between them** because they come from different places: `{"message":"Route GET:/nope not found","error":"Not Found","statusCode":404}` against `{"statusCode":500,"error":"Internal Server Error","message":"…"}`.

**`BAD_REQUEST` is the third code, and it exists because of a measurement that is easy to get backwards.** With a single `GET /health` route and nothing in the tree accepting a body, `POST /health` with `content-type: application/json` and a malformed body is a **400** (`FST_ERR_CTP_INVALID_JSON_BODY`) and a 2 MB body is a **413** (`FST_ERR_CTP_BODY_TOO_LARGE`) — because Fastify's content-type parser runs **before** its not-found handler. A 415 is _not_ reachable: an unparseable content type resolves to a 404, so `UNSUPPORTED_MEDIA_TYPE` was not added. That is 1.7.3's test applied rather than restated — a member per failure that can be produced, not per failure that can be imagined. One member covers 400 and 413 together, decided on what a client branches on: both mean "your request was not acceptable, fix it and retry", and the status line still carries the difference. The reversal trigger is a caller that has to behave differently on a 413.

**The mapping is status-first and is written out in `errors.ts`:** 404 → `NOT_FOUND`, any other 4xx → `BAD_REQUEST`, 5xx → `INTERNAL_ERROR`, and an error carrying no `statusCode` (or one outside 400–599) is a **500** — an error handler running at all means something failed, and a reassuring status would be a lie. **A 5xx never carries the thrown message.** Fastify's default returns it verbatim, measured: a route throwing `connection to postgres at 10.0.0.4:5432 refused` answered with exactly that string. The stack never reached the client even by default, so **the stack was never the whole risk** — a message written for a developer is internal detail too, and it is the half that looks harmless. A 4xx passes Fastify's own message through, because it describes the client's own request; the line to revisit is the day a 4xx message interpolates request content, which request schemas would bring.

**Criterion 6 has two mechanisms and only one of them covers everything.** `apiError()` is the one that does: it builds an object with four slots and no room for a fifth, so nothing can leak from any path. The response schema is the second and is **per-route and opt-in** — measured both ways, a body the error handler decorated with `stack` and `cause` reached the wire as the four contracted fields on a route declaring `500: apiErrorSchema`, and with both extras intact on one that did not. The gap that follows: **`setNotFoundHandler` is not a route and can never have a response schema**, so the serialiser is structurally unavailable on the 404 path and the constructor is what has to hold there. Declare `500: apiErrorSchema` on every route that can fail; nothing in `pnpm verify` checks that you did. Verified end to end: a thrown error carrying `cause: { dsn: "postgres://user:hunter2@…" }` and a `query` property put both on the level-50 log record with the full stack, and neither on the wire.

**The error schema does not copy `/health`'s idiom verbatim, and the one difference is exactly the trap 1.7.3 documented.** `/health` derives `required` from `Object.keys(properties)`, which is exact only because every field of `HealthResponse` is required. `ApiError.details` is optional, so the same derivation would mark it required and 500 at runtime on **every** error without details — which is every error this application currently produces. So `required` is a literal of three and the `satisfies Record<keyof ApiError, JsonSchemaProperty>` guard carries over unchanged. `code` also declares `enum: API_ERROR_CODES`, so the union is enforced in three places that cannot disagree. `JsonSchemaProperty` moved out of `health.ts` into `apps/backend/src/json-schema.ts` when the second schema needed it — two copies of that type is how two schemas stop agreeing.

**Log levels are split by class, and Fastify already split them — this keeps its split rather than inventing one.** Measured on the defaults: a 5xx wrote a level-**50** record carrying `err` with the full stack, a 4xx a level-**30** record also carrying `err`. So `errors.ts` logs a 5xx at `error` and a 4xx at `info`, through `request.log` rather than `app.log` so every record carries `reqId`. `info` and not `warn` for the 4xx, for a reason beyond aggregator noise: Task 1.7.1's property is that at `LOG_LEVEL=warn` a healthy server is completely silent, and **a server answering 404s is healthy** — `warn` would break that. The consequence to know is the other side of the same coin: at `warn` a 404 leaves no trace at all, verified. **The record count did not move** — three records per failure before and after, because Fastify's own error logging lives in the default handler that these replace, so there is no doubling. The not-found handler logs `route not found` explicitly for that reason: without it, replacing Fastify's handler would have removed its `Route GET:/nope not found` record and left a 404 nobody could investigate.

**The 404 message deliberately does not name the route, and Fastify's did.** Reflecting an unvalidated request URL into a response body is a shape worth not having even where the JSON serialiser makes it harmless, and — the deciding argument — **the client already knows which URL it asked for**, so the reflection buys it nothing, while the log record has the method and the url beside the same correlation id. `x-request-id` survives both custom handlers: re-verified on a 200, a 404, a 400, a 413 and a thrown 500, and the body's `requestId` is the same value as the header on every one. Task 1.7.2 proved that against Fastify's _own_ handlers, so it was an expectation here and not a measurement until it was re-taken.

**Production error detail: there is none, and no variable turns it on.** The stack is already in the log line beside the correlation id the client was handed, so a developer loses nothing by never exposing it — and an `ERROR_DETAIL` switch would be the same shape Task 1.7.1 rejected `redact` for: a setting whose misconfiguration leaks, silently, outward. Safe by construction beats safe when configured correctly. This is also why criterion 6's "in production" needed no environment concept; Task 1.6.3's decision holds for the second time in this story.

**The two crash handlers are in `index.ts` and they replace a stream, not a silence (Task 1.7.5).** The criterion's wording is slightly wrong about the baseline and it was measured before anything was written: Node 24 already prints a stack for both an `uncaughtException` and an `unhandledRejection` and already exits **1**. What it does not do is put that stack in the **log stream** — it is raw stderr with no level, no timestamp, no pid and nothing an aggregator indexes, while every other record this process writes is JSON on stdout, so a deployment collecting stdout loses the crash and keeps everything else. The two defaults are also **indistinguishable from each other** in that output; the handlers' `event` field is what tells them apart. They log through `app.log` and that is the only option rather than the lazy one — a process-level handler is handed an error, not a request, so there is no `request.log` and therefore no `reqId`. They live in `index.ts` and not in `buildServer()` for the same reason the signal handlers do: process-wide handlers installed by a factory are a surprise for anything building two instances, which Story 1.9 will.

**A crash ignores `LOG_LEVEL`, and that exception is exactly one record wide.** `app.log.level` is set to `fatal`, the record is written, and the **previous level is restored** — and the restore is not tidiness. The first version of the function left it mutated, and a crash-during-drain run silently lost `shutdown complete`; the level-50 `shutdown timed out, forcing exit` from the ceiling would have gone the same way. (Fastify's per-request child loggers keep the level they were created with, so request records carried on appearing while the root logger's did not — which is why the loss looks selective rather than total.) The rule in two clauses, and Task 1.7.4 is the other half of it: **ordinary traffic obeys the level; the process dying does not** — 1.7.4 logs a 4xx at `info` precisely so a server answering 404s stays silent at `warn`. Without the exception, `LOG_LEVEL=silent` would give a process that dies leaving **nothing at all**, not even Node's stderr stack, because these handlers are what replaced it. Verified at `silent` and at `warn`, in both formats. Mutating the level rather than writing a hand-rolled stderr line is what keeps one rendering of a log record — same serialisers, same format, `pretty` still pretty.

**The flush worry did not materialise here either, and it was re-taken rather than cited.** A `fatal` record followed immediately by `process.exit(1)` survives in **both** formats, `pretty`'s worker thread included, at every level tried. Task 1.7.1's 5000-record measurement is the precedent; this is the one line whose loss would be unrecoverable, so it was checked on its own. No `pino.final` and no delay.

**Both events are treated the same, and the crash does not drain.** An `uncaughtException` leaves the process in an unknown state by definition; a rejection is arguably softer, but two behaviours is two things to remember and Node's own default already treats them alike. There is deliberately **no `app.close()`** on this path — draining would serve remaining requests from a program that has already proved it is not the program you thought, and it stacks a second failure on the one being reported. So in-flight requests are dropped on purpose, which is a decision and not an oversight. Exit code is **1**, like every other failure path in this file. A crash **during** a shutdown reuses the `shuttingDown` flag: the record is written, the function returns, and the existing drain finishes — measured, not reasoned about, with a rejection thrown mid-drain against a deliberately slow route: `shutdown complete`, exit **0**, and the in-flight request answered 200.

**There are three failure experiences now, not two, and the third is the uncomfortable one.** A **contained 5xx**: the error handler answers `{"code":"INTERNAL_ERROR",…,"requestId":"…"}`, logs the stack at level 50 under that `reqId`, the server carries on, and the id the user holds finds the stack. A **crash with a request in flight**: `curl: (52) Empty reply from server`, **no body and no headers at all** — so not even an `x-request-id` — which is the one hole in the shape Task 1.7.4 made universal. And a **crash detached from the request that caused it**: a route that schedules work in a timer answers **200 with a valid `x-request-id`**, and the process dies milliseconds later; the id points at a record saying the request succeeded, because it did, and the level-60 record beside it carries no id at all. All three measured on the shipping tree. Story 1.11's operator should know the third one exists before reading a log with it in.

**The resolved configuration is never logged, and that is the redaction rule.** The tempting startup line naming what the process read becomes a credential dump the moment Epic 2's Alpaca keys and Epic 10's model key are keys on that object. `redact` was the alternative and was rejected as a denylist whose failure mode is a key nobody added to it — silent, in the place secrets are hardest to retract from. Stated in `config.ts` beside the `return`, so the next person to want the convenience reads why not. Related and still true after Task 1.7.2 narrowed the serialiser: **no request header reaches a log line**, so no `Authorization` does. That was pino's default and is now a stated choice — see the request-record paragraph below.

**The `.env` loader is `process.loadEnvFile()` called from `index.ts`, and every part of that sentence was chosen against a measured alternative (Task 1.6.3).** It reads `apps/backend/.env` — resolved from `import.meta.dirname`, so **not** the current working directory, which is what Node's own default and dotenv's would give. Both entrypoints already run with the package as their cwd so they agree either way; resolving from the module means they agree by construction and `node apps/backend/dist/index.js` from the repository root works too. **The `--env-file` flag was rejected on two counts:** on a missing file it is `node: .env: not found` and **exit 9** before any application code runs — which is what a fresh clone is — and a flag has to be repeated at every invocation site, of which there are two (`start` in `package.json`, and `node --watch dist/index.js` inside `scripts/dev.sh`, the file `pnpm verify` checks with nothing). `--env-file-if-exists` fixes the first and writes a stderr line on every ordinary start; `NODE_OPTIONS` cannot hold either flag, Node rejects them there outright. In-process there is one call site and the two entrypoints have nothing to disagree about, so `scripts/dev.sh` was not touched. Three behaviours to know, all measured: **a real environment variable beats a file entry** (tested both ways round — this is what a container depends on); **`KEY=` in a file sets an empty string rather than leaving the key unset**, which is exactly the case `present()` treats as absent, so a blank `PORT` gives 3000 and not port 0; and **a missing file is silent**, ENOENT swallowed, because two of the three environments have no file by design. Reading a two-line file does not show above run-to-run variance — 74–78 ms minimum with and without, against the same 76 ms median baseline.

**There is no environment variable, and that is a decision rather than an omission (Task 1.6.3).** `NODE_ENV` is read nowhere, there is no `APP_ENV`, and nothing in the application branches on which environment it is in. What differs between the three is where the **values** come from — a gitignored `apps/backend/.env` in development, the runner's own process in test (Story 1.9), the container's environment in production (Story 1.11) — and one precedence rule covers all three, so no code path has to know. The reversal trigger is the first thing that has to _behave_ differently rather than be _configured_ differently. **Task 1.7.1 was that test and the decision held.** The log format is genuinely different in development, and it is `LOG_FORMAT=json|pretty` — a value read by the same module with the same precedence, exactly like `PORT` — set by `apps/backend/scripts/dev.sh`, which is the file that _is_ the development loop. Nothing branches on "am I in development"; the development entrypoint simply passes a value. `NODE_ENV` was the third option and was rejected as a reversal that buys nothing over that; piping the JSON through `pino-pretty` in `dev.sh` was the first, and it costs the exit-code propagation Task 1.2.5 verified (a pipeline's status is the last command's) and the trap, which relies on `node --watch` being the shell's foreground process. Do not add a variable naming the environment before something branches on it.

**Fastify's startup log is not evidence of the bound interface.** It rewrites `0.0.0.0` to `127.0.0.1` in its `Server listening at` line, so `HOST=0.0.0.0` logs `http://127.0.0.1:<port>` while the socket really is `*:<port> (LISTEN)`. Confirmed with `lsof` in Tasks 1.2.1 and 1.2.6. Check the socket, not the log — this matters for Story 1.11.

**CSS Modules have a house idiom and both halves of it are forced by lint.** `vite/client` types a stylesheet as `{ readonly [key: string]: string }`, so `noUncheckedIndexedAccess` makes every class `string | undefined` — the obvious ``className={`${styles.a} ${styles.b}`}`` is one `restrict-template-expressions` error per interpolation, and `--max-warnings 0` makes that a failing `verify`. The answer is `cx(styles.a, styles.b)` from `apps/frontend/src/cx.ts`: dot access, composed through the helper. **Task 1.5.2 found a third door into the same problem, and it is a hard type error rather than a lint one:** a single class handed to a component whose `className` is `string | ((props) => string | undefined)` — React Router's `NavLink`, and every Base UI primitive has the same shape — fails `exactOptionalPropertyTypes` as **TS2375**, not `restrict-template-expressions`. So `cx(styles.one)` around a _single_ class is the narrowing rather than a redundancy, and it is what makes a router link's props compile at all. And the cost that has no answer — **a class-name typo is completely silent.** It typechecks, lints, builds, and renders unstyled, because an index signature has no key set to check against. Nothing in `pnpm verify` catches it; per-file generated types would, at the price of a build step and a `.gitignore` entry.

**Design tokens are CSS custom properties, and CSS is the source of truth — `apps/frontend/src/styles/tokens.ts` is a typed reader over it, not a second definition.** Task 1.4.3 rejected the generated pair (TypeScript source, emitted CSS) because it costs a build step, a generated file and a staleness check in `verify` for a benefit nothing needs yet. Four consequences worth knowing before reaching for a value from JavaScript: every token reads back as a **string** (`"4px"`, `"#f4f3ee"`), so Epic 6's WebGL renderer will need a parse layer; `getComputedStyle` runs **once** at startup and the result is frozen and cached, which is the whole reason that module exists rather than each consumer calling it; the read has to happen after the stylesheet is applied, which the built artefact guarantees because a pending `<link>` blocks script execution; and a second theme would invalidate the cache, so `readTokens()` is exported uncached. The one thing it buys back is a **checked name** — a token is a union member, unlike a CSS Module class — which is why `main.tsx` calls `getTokens()` before rendering: a token declared in TypeScript but missing from the stylesheet is a startup throw naming it, rather than a page that renders unstyled in silence.

**The theming mechanism is `:root, [data-theme="light"]`, and both halves of that selector were measured rather than reasoned about.** Themeable values (surfaces, ink, rules, the one shadow) sit in that block; geometry, spacing and type sit on bare `:root`, because a second palette would change none of them. Injecting a `[data-theme="dark"]` block of **eight values and nothing else** and flipping the attribute moved the whole page — ground, surfaces, ink and hairline — with no selector, component or markup change; removing the attribute entirely still gives the correct light page, so a missing or misspelled `data-theme` is not a themeless render. `index.html` sets the attribute anyway, so the theme is out of the first-paint path. The cost, if a second palette ever arrives: the `:root` half has to pick a side. Note also that `color-scheme: light` in `base.css` changes no pixel today — it is there so the light appearance of a native `<select>`, a scrollbar and the pre-paint background is a stated choice rather than a coincidence.

**Colour lives in exactly one file, and that is a property of the layout rather than a habit.** `tokens.css` is structural and **achromatic**; `apps/frontend/src/styles/market.css` (Task 1.4.4) holds every colour that carries meaning. The shape is a chromatic palette block plus a semantic block over it, and **exactly one indirection**: `--price-negative` resolves to `--palette-red-strong`, never to a hex, and never through another semantic token. The achromatic semantics deliberately do **not** get palette entries of their own — `--price-unchanged` is `var(--ink-secondary)`, because a second definition of `#5a5d5c` is a value waiting to drift. The palette is themeable and sits in the `[data-theme="light"]` block; the semantic mapping is not, because positive is green in every theme and only the green changes. Cascade order in `main.tsx` is `tokens.css` → `market.css` → `base.css`, and it is not alphabetical.

**No market state is legible by colour alone, and this was measured rather than asserted.** Under `grayscale(1)` the positive green and the negative red differ by **1.05:1** — they are the same tone, so the hue is the entire difference and nothing about direction survives desaturation. What actually carries it is the arrow glyph and the sign on the figure; an anomaly band is a **written name inside its fill**; a feed state is the **shape** of its marker, filled or hollow. Deuteranopia and protanopia projections of the built page separate the two price directions by 2.99:1 and 2.31:1, both olive. Task 1.4.5 is where this pairing gets a component behind it instead of relying on each author remembering. Two related notes: the anomaly ramp is amber and **deliberately not red**, because red already means price-down and an extreme anomaly on a security moving sharply up would read as a fall; and the direction glyph sits in a fixed-width box because arrows are not in the font's tabular set and would otherwise undo the column alignment.

**The names are domain and live in `packages/shared`; the colours are not and stay in `apps/frontend`.** `AnomalyBand` (`normal` / `elevated` / `unusual` / `extreme`) and `FeedStatus` (`live` / `stale` / `disconnected`) are there because the backend computes and reports both, and the alternative was two vocabularies for one thing. **The score-to-band boundaries are deliberately absent** — that is Epic 5's detection policy, and a threshold invented in a styling task would outlive the guess. Note also that `--status-error` and `--price-negative` resolve to the **same red**: there is one red, and "price down" and "this failed" are separated by presentation — a bare signed figure in a column versus a titled block with a message — rather than by hue. A stale or disconnected feed is neither, and is achromatic apart from the amber on `stale`; PRODUCT_SPEC.md §36 makes it a product state, not a failure.

**One property of `tokens.ts` that only appears once there is a semantic layer:** `getPropertyValue` returns the **substituted** value, so `--price-unchanged` and `--ink-secondary` both read back as `"#5a5d5c"`. The indirection is source-level and does not survive into JavaScript — right for a consumer that wants the colour, and worth knowing before anyone tries to verify the indirection through that module. The eleven market tokens are in `TOKEN_NAMES` because Epic 6's topology colours a node by its band and a canvas cannot read a CSS class.

**`font-variant-numeric: tabular-nums` is set once on `body` and is load-bearing rather than cosmetic.** Measured on the built page at the product's default 14px: `1,111.11`, `8,888.88` and `1,088.18` all render at **60.023 px** with tabular figures and at 44.570 / 58.844 / 53.969 px without — a 14.3 px spread, about a third of the column. Epic 3 updates these continuously, so losing it turns a live price column into visible noise. It is inherited, so a component that needs alignment should not re-declare it; a component that breaks alignment has overridden it.

**The landing route's region grid takes a `height`, not a `min-height`, and the difference is the whole layout.** With a minimum, `fr` rows still size to their content — so the primary region grows as tall as the render check inside it and §9's 3:1 / 2:1 proportions vanish into one very tall box beside a short one. Seen, not reasoned about, in Task 1.5.4. A height makes the ratios real and hands the overflow to the region, which scrolls its own content instead of pushing its neighbours around; that is also what gives Epic 6's WebGL canvas a box with a resolved size, since `fr` rows only resolve if the grid itself has a height. It is `70vh` — a proportion of the viewport rather than "the space left below the chrome", because the second means the shell owning the page's height and `App.module.css` has finished shrinking at two rules. Every colour, gap, border and font in the region stylesheets is still a token; the exceptions are grid fractions and that one viewport-relative height, which are proportions rather than design language.

**The workshop's line was settled in Task 1.5.3, and it is a directory rule with a test behind it.** A `.tsx` file under `src/components/` is workshop material and owes stories; a `.tsx` file anywhere else does not. The test for which side something belongs on is _does it have states worth reviewing side by side?_ — `AppHeader` has three feed states, an optional detail and four current-route states, so it is in; a route placeholder is one state made of two strings, so `src/routes/` is out; `App.tsx` and `main.tsx` are the router's host and the mount and render nothing to look at, so they stay exempt as Task 1.4.5 left them. **The rule is enforced in one direction only** — a component in `src/components/` without stories fails `pnpm verify`, while a stateful component dropped into `src/routes/` escapes the check silently. The argument is written into `scripts/check-stories.mjs` beside the check itself. Task 1.5.4 was the first application of it rather than a restatement: `Region` was a label and a slot, so it went to `src/routes/` and owed nothing. **Task 1.7.6 is the first time the rule has moved a file back.** A region now renders its contents or a fallback where its contents should be, which is two states worth seeing side by side, so it lives in `src/components/Region/` with a stories file. The prediction that came with it was wrong in an interesting way — see the landmark paragraph below.

**Components live in `apps/frontend/src/components/<Name>/`, one component per file, with its stylesheet and its stories beside it.** The layout is not a preference — `scripts/check-stories.mjs` depends on it, and the one-component-per-file half is what keeps that check honest: it cannot see a component declared inside another component's file, so the convention is the thing that makes the limitation harmless. Every component ships **one named story per discrete state plus an `AllPermutations` story** rendering the cartesian product in a labelled grid. Where the product is unbounded, the story fixes representative **extremes** rather than plausible examples — the widest digits, the longest ticker, a negative sign — because those are what break a tabular column, and Task 1.4.3 measured a 14.3 px spread riding on exactly that.

**`pnpm verify` has a sixth step since Task 1.6.6, and it is the first one that checks a claim rather than a file's existence.** `pnpm env:check` runs `scripts/check-env-example.mjs` between `stories` and `test`. It imports the backend's **built** `dist/config.js` — the table is TypeScript and the script is not, so `verify` building first is load-bearing; run standalone on a clean tree it says `run \`pnpm build\` first`rather than throwing a resolver error. Four checks: every`CONFIG_VARIABLES`key is in`apps/backend/.env.example`; every key there is in `CONFIG_VARIABLES`; the **default** each optional variable documents equals the one in `config.ts`; and every name in `apps/frontend/.env.example`carries the`VITE_`prefix. The third is the one a grep cannot do and the one that rots first — a changed default leaves a plausible wrong number rather than a missing line. The fourth is not a leak check: a non-prefixed name there compiles to`void 0`, so it is a variable that silently never arrives. All four were made to fail before the task closed. Named `env:check`and not`env`or`config`because both of those are real pnpm 11 built-ins and a root script shadows a built-in repository-wide — which was right for`clean`, whose built-in deletes `node_modules`, and wrong for two commands that are useful.

**The `.env.example` files are one per package, beside the file each loader actually reads, and there is deliberately no root one.** `apps/backend/.env.example` documents `PORT` and `HOST`; `apps/frontend/.env.example` documents **nothing**, because the frontend reads no configuration yet, and exists so that the file open in front of whoever is about to put an Alpaca key in `apps/frontend/.env` is the one telling them not to. A root example was rejected on a specific hazard rather than a general one: `cp .env.example .env` at the root produces a file **no loader reads**, silently, and the corrected instruction is a copy whose source and destination are in different directories. Beside the file it configures, `cp apps/backend/.env.example apps/backend/.env` is self-evidently right.

**The gitignore negation works at all three locations, and the obvious command for checking it does not answer the question.** `git check-ignore -v` exits **0** for a negated path too, printing the `!.env.example` rule that matched — so read as an exit code it says "ignored" for a file that is tracked, which is exactly the shape of a check that passes while the negation is broken. Task 1.6.7 narrowed it further, and the narrowing makes it worse rather than better: **`check-ignore` skips paths already in the index**, so the two _tracked_ `.env.example` files exit **1 with no output** while an _untracked_ one exits **0 printing the negation** — and untracked is precisely the case anyone actually checks, before committing a new example. `--no-index` makes both print the rule and exit 0. Without `-v` the exit code means what it looks like (0 ignored, 1 not), and `git status --porcelain --ignored=matching` states it outright: `!!` for the six `.env` / `.env.local` files at `apps/backend/`, `apps/frontend/` and the root, and `??` for an untracked example. Task 1.6.6 measured all nine and 1.6.7 re-measured them; the frontend's location had never been checked before 1.6.6.

**The secrets boundary was re-measured against a realistic value, and against a second artefact nobody had considered.** With `ALPACA_API_SECRET_KEY=…` and `VITE_API_BASE_URL=…` in `apps/frontend/.env` and both referenced from `main.tsx`, the built bundle contains ``console.log(`probe`, void 0, `https://api.marketpulse.example/v1`)`` — the secret's **value and its name** are both absent from `dist/` entirely. The same probe in a `.stories.tsx` emits the identical line into `storybook-static/assets/`, which matters because `pnpm build` produces that directory too and it serves from a dumb static host exactly as `dist/` does. That follows by construction from `.storybook/main.ts` reusing `vite.config.ts`, but it had never been measured. A `VITE_` prefix is a boundary against accidents, not a permission — prefixing a credential makes it a string literal in a file every visitor downloads.

**`pnpm stories` proves a file exists and nothing more, and its own header says so.** It does not prove the stories inside cover the permutations; nothing cheap can, because a variant set is a type and the check does not typecheck. It has been seen to fail — move a `.stories.tsx` aside and it exits 1 naming the file and the path it wanted. That matters: a check that has never failed is a check that has never been tested, which is the same problem as the placeholder `test` scripts one paragraph up.

**The workshop loads the same cascade the application does, and this is deliberate rather than incidental.** `.storybook/preview.tsx` imports `tokens.css` → `market.css` → `base.css` in that order — not alphabetical, same as `main.tsx` — sets `data-theme="light"` on the document element, and calls `getTokens()` as the same startup assertion. So `getTokens()` now runs in two places, and a token declared in TypeScript but missing from the stylesheets throws in the workshop exactly as it does in the application. A component that renders correctly in one and wrongly in the other is a cascade problem, and it should not be possible to have one without seeing it.

**The one place the workshop and the application deliberately differ is the router, and it is one decorator in one file.** `preview.tsx` wraps every story in a `MemoryRouter` — memory rather than browser, because the workshop is an iframe with no address bar and a story handed the browser's history could navigate the whole Storybook UI. Its entry comes from a `route` story parameter, which is what lets `AppHeader`'s current-route states be stories; they cannot be rows in a permutation grid, because the active link comes from routing context rather than a prop and two `MemoryRouter`s cannot be nested. Task 1.4.5 reused `vite.config.ts` untouched so there was exactly one place the build lived, and this decorator is a second place where the application's context is described — keeping it to one decorator in one file is the containment. Note the decorator is **named** (`const withRouter: Decorator`) rather than inline: that is the TS2883 idiom, and nothing here would catch a violation since the file is outside every tsconfig.

**The a11y panel reports, and its tab badge does not mean what it looks like.** `@storybook/addon-a11y` runs axe per story and never fails a build — the `test` parameter that would do so drives Storybook's Vitest integration, which Story 1.4 deliberately did not adopt. On `SecurityRow`'s 36-row grid: **0 violations, 17 passes, 1 inconclusive** — and the `1` on the tab is the _inconclusive_, not a violation. The inconclusive is the interesting part: it is `color-contrast` over 24 nodes, every one of them a direction arrow (`<span aria-hidden="true">▲</span>`), with axe's reason "Element content contains only non-text characters". **Automated tooling declines to judge the exact element carrying the non-colour encoding.** That is why Task 1.4.4's manual contrast and colour-blindness measurements are the record, and why Epic 15's review cannot be an axe run.

**The panel produced its first real violation in Task 1.5.3, and the permutation-grid convention caused it.** `AppHeader` renders a `<header>` and a `<nav>` — a banner landmark and a navigation landmark — so its `AllPermutations` grid put six banners on one page and axe reported `landmark-no-duplicate-banner` and `landmark-unique`, both moderate, while every single-state story reported **0 violations, 13 passes, 0 inconclusive**. The application renders exactly one header, so the finding is the grid's rather than the component's, and both rules are disabled **on that one story and nowhere else** via `parameters.a11y.config.rules` — a permanent badge trains the next author to ignore the badge, which is worse than the finding. Expect this for every landmark component: **the permutation grid and landmark uniqueness are in direct conflict, and the grid is the one that gives.**

**Task 1.5.4 took the landmark decision the regions forced, and it is the first time this application has been measured by axe outside Storybook.** Every region is a named `region` landmark — `aria-labelledby` pointing at the heading it already has, with the id from `useId()` so two regions of the same name cannot collide. The alternative was plain `<div>`s, leaving the landmark set as the chrome's banner and navigation, which is cheaper and gives a keyboard or screen-reader user nothing to jump between on the screen the product opens on. Measured with axe 4.13.0 against the built page on a static host: the landing route is **0 violations, 37 passes, 1 inconclusive** and the other four routes are **0 / 25 / 0** each. `landmark-unique` passes. The one inconclusive is the known one and has not changed — `color-contrast` over two `aria-hidden` direction arrows, "Element content contains only non-text characters".

**A render failure is contained to the box it happened in, and there are three boxes (Task 1.7.6).** One boundary around `AppHeader`, one around the route outlet, and one **inside** each `Region`, wrapping the content slot. React uses the nearest boundary, so a failure in a region's contents never reaches the outlet; the outlet's boundary is for the four routes that are deliberately a single area, where the outlet _is_ the affected region, and for a failure in the landing route's own frame. Inside rather than around the `<section>` is the decision that matters: a boundary outside it replaces the heading along with the contents, so a failed box loses its name, its landmark and its place in §9's grid. Inside, all three survive and a failed region is a labelled box with a problem in it. Every placement was exercised with a temporary throwing probe and the tree rebuilds to the same hash with the probe gone. The header's boundary is the one that would look optional and is not: without it, a throwing `AppHeader` leaves `#root` with **zero children** and an empty `<body>`, because it is the one component with nothing above it. Its cost is stated rather than discovered — the fallback replaces the `<header>`, so a broken chrome takes the banner landmark and the navigation with it.

**`ErrorBoundary` is the codebase's only class component and it does two things, neither of which is reporting.** `getDerivedStateFromError` is handed the error and deliberately does not keep it — the state is a boolean — which is what makes "the fallback never shows the error" structural rather than a habit, the same move `apiError()` makes on the backend. And the reset increments a counter used as the children's `key`, so recovery **remounts** rather than re-renders: clearing the flag alone re-renders a child still holding the state that broke it, and the user clicks a button that visibly does nothing. Recovery is never a page reload, because a reload discards the rest of a working screen. Verified in the browser: `performance.timeOrigin` unchanged, one `navigation` entry, the alert gone and the region rendering its real content. **`react-error-boundary` 6.1.4 was built before it was rejected** — +932 B and +1 module — and the deciding finding was not the bytes: its `resetErrorBoundary()` clears the error state without remounting too, so a real reset still means supplying `resetKeys` with your own counter. It is a well-tested wrapper around a `key`-based remount you still have to write, plus a second vocabulary beside four props.

**What a boundary does not catch is the frontend's half of Task 1.7.5's split, and the answer went the other way.** A boundary catches errors thrown during render, in lifecycle methods and in constructors. It catches nothing thrown in an event handler, a `setTimeout` or a promise callback — and neither does React's `onUncaughtError`. Measured: a button whose `onClick` throws leaves every region rendering normally, no fallback anywhere and **no report at all**; a `window` `error` listener added from the console was the only thing that saw it. That listener is deliberately **not** installed. The backend's `process.on("uncaughtException")` earned its place by moving a crash out of raw stderr and into the log stream every other record goes to — the change was the _stream_ — and a browser has no second stream: an uncaught error is already in the console with its stack, which is exactly where a report would go. So a listener would repeat what is there while also catching every browser extension and third-party script on the page. Story 1.12's server endpoint is the reversal trigger.

**All three `createRoot` error options are wired, to `src/report-error.ts`, and wiring them replaces React's own message rather than adding to it.** Measured: one console entry per caught error, ours, with the full component stack, and React's "The above error occurred in ..." absent. So it is a choice of wording, not an extra line of noise, and what it buys is one place to change when there is somewhere to send a report. An `uncaught` report means a boundary is missing rather than a fallback being ugly. **The `StrictMode` double-report that Story 1.7 warned about did not happen** — a render throw caught by a boundary produced exactly one `onCaughtError` report in development with `StrictMode` on, because the first of the two constructor calls aborts that render pass and React reports the failure once. The warning still stands for anything counting renders; it does not stand here, so no de-duplicator was written.

**The landmark conflict was predicted three times and does not exist, and the reason is the useful part.** Story 1.5, Task 1.7.6's brief and the first draft of `Region.stories.tsx` all expected `landmark-unique` to fire on a grid of regions the way six banners did for `AppHeader` — the disable was written before it was measured, and then removed. Three `region` landmarks in one grid report **0 violations** and `landmark-unique` is in the _passes_ list on all three nodes. `landmark-unique` keys on role **and accessible name together**, so it fires on landmarks that are indistinguishable, not on landmarks that repeat; `AppHeader`'s six banners were six copies of one anonymous thing, while a grid reviewing regions gives each cell a different name because that is what a region is. **The permutation grid and landmark uniqueness only conflict for a component whose landmark has no name.** So Task 1.5.3's `AppHeader` disable is still right and the general rule stated there was too broad.

**axe against the built page is unchanged by any of it, and the failed states were measured too.** axe-core 4.13.0 on a dumb static host: the landing route is **0 violations, 37 passes, 1 inconclusive** and the other four routes **0 / 25 / 0**, identical to Task 1.5.4. The same page with a region failed is **0 / 41 / 1** — four more passes, no violations — and with the header failed **0 / 37 / 1**, with `<header>` and `<nav>` gone from the document and all four regions still there. The one inconclusive has not moved in three tasks: `color-contrast` over two `aria-hidden` direction arrows.

**`pnpm --filter @marketpulse/frontend dev` needs `packages/shared` built first, and says so obliquely.** After a `pnpm clean` it starts, serves, and prints `Failed to run dependency scan … @marketpulse/shared … could not be resolved. **Stories are inside `tsc -b`'s program and outside the bundle, and the invariant is worth re-checking after anything that touches the entry graph.** `.stories.tsx` files sit under `src/`, so they typecheck, they lint under the full type-aware pass and the React Compiler rules, and the `.js` import-extension rule applies to them. They are unreachable from `index.html`, so `vite build` still emits **three files** and no story string appears in the output — verified by grepping the emitted JavaScript for `AllPermutations`, the story titles and the workshop stylesheet's class names, all zero. `src/components/stories.module.css` is the file to watch: it is workshop furniture, and the day it appears in `dist/assets/*.css` something has imported a story from application code.

**The Base UI seam is a popover and not a tooltip, and that is a finding rather than a preference.** `src/components/Popover/Popover.tsx` is the only file in the application that imports `@base-ui/react`. It was written as a tooltip first; measured against the built workshop, Base UI's tooltip renders **no `role="tooltip"`** and wires **no `aria-describedby`** — deliberately, and its own documentation says as much: a tooltip is for sighted users, and "if the description is important to understanding the element, don't hide it behind a tooltip". The first thing behind this seam is an anomaly score's explanation, which PRODUCT_SPEC.md §11 makes mandatory and therefore important by definition. The popover measures `role="dialog"` with both `aria-labelledby` and `aria-describedby` present. The cost is that an explanation is a click rather than a glance; if a genuine _hint_ is ever needed, it comes back as a **second** wrapper rather than as a looser version of this one. The general lesson, which Epic 15 should inherit: "accessible primitives" is a property of each primitive, not of a library.

**The wrapper rule now stands on its own reason, because the check behind it was retired.** Base UI was chosen over the lighter Radix on an intended later swap to an external shared component library, and that library's exports have never been read — Task 1.5.1 asked directly and they are **not available**, so the check is closed as unresolvable rather than deferred a fourth time. What replaces it: build against Base UI's interfaces and our own, keep every usage behind a thin wrapper in `src/components/<Name>/`, and make a wrapper's props **our** vocabulary rather than a re-export of the primitive's — `Popover` is the model at 30 lines of assembly with nothing of `@base-ui/react` in its public type. The count of files importing `@base-ui/react` is the figure worth watching; it is **one**. The swap cost is then the wrapper files rather than the application, which is the property the wrapper layer was bought for. Radix and react-aria-components remain the standing alternatives if Epic 15 finds against Base UI.

**The router is React Router 8.3.1, and two things about it are traps.** `react-router-dom` is **not** the package — it is stranded at 7.18.3 and v8 ships everything from `react-router` itself, so installing the familiar name gets a major version behind. Relative imports inside a package carry explicit `.js` extensions from `.ts` files (`./ticker.js`, and `./App.js` for an `App.tsx`). It looks wrong; `nodenext` resolution requires the _emitted_ filename and errors (TS2835) without it. Every package also needs `"type": "module"`.

**In `apps/frontend` the convention has exactly one enforcer, and it is `tsc`.** Both producers accept the extension, for different reasons — tsc maps the emitted name back under `nodenext`, Rolldown tries TypeScript source extensions for a `.js` specifier — but they do not agree on the _negative_ case. ## What MarketPulse is

An AI-assisted situational-awareness tool for US equities. It detects statistically unusual market behaviour and lets a human or an AI agent investigate it against primary-source evidence. `planning/PRODUCT_SPEC.md` is the authoritative product definition — read the relevant section before implementing a feature. Each `planning/epic-NN-*/EPIC.md` states that epic's goal, scope, exit criteria and the spec sections behind it; read the current epic's file before starting work on it.

It is explicitly **not** a trading system. It never predicts prices, recommends trades, or produces target prices.

## Non-negotiable architectural invariants

These are the load-bearing decisions. They are cheap to honour up front and very expensive to retrofit — treat a change to any of them as a design discussion, not an implementation detail.

**1. The LLM never calculates.** Every number a user sees comes from deterministic code (an analytical tool or service). The model chooses _what_ to investigate and explains results; it must not produce figures from its own reasoning. If a feature needs a number the tool layer can't produce, add the tool — don't let the model estimate it.

**2. The AI manipulates typed application state, never markup or code.** Agent-driven UI changes are schema-validated `WorkspaceCommand` objects (`focusSymbols`, `openPriceChart`, `compareSymbols`, `setTimeWindow`, `pinEvidence`, …) executed against trusted, pre-existing components. No LLM-generated HTML, JSX, or executable frontend code, ever. Validate → permission-check → execute → record in investigation history.

**3. The product works with the AI switched off.** Every analytical capability must be reachable through direct user interaction. AI accelerates investigation; it is never the only path to a feature.

**4. Temporal isolation is enforced in the data/tool layer, not the prompt.** In replay mode, no component may read data timestamped after the replay clock. This constraint belongs in the data-access and tool implementations so future-information leakage is structurally impossible — never rely on instructing the model to behave. Design data access with this in mind from the first query, even before replay exists.

**5. Confidence and provenance are part of the domain model, not prose.** Findings carry an explicit confidence level — `CONFIRMED` / `SUPPORTED` / `POSSIBLE` / `UNKNOWN`. Evidence records source, event timestamp, retrieval timestamp, calculation method, and a raw-data reference. "Not enough evidence to explain this move" is a correct, first-class outcome, not a failure.

**6. Market-data provenance is displayed, never implied.** Alpaca's free tier is IEX, not consolidated SIP. The UI must label the feed (e.g. `Market feed: IEX`) and must not suggest full US-market coverage.

**7. Provider abstractions at the edges.** Market data sits behind a provider interface; the LLM sits behind an `AgentProvider` interface (`runInvestigation` / `streamEvents` / `cancel`). No vendor SDK types leak into the domain model.

## Domain model

The core objects, in dependency order — `Investigation` → `Step` → `Finding` → `Evidence`. An **Investigation is a persisted, first-class, long-running object**, not a chat session: it outlives any single AI response and has explicit status (`running` / `awaiting user` / `completed` / `failed` / `cancelled`). Steps have observable status so the UI shows real progress rather than a generic spinner.

The frontend renders investigation state from an ordered stream of typed backend events (`STEP_STARTED`, `TOOL_CALL_COMPLETED`, `FINDING_CREATED`, `WORKSPACE_COMMAND`, `INVESTIGATION_COMPLETED`, …) — never by parsing unstructured model text. This is what makes streaming, cancellation, retries, replay and testing tractable.

Anomaly detection is deterministic and deliberately interpretable: price percentile, volume ratio, relative move vs. sector and market, and breadth, normalised into a 0–100 score. **Every score must carry its explanation.** The score measures "how unusual is this?" — never risk or opportunity.

## Intended stack

React + TypeScript, Redux for domain state, RxJS for streaming pipelines and cancellation. Node + TypeScript backend (Fastify or NestJS). PostgreSQL, optionally TimescaleDB. Sigma.js/WebGL for the market topology, with the graph model kept separate from the renderer.

WebSocket for continuous market data; SSE/streaming HTTP for agent investigation events. These two streams have different semantics and stay separate.

Resist adding libraries before complexity demonstrates the need, and don't introduce a second database in V1 without a measurement justifying it.

## Frontend structure

Feature modules under `app/`: `market`, `topology`, `charts`, `anomalies`, `investigations`, `replay`, `filings`, `shared`. Modules expose domain-level APIs; they do not reach into each other's stores. Create a module when the iteration needs it, not before.

## Delivery order

Fifteen epics, delivered in sequence — see `planning/EPICS.md`. Condensed: foundation → historical data → live data → overview → anomaly detection → topology → **deterministic investigations** → evidence workspace → SEC evidence → AI investigations → generative workspace → persistence → replay → performance → portfolio release.

Checkpoints: by end of Epic 8 MarketPulse is a credible non-AI product; Epic 10 makes it agentic; Epic 11 delivers the AI/frontend interaction the portfolio is built around; Epic 13 delivers its signature capability.

**Do not start with the AI.** The investigation engine, its analytical tools, and its event stream must work end-to-end without an LLM first. Only once the Investigation model feels correct should a model be allowed to drive it. This ordering exists specifically to prevent the architecture collapsing into `chat box → LLM → miscellaneous API calls`.

First milestone: display ~100 securities, receive live price updates, calculate an explainable anomaly score, click through to underlying price/volume evidence.

## Failure handling

Agentic failures are normal product states, not exceptions. Degrade incrementally and locally — a failed SEC lookup, analytical tool, or dropped market socket must leave the rest of the workspace and any already-gathered evidence intact and clearly labelled (e.g. "Live feed disconnected — displaying data through 10:42:17"). Never collapse to a global error screen.

## Performance targets

Measured, and published in the repo. Event → application state <250 ms p95 (excluding provider latency); 60 FPS at 500 nodes / 5k edges; >45 FPS in synthetic mode at 5k nodes / 25k edges; no routine main-thread task >50 ms; visible investigation feedback <500 ms after user action, streaming incrementally.

## Out of scope for V1

Brokerage integration, trade execution, portfolios, options, crypto, price predictions, buy/sell recommendations, social sentiment, news aggregation, real authentication, mobile UX, tick-level replay. Don't build toward these.
