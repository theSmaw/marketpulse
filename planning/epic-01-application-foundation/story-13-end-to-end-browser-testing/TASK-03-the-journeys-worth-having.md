# Task 1.13.3 — Write the journeys worth having, and state the ones deliberately not written

**Status:** Not started
**Story:** [1.13 End-to-End Browser Testing](STORY.md)
**Depends on:** Task 1.13.2

## Objective

Encode the small number of behaviours that only a browser can assert, and write down what this suite deliberately does not cover — because a suite whose limits are unstated will be read as covering everything.

## Work

- ~~**Deep-linking and the not-found route, against a host that behaves like production.**~~ **Moved to Task 1.13.5 (amended 2026-09-04), because Task 1.13.2 found the target is not a free choice.** The suite drives **the origin `CORS_ORIGIN` names**, and that is forced rather than preferred: the backend's allowlist holds exactly one origin, so a suite pointed at `vite preview` on 4173 or at a dumb static host drives a page every one of whose backend calls the browser refuses while the server logs a 200 — this story's own target failure, arriving as a property of the harness. That origin is the dev server, which **answers a deep link and `/assets/nope.js` with a 200**, so neither criterion is assertable here. They are properties of a **host**, the deployed host is the one that has `navigationFallback` configured, and Task 1.13.5 is what drives it. **The local alternative was considered and is recorded rather than dropped**: serving the built artefact at the origin `CORS_ORIGIN` names, behind a fallback with an `exclude` — which is the shape Task 1.6.5 built as a probe and did not ship. It costs a second host in the harness and a hand-written copy of the deployed host's rule, and a copy of a fallback is not evidence about the fallback that ships. Reverse this only if Task 1.13.5 turns out not to be able to hold the assertion
- **The two halves talking, which is the journey this story exists for.** The page loads, calls the deployed contract, and the status is what the backend actually said. Then break it: with a wrong allowlist the browser reports `TypeError: Failed to fetch` while `curl` with the same `Origin` gets a **200 with a full body** and the log records `statusCode: 200`. **Make that failure happen and watch this suite go red on it** — that is the acceptance criterion, and it is the one measurement that justifies the whole story
- **Story 1.12's three states and its recovery criterion.** Healthy, then the backend stopped, then the backend back — with **no page reload**. Two things about writing it: the recovery cannot be observed faster than the next poll, so read the interval Task 1.12.3 chose (`HEALTH_POLL_INTERVAL_MS`, currently 30 s) rather than hardcoding a wait; and prove the absence of a reload with `performance.timeOrigin` unchanged and exactly one `navigation` entry, which is the check this repository already uses for HMR, rather than by asserting that something did not happen
- **The visibility question is answered and the answer is `visible`, so write these as ordinary specs (settled by Task 1.13.1, 2026-09-04).** ~~Check `document.visibilityState` in the driven browser before writing anything that waits on the poll~~ — it was checked, in both candidates and in three engines, and **every one reports `visible`, `hidden: false`, `hasFocus: true`**. No override is needed and none should be written. Playwright goes further in a way worth using: **a second page does not hide the first** — both report `visible` simultaneously and `bringToFront()` changes nothing — so several pages can poll at once, which is what makes a two-tab journey writable if one is ever wanted. **The repository's recorded "an automated tab reports `hidden` and throttles React's scheduler" is a property of the browser-extension harness rather than of automation, and does not transfer**; that observation stays correct in its own context and must not be cited about this runner. Proved against the running pair rather than a blank page: the `Backend service` region goes `checking` → `healthy` and the poll fires unaided. **If a spec ever does see `hidden`, that is a harness regression to fix once and state — never a reason to weaken the visibility rule in the application**, which exists so a tab somebody forgot is not billed for
- **Playwright's default _per-test_ timeout is 30 s, so a spec that waits out a hung cycle fails before its assertion does (added by Task 1.13.2, 2026-09-04).** `playwright.config.ts` raises the **`expect`** timeout to 10 s and deliberately leaves the per-test timeout at its default, because the two are different numbers and a blanket raise would hide a genuinely stuck page. A journey waiting **36 s** for a hung poll to settle therefore has to set its own `test.setTimeout()` and say why beside it. This is the same class as the `expect` decision it inherits: a timeout picked from the healthy figure is red on the failing path
- **The two intervals are separate numbers, and one of the two written here was wrong (amended 2026-09-04).** After a cause is introduced the state changes on the next poll, so up to **30 s** — and ~~up to **35 s**~~ **up to 36 s** when the cause is a hung socket, because scheduling is on **settle** and the client's 5 s deadline elapses first. 35 is the arithmetic; **36.00 s is what Task 1.12.6 actually measured**, three times, and a timeout derived from 35 is a flake on the one path this suite exists for. Wait for the state rather than for a duration wherever the tool allows it, and where a timeout is unavoidable derive it from both constants rather than picking a number that happens to pass today
- **The healthy cycle is 30 s under Playwright and not the 31 s this repository records (2026-09-04).** Tasks 1.12.6 and 1.12.7 measured **31.00 s** and **31.05 s** and attributed the extra second to Chrome aligning timers in a backgrounded automated tab rather than to the application. Task 1.13.1 measured **30.02 s** through Playwright against the same running pair, which confirms that attribution by its absence. **Expect 30 s here, and do not read the difference from the recorded figure as drift** — both numbers are right about their own harness
- **A spec that stops the backend is mutating a resource every other spec shares, and the default is to run them at the same time (added by Task 1.13.2, 2026-09-04).** Playwright's default worker count is half the CPU count — **4** on the development machine — and Task 1.13.2 left it at the default because one spec cannot race itself. The moment there are several, a spec that kills the backend to produce `unreachable` will do it underneath a sibling asserting `healthy`, and the sibling fails for a reason that is not its own. `pnpm e2e`'s readiness gate does **not** protect against this: it runs once, before the suite, and says nothing about what the suite then does to the pair. Decide it explicitly — a serial project for the mutating specs, `test.describe.serial`, or `workers: 1` — and write the reason beside it, because it is the second decision after the target that every later spec inherits silently
- **Write the mutating specs so they do not assume they own the servers.** Locally the pair is started by hand in another terminal; in CI it is started by whatever Task 1.13.4 builds. A spec that stops the backend has to restore it through a mechanism that works in both, and Story 1.8's measurement is the trap: **freeing the port is not enough to recover a `node --watch` loop** — it waits for a file change, not for the port. If restoring is not reliably possible, the honest shape is a spec that produces the state without killing the process at all
- **The rest of the interface remaining usable while the backend is down** — navigate every route, and confirm nothing collapses to a global error screen. This is PRODUCT_SPEC.md §36's core principle and it is the criterion most likely to stop being true without anything failing
- **Decide whether a render failure is worth a journey, knowing this application contains no way to produce one.** Task 1.7.6 exercised every boundary placement with a temporary throwing probe and removed it; the process suite faced the same problem and answered it by injecting a crash through a wrapper rather than shipping a route. If the answer here is a test-only injection, keep it out of the shipping bundle and say how
- **Four things about selecting in this application, all measured by Task 1.13.2's one journey (2026-09-04).** `BACKEND_STATUSES` **imports and resolves from a spec**, which is the payoff of the specs being a workspace package — assert on the vocabulary rather than writing the words out. The words render **lowercase** in the DOM and are uppercased by CSS, so the accessible text is `healthy`, not `HEALTHY`. The status strip's three cells are plain `<div>`s and **not landmarks**, so there is no role to scope a status word by — the label's own parent stands in for one, and a status word matched unscoped matches the wrong indicator half the time, because a correct first run shows a `DISCONNECTED` market feed beside a `HEALTHY` backend service. And `checking` is what every page load renders until the first poll settles: **wait past it rather than reading it as a failure**, and never add it to `BackendStatus`, because it is a fact about this client's own startup rather than about the server
- **Write the must-not list into the suite itself, not just into this file.** Not colour — no global stylesheet reaches the component tests and `getTokens()` throws there, but a **browser has the real stylesheet**, so this is the first level where a colour assertion would actually work, and it must still not be written: greyscale separates this palette's red and green by **1.05:1**, so a colour assertion tests the thing that carries no meaning. Not a single element's text where a component splits it across a visually-hidden `<span>` and a sibling text node — and **Task 1.13.2 met the same rule from the other direction, which is the half nobody expects**: scoping the backend indicator with `toContainText(/\b(healthy|…)\b/)` fails, because the region's text is `Backend servicehealthy` with **no separator** between the label and the word, so there is no word boundary to anchor to. The concatenation a screen reader is handed is not the string the elements read as. Match an element whose whole text is the word. Not a `useId()` value or a DOM snapshot of a route, because both move when anything above them moves. **And not latency** — CI's runner-to-runner spread on identical work is 13.6 s, and the process suite asserts no timing for that reason
- **Decide the axe question and record it.** A browser makes an automated accessibility pass cheap, and this repository has run one by hand four times. It is also true that axe returns `color-contrast` **inconclusive** on exactly the non-text elements this product encodes with, that Story 1.9 rejected an axe pass as coverage, and that Epic 15 owns the accessibility review. A diagnostic that reports is a different thing from a gate that fails; if it goes in, say which it is
- **Say what a green run does not certify**, in the same shape ADR 0010 says it for the tick. It does not certify the states the suite cannot produce, anything about a browser it does not run, or anything about the deployed environment — that is Task 1.13.5's

## Done when

- The journeys above are written, passing, and each has been seen to fail for its own reason — noting that the deep-link and missing-asset criteria are **not** among them, having moved to Task 1.13.5
- How specs that mutate the shared pair are kept from running underneath specs that do not is a written decision, not a default
- No journey carries a `visibilityState` workaround, and any wait on the poll is derived from `HEALTH_POLL_INTERVAL_MS` and `API_TIMEOUT_MS` rather than from a number that happens to pass
- The cross-origin failure has been produced deliberately and this suite caught it, with the server-side evidence recorded beside it to show what it looked like from the other side
- The must-not-assert list is stated where the next person writing a spec will meet it
- The axe decision is recorded with its reason
- `pnpm verify` passes and `pnpm test` is still the fast suite

## Approach note

The temptation here is coverage, and it is the wrong instinct twice over. There is very little application to cover — one indicator, five routes and four empty regions — and the levels below already cover what they can reach. Every journey in this task is here because **no cheaper level can see it**: a host's fallback behaviour, two origins, a sequence over time, and a failure that every server-side instrument reports as success.
