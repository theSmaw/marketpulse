## Story 1.13 is an addition to this epic, made on 2026-09-03

**This epic's scope said "Unit/integration test foundations", deliberately narrow, and Story 1.9 delivered exactly that** — Vitest, jsdom, 118 fast tests, ten process tests, and `@storybook/addon-vitest` measured and rejected. Nothing in this epic ever scoped a test that drives a real browser, and neither Playwright nor Cypress appears anywhere in the planning tree. That was noticed as a gap rather than found as a defect, and it is worth recording what the gap actually is, because the obvious reading of it is wrong twice.

**It is not a roadmap omission this epic should fix.** `PRODUCT_SPEC.md` §41 puts "E2E tests" in **Phase 6 — Portfolio polish**, whose home here is Epic 15 — and Epic 15's scope carries "Testing strategy documentation" rather than the tests themselves. So the **suite** has no owner anywhere in the roadmap. That divergence is recorded and deliberately **not** resolved: where a suite lives is a question about a product that does not exist yet, and answering it now would be scoping tests for fourteen epics of features nobody has written.

**What justifies a story here is narrower and is a measurement.** Task 1.11.7 declined a browser-driven post-deploy check and named the gap precisely: only a real browser catches a wrong `CORS_ORIGIN` or a missing `VITE_API_BASE_URL`, and `curl` is **structurally incapable** of it — with the same `Origin` it gets a 200 with a full body while the browser reports `TypeError: Failed to fetch` and the server logs `statusCode: 200`. **Scoped 2026-09-04 (Task 1.13.5): _structurally_ is too strong.** The status, the body and the log genuinely cannot catch it, but `access-control-allow-origin` is a readable copy of `CORS_ORIGIN`, so an instrument **told the frontend's origin** can compare the two — which is what no server-side instrument has, and which is a proxy for the browser's verdict rather than the verdict, saying nothing about the missing-`VITE_API_BASE_URL` half where the backend is never asked. The deployed suite makes the comparison anyway, because two instruments disagreeing is diagnostic. Every instrument in this repository reports the system as healthy. That decline was correct at the time for a stated reason — nothing could yet produce the failure — and it named **Story 1.12** as the trigger. Story 1.12 produces it. Leaving the check unbuilt after that is a different decision from the one Task 1.11.7 took, and it is one nobody had taken.

**So Story 1.13 depends on 1.12 rather than preceding it**, which is the ordering question worth stating rather than assuming. Building the harness first would mean choosing a tool, a home and a CI position against a shell with no behaviour — scaffolding ahead of the iteration that needs it, and taking the tool decision without its main use case in front of it. Story 1.12 ships the first behaviour in this application that is a sequence over time rather than a rendered output, and the first failure mode no existing level can see.

**What it is scoped to is a foundation, not a suite**: one tool, one home for specs, a handful of journeys that no cheaper level can assert, a CI position, and the post-deploy check. It is six tasks. The scope to resist is coverage — there is very little application to cover, and Epic 8 is the checkpoint where there are user journeys worth asserting on in quantity, inheriting a harness whose decisions are already recorded.

**No other story was changed by this addition beyond its cross-references.** Story 1.12's split had claimed to close the epic; its Tasks section, Task 1.12.7 and Task 1.12.8 were amended, and 1.12.7 now hands the smoke check to 1.13 by name rather than deciding it. Nothing was deleted or re-ordered, and this epic's four exit criteria are unchanged — 1.12 still meets the fourth, and 1.13 is what checks all four against the tree.

## Conventions Story 1.1 set for the rest of this epic

Story 1.1 is complete, and the conventions it established bind every story after it. They are recorded in full in `docs/adr/0001-repository-structure-and-typescript-toolchain.md`, and **restated verbatim in every story from 1.2 to 1.12** under a `Conventions from Story 1.1` heading, followed there by a `What that means for this story` section spelling out the consequences for that story in particular. Each story is meant to be readable on its own without this file; the duplication is deliberate, and the wording is identical so that drift is visible in a diff. Change one and change all eleven.

The four, summarised:

- **`pnpm verify` is the acceptance command** — `build && lint && format:check && stories && env:check && test && test:process`. Every story here should pass it from the root, and Story 1.10 runs it unchanged rather than re-listing the tools. It was a four-step chain until Task 1.4.5 added `stories`, which fails if a component has no stories file — `build` grew a second bundler in the same task — and a six-step one since Task 1.6.6 added `env:check`, which fails when `.env.example` and `CONFIG_VARIABLES` have drifted apart. **Story 1.6 changed one step and so changed all eleven restatements; that sweep happened on 2026-09-01 rather than inside the story, which is the drift this convention exists to make visible** — and it is a **seven**-step chain since Task 1.10.5 added `test:process`, the backend's ten process-level tests against a spawned `dist/index.js`. **That sweep happened later still, on 2026-09-03, in Story 1.10's own review pass rather than in the task that changed the step** — the second time in three stories that the step moved and the restatements did not, and the reason this convention is worth the duplication
- **Six verbs, identical in every package** — `dev`, `build`, `test`, `lint`, `typecheck`, `clean`. A new package gets all six; a story that changes what a verb means in one package should change it everywhere or explain why not. Only `test` and `dev` fan out with `pnpm -r`; the rest run their tool once
- **Shared tooling lives at the workspace root; packages declare only what they actually import.** A test runner, a bundler or a formatter plugin goes at the root. A library the code imports — React, Fastify, a schema library, `@types/node` — goes in the package that imports it
- **The module setup is ESM-only and single-file-safe** — `"type": "module"`, `module: nodenext`, `isolatedModules`, `verbatimModuleSyntax`, and relative imports carrying `.js` extensions from `.ts` files. This constrains framework and runner choices in Stories 1.2, 1.3 and 1.9, and each of those now says so

One correction to the second bullet, found in Task 1.2.6 and not worth re-editing eleven verbatim blocks over: the six verbs are right, but **`pnpm --filter <pkg> clean` does not work** — `clean` is also a built-in pnpm 11 command, so the filtered form reaches the built-in and exits 1 with `Unknown option: 'recursive'`. `pnpm --filter <pkg> run clean` works, and root `pnpm clean` is unaffected because the root has a `clean` script to shadow it. `CLAUDE.md` and `README.md` both carry the detail.

## What Story 1.3 established for the rest of this epic

Story 1.3 is complete and recorded in `docs/adr/0003-frontend-build-tooling-and-browser-baseline.md`. Five things bind later stories, and the first two are traps rather than decisions:

- **Both local servers have an SPA fallback and a real static host does not.** `vite` and `vite preview` answer _any_ unmatched path **that a browser asks for** with `index.html` and a 200 — a missing asset included, which reaches the browser as a MIME-type error rather than a 404. (**Scoped 2026-09-04 (Task 1.12.6): `preview`'s fallback keys on the `Accept` header**, so `Accept: application/json` — which is what an API client sends — gets a 404 instead. Three hosts, three behaviours: `python3 -m http.server` 404s both, `vite preview` splits on `Accept`, and Azure Static Web Apps splits on **path**. Never write "the SPA fallback" without saying which host.) Story 1.5's "deep-linking works on page reload" therefore passes locally before anyone configures anything, and Story 1.11 inherits the question of whether the deployed host does the same
- **The `.js` import-extension convention has exactly one enforcer in the frontend, and it is `tsc`.** Drop an extension and `tsc -b` fails with TS2835 while `vite build` emits a byte-identical bundle. `pnpm verify` catches it; the dev server and the bundler do not. This matters most in Story 1.5, which adds many small files at once
- **The frontend's deployable unit is `dist/` alone and its configuration is build-time.** Two files, no `package.json`, no `node_modules` — the opposite shape to the backend, where the package directory is the unit. Asset paths are absolute (`base` defaults to `/`) and any environment variable is inlined at bundle time, so **a subpath deployment and a per-environment configuration are both rebuilds, not hosting settings**. Stories 1.6 and 1.11 own the two halves of that
- **`pnpm verify` now runs a bundler, which grew both CI's runtime and its failure surface.** Root `build` is `tsc -b && pnpm --filter @marketpulse/frontend exec vite build` and hardcodes that one package name — a second frontend package would be silently missed. Story 1.10 carries the detail, including Rolldown being this repository's first platform-specific native binding
