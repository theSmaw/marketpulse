# Task 1.3.5 — Verify the story end to end and document

**Status:** Not started
**Story:** [1.3 Frontend Application Shell](STORY.md)
**Depends on:** Task 1.3.4

## Objective

Execute all five acceptance criteria together, from a clean build, rather than inheriting each task's own claim about itself. Then write down what was learned, in the three places that carry it: the ADR, `README.md`, and `CLAUDE.md`. This is the task Story 1.1 and Story 1.2 both ended with, for the reason both found useful — the tasks that made a thing work are not the ones best placed to say whether it still works together.

## Work

### Verify

Run all five acceptance criteria in one sitting, from `pnpm clean` and a fresh install, recording the actual output rather than "passed":

- Development server runs with hot module replacement — **and this one cannot be checked the obvious way.** Task 1.3.3 removed the stateful probe it used, so the tree now holds no component state at all; editing the heading and watching it change passes identically whether Fast Refresh works or the page fully reloaded. Re-create the four-line counter from Task 1.3.3's Outcome, click it to a non-zero value, edit a _different_ line, and check the number survived. Delete it again afterwards
- The application renders a placeholder shell in the browser
- The production build emits static assets — and they serve and render. Task 1.3.4 met this; the thing to repeat rather than assume is **where** it was served from. `vite preview` alone is not sufficient evidence: its SPA fallback answers _any_ unmatched path with `index.html` and a 200, `/assets/nope.js` included, so a missing asset arrives as a browser MIME-type error rather than a 404 naming the file. Copy `dist/` outside the workspace and serve it with something dumb (`python3 -m http.server`) as well
- `pnpm verify` passes from the repository root
- The browser target is documented and `target`/`lib` match it

Then the checks that only make sense once everything is in place:

- Root `pnpm dev` with all three packages, including Ctrl-C leaving nothing behind
- A **clean clone** into an empty directory, following `README.md`'s written words rather than the working tree — the method Task 1.1.8 established. This is not Story 1.8's criterion (which requires a running _pair_ reached from the README) but it is the frontend half of it, and finding out here is cheaper
- The `.js`-extension import resolving through both `tsc` and the bundler, since that is the one convention this story stresses in a way the backend never did

### Document

- **Write the ADR.** It records the build tool choice, what `build` means once a bundler exists, the output-directory decision, and the browser baseline — each with its rejected alternative, which is the part that makes an ADR worth writing. Number it the **next free number in `docs/adr/`**, which is `0003`, and follow the convention in `docs/adr/README.md`: numbered in the order written, never renumbered
- Two of those four have answers that are not the obvious ones and need their reasoning preserved, because a future reader will otherwise "fix" them. **The output-directory decision was made by removing a producer** — `noEmit` on the frontend's TypeScript half — which is only safe because it is a composite project referenced by nothing, and would be actively wrong for `packages/shared`. And **`build` at the root is not the same string as `build` in the package**: the root's is `tsc -b && pnpm --filter @marketpulse/frontend exec vite build`, because a plain root `tsc -b` would have let `pnpm verify` pass without ever running the bundler. The rejected alternative there was a `pnpm -r run build` fan-out, which the root scripts deliberately avoid
- **Fix the stale reference in Story 1.4.** Its final acceptance criterion says the styling decision will be captured "as ADR 0002", which was written before Story 1.2 took that number for the backend framework. Following it as written would force exactly the renumbering the ADR convention forbids. Correct it to name the next free number at the time, not a fixed one
- **The install-script prediction has now failed three times** — Tasks 1.3.1, 1.3.2 and 1.3.3 each swept the tree and found zero `preinstall`/`install`/`postinstall`. Write it as a resolved wrong prediction rather than a standing expectation, and say plainly that `allowBuilds` is empty and untested
- **Update `README.md`'s "What exists today" section.** It names itself as the first thing to change when the repository reaches a running application, and this story is what makes that true. The command table gains whatever this story added — including `preview`, which Task 1.3.4 **did** add, with the same "an extra, not a seventh verb" status `apps/backend`'s `start` has, and the third port that comes with it (4173) — and the install-script policy section — which predicts esbuild in Story 1.3 — gets replaced with what actually happened: **it did not fire.** Vite 8 uses Rolldown, shipped as prebuilt per-platform binaries, and a sweep of the whole tree in Task 1.3.1 found zero install scripts. `allowBuilds` is still empty and still untested, which is worth saying plainly rather than leaving the prediction standing as though it had been confirmed
- **Update `CLAUDE.md`** — the current-state paragraph, the layout tree, the commands section, and every claim this story falsified. Specifically: `apps/frontend` is no longer a skeleton; `dev` is no longer a placeholder anywhere; **the four-compiler-option claim is now six** (`noEmit` from Task 1.3.1, `jsx: "react-jsx"` from Task 1.3.2, both in `apps/frontend`), and the file's assertion that each of the four is load-bearing needs the same treatment for the new two; **`clean` is no longer `tsc -b --clean` in either the root or `apps/frontend`**, and the paragraph explaining the `tsc -b --clean` orphaning trap needs a note that the frontend's `rm -rf` half is content-blind and immune to it — plus the finding that made the whole worry moot, that **`build.emptyOutDir` defaults to true** so hashed assets never accumulate in the first place, which is a default rather than a guarantee and worth stating as one; **root `build` is no longer a bare `tsc -b`**, which contradicts the "most root scripts do not fan out" paragraph unless that paragraph is amended to describe what it now does; and the "esbuild will probably be the first install script" prediction resolves as wrong
- Add the layout entries this story created: `apps/frontend/index.html` (Vite's real entry, at the package root and inside no tsconfig), `apps/frontend/vite.config.ts`, `apps/frontend/src/main.tsx` (the mount) and `apps/frontend/src/App.tsx` (the shell). `vite.config.ts` is also the second file to need the trailing `disableTypeChecked` block in `eslint.config.mjs`, and the first that is not `eslint.config.mjs` itself — the note there about that block having to stay last is now protecting two files
- **`eslint.config.mjs` has grown a fourth kind of block**, and its ordering constraint is worth restating once rather than rediscovering. The order is now: global ignores → `js.configs.recommended` → type-aware TypeScript → per-package globals → React (`apps/frontend/src/**`) → tooling files (`disableTypeChecked`, last). The React block sits between the globals blocks and the trailing one deliberately: it is scoped to `src` so `vite.config.ts` is not asked React questions, which means the trailing block's job is unchanged
- **Document two things Task 1.3.2 added that are not in the list above.** `--max-warnings 0` is now on all four `lint` scripts, which is a change to what a workspace verb means and belongs wherever the six-verb convention is stated — with its reason, that `eslint-plugin-react-hooks` brought the workspace's first `warn`-severity rules and `eslint .` alone does not fail on them. `eslint-plugin-react-hooks` itself is the first ESLint plugin here beyond `typescript-eslint`, and the `configs.flat` trap (the top-level `recommended-latest` is eslintrc-shaped and ESLint 10 exits 2 on it) belongs next to it. (`StrictMode` was the third item here while it was still an open deferral; Task 1.3.3 adopted it and it is covered below.)
- **Record the development-loop asymmetries between the apps**, since a person working in both will otherwise be surprised by each in turn. One of the two originally listed here **is no longer true**: Task 1.3.3 adopted `strictPort: true`, so the frontend now exits 1 with `Error: Port 5173 is already in use` like the backend, rather than quietly binding 5174 — do not document the old behaviour. What remains is that the frontend's dev server **does not typecheck**, and it is worth stating as the pair of opposite failure modes Task 1.3.3 measured: a **type** error is applied as an ordinary HMR update with no overlay, no console error and state preserved, caught only by the editor or `pnpm verify`; a **syntax** error fails the oxc transform loudly, logs source context, and leaves the page on its last good render
- **Two measurements from Task 1.3.3 belong in the documented baselines**, next to the backend's ~1.1s restart: HMR edit-to-visible-update is **~100–140 ms warm**, with the first edit after a server start at ~850 ms and not the number to regress against. Also record _how_ it was verified, because the obvious method is wrong twice over — `clearScreen` cannot be checked through a redirected log (Vite only clears on a TTY, so both settings look identical), and the clear sequence is `ESC[1;1H ESC[0J` rather than the `ESC[2J` a grep reaches for first, which reports zero in both configurations and reads as a pass
- **`StrictMode` is adopted**, in `main.tsx` — so the "its absence looks like an oversight" problem 1.3.2 flagged is gone, and what needs recording is the ordering rather than the fact: the fast-refresh measurement was taken on the plain tree first and retaken with it on (unchanged), because adopting it first makes a double-render and a lost-state bug look alike
- **Amend the downstream stories this story changes**, in the habit Task 1.2.6 established — Story 1.2's amendments to Stories 1.6 through 1.12 are the model. At minimum: Story 1.8 (its `pnpm dev` criterion is now fully in scope rather than half-met, and the frontend port question is settled — `strictPort: true`, so **its "conflicts produce a clear message" criterion is now met on both halves**, where it was previously recorded as half-met on the backend), Story 1.9 (a component test needs a DOM environment, which is a different runner decision from the backend's `app.inject()`), Story 1.11 (two artefacts of different shapes, now **measured** in Task 1.3.4 rather than expected: the frontend's `dist/` alone renders from a plain static server with no `package.json` and no `node_modules`, while the backend's `dist/` alone does not run at all. Carry two specifics there that neither half implies — the emitted asset path is absolute, so a subpath deployment is a `base` change and a **rebuild** rather than a hosting setting; and the host's SPA-fallback behaviour has to be stated rather than discovered, because `vite preview` has it and a plain static server does not), and Story 1.12 (the frontend can now call something; CORS and the shared `HealthResponse` land on this shell)
- **Record the size-budget deferral, and note where it nearly went.** Task 1.3.4 declined to set a bundle-size budget — 190.80 kB is React and almost nothing else, so a budget today is a budget on a dependency — and deferred it to **Epic 14 (Performance & Scale Validation)**. It originally said "Story 1.14", which does not exist: Epic 1 has twelve stories. A deferral aimed at a non-existent destination is one nobody ever picks up, which is exactly what dating a deliberate gap is supposed to prevent. Worth one pass over the other forward references this story wrote while the habit is fresh
- **The workspace now has three ports and only two of them are decisions.** Backend 3000 and dev server 5173 were chosen; preview 4173 is Vite's default written down explicitly, because `preview` inherits `server.strictPort` but **not** `server.port` — measured both ways — so a config naming only 5173 would read as covering both servers while leaving one at a default. `preview.strictPort` is deliberately absent for the opposite reason: it _is_ inherited, and a second copy is one more place for the two to disagree on an upgrade
- **Story 1.10 gains a specific new note.** The frontend toolchain is the first dependency in this repository with a **platform-specific native binding** — Rolldown resolves `@rolldown/binding-darwin-arm64` locally and something else on Linux CI. pnpm records every platform's optional dependency in the lockfile, so this should just work, but it is the first time "works on my machine" has a real mechanism behind it in this repo and CI is where it would surface. Story 1.10 also still carries the note that `pnpm verify` covers no shell script; `apps/frontend`'s `clean` now contains an `rm -rf`, which is a second unchecked shell fragment and belongs in the same dated paragraph
- **Name what the verification could not prove**, the way Story 1.2's own section does. Candidates: nothing here proves cross-origin access to the backend, nothing tests any of this (Story 1.9), nothing has been served by a **real** static host — Task 1.3.4 used `python3 -m http.server`, which proves the artefact is self-contained and proves nothing about caching, compression, redirects or SPA fallback on whatever Story 1.11 picks — and the browser baseline is a decision rather than a measurement — no browser matrix was exercised. Add one from Task 1.3.2: **the React Compiler rule set has never met real code.** Fifteen of those 17 rules are at `error` and the tree contains one stateless component, so they have been adopted rather than exercised. The first time they say something interesting will be in Epic 2, and it may not be welcome then — that is the risk that came with taking `recommended` whole, and it should be written down next to the decision rather than discovered later

## Notes

Two documentation habits from earlier stories are worth keeping rather than rediscovering. Measure before writing — Task 1.2.6 found that a guess written down confidently (the `tsc -b --clean` mechanism) survived two tasks before being checked and turned out to be backwards. And date the deliberate gaps: a known choice with a date is a decision, while the same gap unwritten is an oversight, and the two are indistinguishable six weeks later.
