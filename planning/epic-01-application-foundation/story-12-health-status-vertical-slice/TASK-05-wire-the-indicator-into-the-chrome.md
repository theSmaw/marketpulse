# Task 1.12.5 — Wire the indicator into the chrome, on every route, without making the chrome fragile

**Status:** Not started
**Story:** [1.12 Health & Status Vertical Slice](STORY.md)
**Depends on:** Tasks 1.12.3 and 1.12.4

## Objective

Connect the poll to the indicator and put it in `AppHeader`, so backend status is visible on all five routes and the rest of the interface stays usable when the backend is not.

## Work

- ~~Decide **where the hook is called** and record it.~~ **Task 1.12.3 already called it, and this task inherits the call site rather than choosing one (2026-09-04).** `App.tsx` calls `useBackendHealth()` today and **discards the result** — deliberately, for exactly one task, because deleting `health-probe.ts` without starting the loop would have left a merge window in which the deployed frontend called the deployed backend nowhere at all. What this task does is give that value a consumer. The reason it is in `App` and not in `AppHeader` is written beside the call and is worth not undoing: `AppHeader` sits inside its **own** `ErrorBoundary`, so a header that throws would take the health check down with it at the moment it became most interesting. **Pass the value down; do not move the call.** A prop from `App` is still the smallest thing that works and needs no context — `AppHeader` is rendered once outside `<Routes>` — and a context provider is still the alternative whose cost is `apps/frontend/src/test-render.tsx` becoming the place every test gets it from, which is the file Story 1.9 named as the third and last description of the application's context. Take the cheap option unless a second consumer already exists
- **One measured input to that decision that Task 1.12.3 produced: every poll re-renders the hook's caller, even when nothing changed.** Measured rather than assumed — 4 polls produced 5 renders, one initial and one per poll — because a successful poll writes a fresh `lastSuccessAt`, so the state object is new and React cannot bail out. `App` is the router's host, so **as it stands every 30 seconds re-renders `AppHeader`, `<Routes>`, the current route, all four `Region`s and the render check's 36-row table.** At this size that is nothing and it is not a performance target; it is the shape Epic 3 inherits at a much higher rate, and it is the one concrete argument for a context provider sited lower — a provider around only the header would confine the re-render to the thing that displays the state. Decide it on that rather than on taste, and note the cheap middle option: leave the call where it is and memoise the subtree, which trades one decision for a second one nothing checks
- **The indicator goes in the header's feed region or the reserved market clock region — a decision, not a search.** `AppHeader` carries four slots: the product name, a market feed region, a reserved market clock region and the navigation. The clock is reserved for a clock; putting a status indicator in it spends a slot Epic 3 has a use for
- **`AppHeader`'s `AllPermutations` grid is already an exception, and this task multiplies it.** Six headers on one page is six `banner` landmarks, so `landmark-no-duplicate-banner` and `landmark-unique` are disabled **on that one story and nowhere else**. Adding a status prop multiplies the grid; keep the disable scoped to the grid story rather than widening it to the component, because a permanent badge trains the next reader to ignore the badge. Note the general rule Task 1.7.6 corrected: `landmark-unique` keys on role **and accessible name together**, so it fires on landmarks that are indistinguishable rather than on landmarks that repeat — the conflict only exists for a landmark with no name
- **The chrome is eager and outside the router, and that is what makes this indicator trustworthy.** A failure inside `<Routes>` blanks `<main>` — four named region landmarks and the 70vh grid — under a header that still renders, measured in Task 1.5.5 against a host delaying chunks. So the status stays visible when the page body has failed, which is exactly the §36 shape. The cost is stated rather than discovered: `AppHeader` has its own boundary since Task 1.7.6, and that fallback replaces the `<header>`, so a broken chrome takes the banner landmark, the navigation **and this indicator** with it
- **A hidden tab does not poll, so check the indicator against a tab you have switched away from and back to.** Task 1.12.3 stops the loop on `visibilitychange` to hidden and polls immediately on return, which means the state a returning user sees is written within a round trip of them looking at it rather than up to a whole interval stale. What is worth confirming on screen is the case that reads as a fault: switching away for several minutes and back should produce **one** request and a state that either does not change or changes once, not a burst. Note an automated tab reports `hidden` and cannot be foregrounded, which is why this one is a manual check
- **Check the not-found route specifically.** There are five routes and the indicator is on all of them; an unreachable-backend state has to read correctly on a page that is itself an error state, and `NotFound` is a real route rather than a fallback. Worth looking at rather than assuming
- **"The rest of the interface remains usable" is a criterion, so exercise it rather than reasoning about it.** With the backend down: navigate between all four routes, use the recovery affordance in a region, and confirm nothing collapses to a global error screen. An unreachable backend must not reach `ErrorBoundary` at all — and since Task 1.12.3 that is **structural rather than hopeful**: `getHealth()` never throws in any branch, so there is no `try`/`catch` anywhere in the loop and there is no rejection for a boundary to catch. The half worth exercising is therefore the half this task adds — a **rendering** of a failure state, which can throw like any other render
- Component tests through the render helper. `App.test.tsx` is the one deliberate exception to it: it drives the real `BrowserRouter` through `window.history` because `App` contains its own router, and re-declaring the routes inside a `MemoryRouter` would test a copy of the route table rather than the one that ships

## Done when

- The indicator renders in `AppHeader` on all five routes, driven by the real poll, and `App` no longer discards the hook's result
- The call site decision is re-recorded rather than left implicit, including whether the per-poll re-render of the whole tree was accepted or confined
- With the backend stopped, every route still navigates and renders, and no fallback appears anywhere
- The a11y disable on `AppHeader`'s grid story is still scoped to that story, and the panel reports no new violation on any single-state story
- `pnpm verify` passes, and `pnpm dev` plus `pnpm ready` still describe a healthy pair

## Approach note

Two criteria are met here and only one of them is visible. "Displays it in the application chrome" is the obvious half. The other is that a backend the user cannot reach leaves them with an application they can still use — which is met by the shape of the code (a value in state, not an exception) rather than by anything on screen, and which is therefore the half that will silently stop being true.
