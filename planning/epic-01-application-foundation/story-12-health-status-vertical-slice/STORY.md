# Story 1.12 — Health & Status Vertical Slice

**Status:** In progress — Tasks 1.12.1, 1.12.2 and 1.12.3 complete (2026-09-03), Task 1.12.4 complete (2026-09-04)
**Epic:** [Epic 1 — Application Foundation](../EPIC.md)
**Depends on:** Stories 1.5, 1.7, 1.8
**Epic scope covered:** epic exit criterion — backend health/status viewable from the frontend

## Description

The story that closes the epic: prove the whole foundation works end to end by having the frontend display real backend status. Small in scope, but it exercises configuration, routing, layout, the API contract, error handling and deployment together.

It also establishes the connection-state pattern that Epic 3 reuses for the live market feed.

## Conventions from Story 1.1

Story 1.1 is complete, and these four bind this story. They are stated in every Epic 1 story so each one can be read on its own; the full reasoning is in `docs/adr/0001-repository-structure-and-typescript-toolchain.md`.

- **`pnpm verify` is the acceptance command** — `build && lint && format:check && stories && env:check && test && test:process`, chained with `&&` so the first failure is the exit code. It took its fifth step in Task 1.4.5: `stories` fails if a component has no stories file, and `build` now also produces the Storybook bundle. It took its sixth in Task 1.6.6: `env:check` fails if `.env.example` and `CONFIG_VARIABLES` have drifted apart, which is what makes the documented variable set a checked claim rather than prose. It took its **seventh** in Task 1.10.5: `test:process` runs the backend's ten process-level tests against a spawned `dist/index.js`, which is why the chain building before it runs is load-bearing rather than incidental. This story passes it from the repository root. Prettier owns Markdown as well as code, so an unformatted planning document fails it too
- **Six verbs, identical in every package** — `dev`, `build`, `test`, `lint`, `typecheck`, `clean`. Only `test` and `dev` fan out with `pnpm -r`; the rest run their tool once from the root, because the reference graph and ESLint's project service already cover the workspace in one pass. Changing what a verb means in one package means changing it everywhere, or saying why not
- **Shared tooling lives at the workspace root; packages declare only what they actually import.** ESLint, Prettier and TypeScript are root-only devDependencies, and pnpm puts the root's `node_modules/.bin` on every package script's PATH. A library the code imports belongs in the package that imports it — `@types/node` in `apps/backend` is the counter-example that keeps the rule from being over-applied
- **The module setup is ESM-only and single-file-safe** — `"type": "module"`, `module: nodenext`, `isolatedModules`, `verbatimModuleSyntax`, and relative imports carrying `.js` extensions from `.ts` files (TS2835 without one). `packages/shared` is consumed as **built output**, so it must be built before any consumer can be typechecked; `tsc -b` orders that itself, which is why `typecheck` and `build` are the same command

## What that means for this story

- The health response type is exactly what `packages/shared` exists for — one definition, both sides compiling against it. This story is the first real payoff of creating that package in Story 1.1 rather than deferring it, and the first place the build-before-typecheck ordering has a genuine consequence: change the health shape and both apps must be rebuilt, which `tsc -b` handles and `--noEmit` silently does not
- **The type this story promotes now exists, with names.** `HealthResponse` and `HealthStatus`, ~~exported from `apps/backend/src/routes/health.ts`~~ — **promoted into `packages/shared` by Task 1.12.1 (2026-09-03), which is what this bullet was anticipating.** They are imported back by `apps/backend/src/routes/health.ts`, and that import is the first thing to make this repository's oldest declared-but-unused dependency honest. The schema and its `satisfies` guard stayed in the backend, because `JsonSchemaProperty` deliberately is not shared. **The client-side vocabulary is settled too, and it is a second type rather than a widening of the first**: `BackendStatus` — `healthy` / `degraded` / `unreachable` — in `packages/shared/src/backend-status.ts`, with `BACKEND_DEGRADED_CAUSES` naming the two producible causes of the middle state (`not-ok-status`, `unreadable-body`) and `isHealthResponse()` shipping beside the interface so that definition is executable rather than prose. **Latency is deliberately not degradation**, so a request that times out is `unreachable` — nothing arrived — which makes the request deadline the boundary between those two states and ~~Task 1.12.2's to own~~ **owned and set by Task 1.12.2 at `API_TIMEOUT_MS = 5_000` in `apps/frontend/src/api-client.ts` (2026-09-03)**. That number carries an obligation nothing checks: it has to stay **strictly below Task 1.12.3's poll interval**, or a hung request is still outstanding when the next poll starts. Two details worth not guessing at: the uptime field is **`uptimeSeconds`**, not `uptime` — the unit travels in the name so it survives the wire — and `HealthStatus` is a one-member union `"ok"`. So the healthy / degraded / unreachable distinction in the criteria below is **entirely client-side today**: "unreachable" is the absence of a response, which no server can report about itself, and nothing widens the union until Epic 3 adds market-feed state. The union exists so that is an addition rather than a breaking change
- **`apps/backend` declares `@marketpulse/shared` without importing it**, and promoting the health type there is what makes that manifest entry honest again. Worth saying so the dependency is not deleted as dead first. It also makes a latent deployment problem live: because nothing imports the package today, the pnpm symlink into `packages/shared` is never followed at runtime, so a copied package directory runs despite it. The first import from this story starts exercising it — a reason to land Story 1.11's `pnpm deploy` mechanism before, or alongside, rather than after
- ~~**CORS has not been considered by any task in Story 1.2**, deliberately … so this story starts from zero on that~~ — **Story 1.8 built it, and this story starts from a working allowlist rather than from zero.** `apps/backend/src/cors.ts` registers `@fastify/cors` 11.3.0 inside `buildServer()`, exactly where this bullet predicted it would go and alongside Story 1.7's error handling, with one origin from `CORS_ORIGIN`. What is left here is not attaching it but being its **first shipping consumer** — see the Story 1.8 hand-off below, including why `curl` cannot re-check it
- ~~**`/health` has no response schema**~~ — **it has one since Task 1.7.3, and it does more than validate.** Fastify serialises through `fast-json-stringify`, which **strips every property the schema does not declare**, and the schema's properties are declared `satisfies Record<keyof HealthResponse, JsonSchemaProperty>`, so a field added to the interface and not to the schema is **TS1360** rather than a field that silently vanishes from the wire. Copy that idiom for whatever this story adds. Two gaps stay open and are dated 2026-09-01: a declared property whose JSON type disagrees with the TypeScript one is **coerced silently**, and a `required` property the handler omits is a runtime failure rather than a compile error
- The frontend must reach the backend over HTTP without importing anything server-side. ~~`apps/frontend`'s `types` array enforces that structurally — `process` does not typecheck there~~ … ~~the guard was re-measured after that change: `process` still fails `TS2591`~~ — **both of those are false and have been since Task 1.4.5, which is two stories before this bullet was last edited.** `.stories.tsx` files entered the program, so it reaches `@storybook/react-vite` and `vite`'s own node build, both of which carry a `/// <reference types="node" />` in a declaration file — and the `types` array cannot stop a triple-slash reference, only auto-discovery. Re-measured by Task 1.6.4, again by Task 1.10.7 and again in Story 1.11's review pass: a probe under `apps/frontend/src/` reading `process.env` and importing `node:path` **typechecks at exit 0**. **What actually stands there is a lint rule** — `no-restricted-globals` over `apps/frontend/src/**` for `process`, `Buffer`, `__dirname` and the rest, plus `no-restricted-imports` over `node:*` — and it is the only thing standing there, so `--max-warnings 0` is load-bearing rather than tidy. Resist any convenience that requires weakening it, and do not cite the `types` array as the reason it is safe. ~~**the frontend still has no environment-variable mechanism** — `import.meta.env` typechecks now that `vite/client` is in scope, but nothing uses it and there is no `.env` file~~ — **Task 1.11.5 built one**: see the Story 1.11 section below, which is the current statement. The browser's `fetch` is still available through the `dom` lib

### What Story 1.3 hands this story

- ~~**There is a shell to put the indicator in, and it is one component.**~~ **Five since Story 1.4 (2026-08-31), and one of them is close to what this story needs — see the Story 1.4 section below.** `apps/frontend/src/App.tsx` is still a single stateless function, and this story adds the application's **first state, first effect and first network call** — which means it is also the first code the React Compiler rule set will have anything to say about. Fifteen of `eslint-plugin-react-hooks`'s 17 rules are at `error`, `exhaustive-deps` is a `warn`, and `lint` runs with `--max-warnings 0`, so a polling effect with a sloppy dependency array fails `verify` rather than merely warning
- **The CORS origin is settled and stable.** Task 1.3.3 adopted `strictPort: true` precisely for this: a busy 5173 exits 1 rather than quietly binding 5174, so an allowlist pinned to `http://localhost:5173` cannot be defeated by a port shifting underneath it. That failure would have surfaced as a browser CORS error naming neither the port nor the cause
- **Watch the loopback family.** The frontend dev server binds `[::1]` and the backend binds `127.0.0.1`, so a browser talking to `http://localhost:3000` is fine while a script pinned to one family may not be. It also means the two origins differ by port only, which is still cross-origin
- **The frontend dev server does not typecheck.** A type error in this story's client code — the most likely place for one, since it compiles against `HealthResponse` from a package built by something else — is applied as an ordinary hot update with no overlay and no console error. `pnpm verify` or the editor is what catches it, and `packages/shared` must be rebuilt before either says anything true
- **Nothing about the deployed half is easier than it was.** The frontend artefact is `dist/` with an **absolute** asset path and no runtime configuration, so "point the frontend at the deployed backend" is a build-time input rather than a deploy-time one unless this story makes it otherwise
- Closing the epic means `pnpm verify` passes and the slice works in the **deployed** environment, not only locally. Verifying against a running local pair is the thing this story exists to go beyond

### What Story 1.4 hands this story

- **The status indicator has a component already, and it is not an error indicator.** `FeedIndicator` renders `live` / `stale` / `disconnected` as a marker **shape** plus a word, taking its `FeedStatus` from `packages/shared`, with stories for each state. It is close enough to this story's healthy / degraded / unreachable that the question is whether to reuse it, widen it or build a second one beside it — and that is a decision to take deliberately rather than by reflex, because **`FeedStatus` means the market feed and this story means the backend service**. Two vocabularies for one visual language is the trap; one vocabulary for two different things is the other. **Task 1.12.4 took it and the answer is a second one beside it (2026-09-04)** — see the section below
- **A degraded or unreachable backend is a product state, not a failure**, and the token layer already takes that position: `FeedIndicator` is achromatic apart from the amber on `stale`, and `--status-error` is reserved for something that actually failed — the same red as `--price-negative`, separated by presentation rather than hue. "Displaying data through 10:42:17" is the §36 shape this story is the first instance of, and it should not be red
- **Colour is never the only signal.** Under greyscale this palette's red and green are 1.05:1 apart. The status this story displays needs a word and a shape as well as a colour; that is what `FeedIndicator` is for, and it is the reason not to reach for a bare coloured dot
- **Whatever this story renders lives in `src/components/<Name>/` with a stylesheet and a stories file**, one story per state plus an `AllPermutations` grid — `pnpm stories` fails the build otherwise. A status indicator has a small, closed set of states, so this is the cheap case rather than the expensive one

A polling effect is exactly what they were adopted for, and ~~it is still this story or Story 1.7's recovery affordance that meets them first~~ — **Story 1.7 did not meet them either.** Its only state lives in `ErrorBoundary`, a class component the rules cannot see, so this story is now the first and only candidate

### What Story 1.5 hands this story

The chrome this story's first acceptance criterion names now exists, and it already contains a status indicator — hard-coded, deliberately, with a note saying which story decides what replaces it. That is the useful thing Story 1.5 hands over: the placement question is settled and the vocabulary question is sharpened.

- **"Displays it in the application chrome" has a literal place to go.** `components/AppHeader` renders once outside `<Routes>`, so it survives navigation and survives a route-level failure, and it carries four slots: the product name, a market feed region, a **reserved market clock region** and the navigation. A backend-status indicator goes beside the feed indicator in that first region or into the reserved one — a decision, not a search
- **`AppHeader` already renders a `FeedIndicator`, hard-coded to `disconnected`.** `App.tsx` passes `feedStatus="disconnected"` with a detail line reading "No market data until Epic 3", because rendering `live` for a feed that does not exist would be a green tick that means nothing. The comment there names this story as the one that decides whether the backend connection is that same fact or a second indicator beside it. Story 1.4 posed the vocabulary question — `FeedStatus` means the market feed and this story means the backend service — and Story 1.5 has now put the market-feed answer on screen, so the choice is visible rather than hypothetical: two indicators in one region, or one indicator whose meaning widens. **Decided by Task 1.12.4 (2026-09-04): two indicators**, which leaves Task 1.12.5 the smaller question of a third region in the strip rather than a repointed one — the clock region stays reserved for a clock
- **Whatever this story adds to the header changes a component that has stories, and one of them is already an exception.** `AppHeader`'s `AllPermutations` grid renders six headers on one page, which is six `banner` landmarks — `landmark-no-duplicate-banner` and `landmark-unique`, both disabled on that one story and nowhere else. Adding a status prop multiplies that grid; keep the disable scoped to the grid story rather than widening it to the component, because a permanent badge trains the next reader to ignore the badge
- **The chrome is eager and outside the router, and that is what makes this indicator trustworthy.** A failure inside `<Routes>` blanks `<main>` and leaves the header rendering — measured in Task 1.5.5 against a host delaying chunks. So a status indicator in the header reports on the backend even when the page body has failed, which is precisely the §36 shape this story is the first instance of. It also means the header has nothing above it to contain _its_ failure; **Story 1.7 answered that with a boundary around `AppHeader` itself** — without one, a throwing header leaves `#root` with zero children and an empty `<body>`. The cost is stated rather than discovered: its fallback replaces the `<header>`, so a broken chrome takes the banner landmark and the navigation with it, and the status indicator this story puts there goes with them
- **There are four routes now, and the indicator is on all of them.** Nothing about polling is per-route, but the not-found route renders under the same chrome — so an unreachable-backend state has to read correctly on a page that is itself an error state. Worth checking rather than assuming
- **A component test of anything in the chrome needs router context.** `AppHeader` uses `NavLink`, so it cannot render outside a router; the workshop solves this with a single `MemoryRouter` decorator in `.storybook/preview.tsx`. If this story writes the first component test (Story 1.9 permitting), that is a second place the application's context gets described — see Story 1.9, which owns keeping it from becoming a third

### What Story 1.6 hands this story

The frontend reads **no** configuration today, and this story brings the first variable it will genuinely need: the backend's URL. Everything about how that variable behaves is already decided and measured.

- **It must be `VITE_`-prefixed or it silently never arrives.** `envPrefix: ["VITE_"]` is stated in `vite.config.ts` as a decision, and the enforcement is at the reference site: a non-prefixed read compiles to `void 0`, not to a runtime lookup. `pnpm env:check` fails on a non-prefixed name in `apps/frontend/.env.example` for exactly this reason. `VITE_API_BASE_URL` is the shape the boundary was measured with
- **Adding it means adding it in two places, and the check enforces the second.** The variable itself, and a line in `apps/frontend/.env.example` — which is currently deliberately empty of variables. `env:check` only requires the prefix on the frontend side today; if this story wants the stronger backend-style guarantee (every documented name read by something, every default in step), that is a small extension to `scripts/check-env-example.mjs` rather than a new mechanism
- **It is inlined at build time, so one artefact cannot be promoted across environments.** A different backend URL is a **rebuild**, not a setting — the same shape as `base`. If this story's deployment story needs one artefact against two backends, that is the reversal trigger for ADR 0006 §6 and it is a decision, not a workaround
- **A credential must never follow it.** The browser talks to the MarketPulse backend and never to Alpaca or a model provider. A `VITE_` prefix is a boundary against accidents, not a permission: prefixing a credential makes it a string literal in a file every visitor downloads
- **CORS is pinned to 5173, and that is why the frontend's ports are literals.** Task 1.6.4 closed the "should the frontend's ports be configurable" question against making them so, partly on this story's allowlist: a silently moved port fails as a browser error naming neither the port nor the cause, which is why `strictPort` is on. If this story needs a second origin, it is `loadEnv()` in `vite.config.ts` rather than `process.env`
- **The backend's URL is the first thing that will want to differ between environments, and nothing branches on the environment today.** ADR 0006 §4 made that a decision rather than an omission. Read it before adding an `APP_ENV`; the answer is very likely one more value, not a name for the environment

### What Story 1.11 hands this story — read this before the sections above

**Task 1.11.5 took a bite out of this story, deliberately and with a stated line, because Story 1.11's "the deployed frontend communicates with the deployed backend" criterion could not be met without one.** Several of the sections below were written when nothing crossed the boundary and are now one step out of date; this section is the correction, and where it disagrees with them it wins.

**What was taken, and it is small:**

- **`apps/frontend/src/health-probe.ts`** — one `fetch` of `/health` at startup, reported to the console, called as `void probeBackendHealth()` from `main.tsx` **before the tree mounts and outside React entirely**. No state, no effect, no polling, no component, no retry, no timeout, no abort.
- **`VITE_API_BASE_URL`**, with `apps/frontend/src/api-base-url.ts` resolving it. Optional, defaulting to `http://localhost:3000`, documented in `apps/frontend/.env.example`.
- **`apps/frontend/src/vite-env.d.ts`**, which declares Vite's `strictImportMetaEnv` so a misspelled `VITE_` name is **TS2551** rather than an `any` evaluating to `undefined`.
- **15 tests** across `api-base-url.test.ts` and `health-probe.test.ts`, taking `apps/frontend` from 47 to 62.

**What was deliberately left, all of it still this story's:**

- **The API client.** What exists is one `fetch` with no shared transport and no error policy.
- **Promoting `HealthResponse` into `packages/shared`.** The probe types its body as `unknown` on purpose — that promotion is this story's stated payoff for creating the package in Story 1.1, and spending it in a deployment task would have been the wrong trade.
- **All state, every effect, the polling, and the status indicator** — including the vocabulary decision Story 1.4 posed and Story 1.5 sharpened. **Nothing rendered changed**, so `AppHeader` still hard-codes `feedStatus="disconnected"` and the two-indicators-or-one question is exactly as open as it was.
- **The `ApiError` seam and the `requestId` question.** The probe shows a _developer_ an id in a console and shows a _user_ nothing.
- **The React Compiler rules' first real test.** Keeping the probe out of React is precisely what preserved that for this story's polling effect. It is still true that fifteen error-level rules have never fired on shipped code.

**`main.tsx`'s `void probeBackendHealth();` and the module behind it are meant to be deleted by this story**, and both say so in their own comments. Deleting them is the expected shape, not a regression.

**Four things it measured that this story would otherwise rediscover:**

- **`exposedHeaders` is load-bearing and now proven.** The `x-request-id` the browser reads is the `reqId` in the backend's Log Analytics records for the same request — end to end, across an origin boundary. This is the payoff of Story 1.8 rejecting a Vite proxy, which would have exposed every header and hidden the requirement.
- **The cross-origin failure was made to happen and both halves were observed together.** The browser reports `TypeError: Failed to fetch`; `curl` with the same `Origin` gets a **200 with a full body**; the server logs `statusCode: 200`. Every piece of server-side evidence says the system is healthy. Do not debug this story's fetch failures from the server log.
- **The address is a build-time literal and the numbers now exist.** A build without the variable is 344,537 B and the deployed build is 344,609 B — **different artefacts**. One cannot be promoted across environments, and a build that forgets the variable does not fail: it ships a page dialling `http://localhost:3000`, which an HTTPS page blocks as mixed content and which reads as an unreachable backend.
- **The two local defaults are a matched pair.** `VITE_API_BASE_URL`'s `http://localhost:3000` and `CORS_ORIGIN`'s `http://localhost:5173` point at each other, verified on a tree with no `.env` file at all. Change one without the other and the local loop fails in a browser while every server log stays green.

**One thing this story now owes that nobody owed before:** a variable is declared in **two** places — `apps/frontend/.env.example` and `apps/frontend/src/vite-env.d.ts` — and **nothing checks that pair**. `scripts/check-env-example.mjs` reads the example and has no view of the declarations. This story brings the second variable, which is where a pair becomes a set; extending that script is the obvious move and is deliberately not made in advance.

**The section above was written by Task 1.11.5, mid-story, and three tasks landed after it.** Story 1.11 closed on 2026-09-03, and what follows is the completion rather than a correction — nothing above was falsified, but four things below change how this story's last two acceptance criteria can be met at all.

- **A merge to `main` now deploys both halves, and `VITE_API_BASE_URL` is a literal in `.github/workflows/deploy.yml`.** So the variable this story inherits is declared in **three** places, not two: `apps/frontend/.env.example`, `apps/frontend/src/vite-env.d.ts` and the deploy workflow — and the workflow's copy is the one that decides what users get. It is described in its own file as the most dangerous line in it **by being absent rather than wrong**, because a build that forgets the variable does not fail: it ships a page dialling `http://localhost:3000`, which an HTTPS page blocks as mixed content and which reads to a user as an unreachable backend. That is exactly the state this story's indicator is supposed to report, arriving from a cause that has nothing to do with the backend
- **`verify` and the deploy build two different artefacts, and the divergence is two files.** `verify` builds without the variable and now says so in its own job summary; the deploy builds with it and fingerprints that build. The JavaScript differs by 72 bytes and **`index.html` differs at an identical 1,101 B**, because it carries the hashed script filename — so a size comparison reports the document unchanged and it is not. Read the hash. The practical consequence for this story: **the bundle CI fingerprints is not the bundle you are looking at in a browser**, and a green tick says nothing about the address baked into the deployed one
- **The frontend's upload is not atomic, and the window opens at the exact second the deploy step reports success.** ~2 seconds holding **two** distinct broken states — the incoming document served before the incoming asset exists, then the outgoing asset withdrawn while the outgoing document is still served — reproduced across four deploys and accepted deliberately. So the criterion "behaviour is verified against the deployed environment" has a mechanical requirement: **poll, do not check once**, and treat a failure in the first few seconds after a deploy as the deploy rather than as this story's code. Anyone already on the page is unaffected, and `no-cache` on the document means their next navigation revalidates
- **You cannot produce this story's "unreachable" state by breaking the deployment, and that is measured rather than assumed.** Four failure classes were made to happen against the live environment in Task 1.11.7 and **no request ever returned a non-200 through any of them**, with `uptimeSeconds` never resetting — the failing revision holds `trafficWeight: 100` while the previous one at weight 0 keeps serving. A half-deployed merge was produced (backend at the merge commit, frontend a commit behind) and both halves answered. So to exercise the degraded and unreachable states against the deployed environment you need a cause the platform does not heal around — a wrong `CORS_ORIGIN`, a wrong `VITE_API_BASE_URL`, or a rolled-back backend — and **the first two are invisible to every piece of server-side evidence**: the browser reports `TypeError: Failed to fetch` while `curl` with the same `Origin` gets a 200 with a full body and the log records `statusCode: 200`
- **There is no preview environment and there deliberately never will be one on this plan.** `CORS_ORIGIN` holds exactly one string and a wildcard admitting previews would admit every Static Web App in the region, so a preview is a page that loads perfectly and cannot call the backend. This story's deployed verification therefore happens against the live environment, on a branch that has already merged. Plan the check accordingly — and know that **`workflow_dispatch` on `deploy.yml` is a re-deploy, not a rollback**: it checks out `main`, so pressing it after a bad merge deploys the bad merge again
- **Rollback is asymmetric and the fast half expires.** The backend rolls back with `az containerapp update --image <previous digest>` in **43 s** — not by shifting traffic, which this app refuses because it is deliberately in single-revision mode — and **the next merge silently undoes it**, watched happening. The frontend has no revision history at all on the Free plan, so its rollback is a revert commit through the pipeline at **3 min 42 s**. Both durable fixes are a revert commit; the fast one only buys time
- **The declined browser smoke check names this story as its reversal trigger.** Task 1.11.7 declined a post-deploy check that drives a real browser, with the gap stated: only a real browser catches a wrong `CORS_ORIGIN` or a missing `VITE_API_BASE_URL`, and `curl` is structurally incapable of it. **This story is the first one capable of shipping that failure**, so whether to build it is a decision to take here and record, not a check to add by reflex or to leave unmentioned
- **"Polling is deliberate about frequency" now has a cost dimension as well as a log-noise one, and the cost question is open.** The Consumption plan's **idle billing rate** — the thing that keeps this environment at ~$9.21/month rather than ~$19.04 — has among its conditions that the replica receive **less than 1,000 bytes per second** of network traffic. Platform health probes are not billable; **this story's polls are**, and they arrive from every open browser tab. Whether continuous probing breaks that condition **could not be answered in Story 1.11** — both billing APIs refuse this subscription with _"doesn't have valid WebDirect/AIRS offer type"_, reproduced six times, and the environment was under six hours old against cost data that lags 8–24 hours. Epic 2 re-reads it and Epic 3 must re-take it regardless. The baseline to measure against exists: **16 log records a minute at idle** from the three probes, and a probe-only idle baseline of **1–4 requests per 30 s**. A poll every 5 s from a single tab is 12 requests a minute on top of that. Choose the interval with that in front of you, and say why in the code
- **The deployed backend's configuration lives only in the platform, and this story is likely to change one value of it.** The three HTTP probes, `minReplicas: 1`, the ingress target port, `HOST=0.0.0.0` and `CORS_ORIGIN` are set on the app and recorded in no file here — `deploy.yml` uses `update` and never `create`, deliberately. If this story moves the frontend's origin, `CORS_ORIGIN` is a platform change that **nothing in a diff will show**, and the sharpest instance of the same shape is already live: the probes pin port 3000 while `PORT` is an environment variable, so the two can be made to disagree from a portal panel with nothing here noticing

### What Story 1.8 hands this story

Story 1.8 is complete and `docs/adr/0008-*` records it. It is a dependency, and it was closed in a way that leaves this story with a working connection it cannot yet see.

- **The browser boundary is decided and built: real CORS on the server, not a Vite proxy.** `apps/backend/src/cors.ts`, registered **inside `buildServer()`** so Story 1.9's `app.inject()` instances get it, one origin from `CORS_ORIGIN` (default `http://localhost:5173`) and `exposedHeaders: [REQUEST_ID_HEADER]`. **A proxy was built and rejected**, and the deciding measurement is one this story should not lose: through a proxy `x-request-id` reads back with **no configuration at all**, because a same-origin response exposes every header. Under real CORS it does not — the safelist is short and `x-request-id` is not on it — so `exposedHeaders` is what makes the correlation id readable from JavaScript, and a proxy would have hidden both the allowlist and that fact. Re-verified from a browser: the headers visible to a page are exactly `content-length`, `content-type` and `x-request-id`
- **The criterion is met and it is invisible.** The probe that demonstrated it was removed before Task 1.8.3 closed, nothing calls the API until this story, and **`curl` cannot re-check it** — with a string origin the server asserts the allowed origin to every caller and the browser is the only party that compares, so an unlisted origin gets a 200 too. **The first thing this story writes is the first shipping consumer of that decision.** If it fails, the symptom is `TypeError: Failed to fetch` in the page beside a **200 in the server log** — the request is answered and the browser discards it — which names neither CORS nor the origin
- **The dev terminal's floor is 2 lines per request, not 12.** Task 1.8.2 took a rendered `GET /health` from 12 lines to 2 and a 404 from 14 to 3, with no field dropped, so the "polling does not spam logs" criterion is being judged against a six-times cheaper terminal than the one Story 1.8 was told to decide against. Budget accordingly: a poll every 5 s is 24 lines a minute
- **One reversal trigger is explicitly yours.** `reqId` was kept in the `pretty` rendering precisely because **this story is what makes requests interleave**. If they turn out not to, `ignore: "reqId,pid"` is the lever and it is worth **172 → 117 columns** — the difference between a request line wrapping and not

Know before writing it that frontend configuration is statically substituted at build time, so the API's address becomes a literal in the bundle and **one artefact cannot be promoted across environments** — the same shape as `base` and `basename`, and Story 1.11 owns the consequence
- **The half-pair is a state this story's indicator will actually meet.** A busy port 3000 leaves `pnpm dev` running and looking healthy with no backend behind it, and nothing exits non-zero. `pnpm ready` is the command-line answer; the on-screen answer is this story's status display, and "unreachable" is the state it will be in

Story 1.9 is complete (2026-09-03) and recorded in `docs/adr/0009-the-test-runner-conventions-and-coverage.md`. This story is the first one that will write tests against the conventions it set, so most of what it hands over is a shape to follow rather than a constraint.

### What Task 1.12.3 settled, for the four tasks after it

- **The poll interval is `HEALTH_POLL_INTERVAL_MS = 30_000`, a literal in `apps/frontend/src/use-backend-health.ts`, and it is not a `VITE_` variable.** So this story still has exactly one environment variable and the three-place declaration set (`.env.example`, `vite-env.d.ts`, `deploy.yml`) is untouched — the check that would keep that trio honest is still owed by whichever task adds a second variable, and it is not this story's unless 1.12.4–1.12.7 add one. - **The hook returns five fields and none of them is a fourth state name.** `status: BackendStatus`, `degradedCause: BackendDegradedCause | null`, `lastSuccessAt: Date | null`, `lastSuccess: HealthResponse | null` and `hasChecked: boolean`. ## Acceptance criteria

- The frontend queries backend health and displays it in the application chrome
- Status distinguishes healthy, degraded and unreachable
- When the backend is unreachable the indicator reports it along with the last successful check time, and the rest of the interface remains usable
- Recovery is automatic when the backend returns — no page reload required
- Behaviour is verified against the deployed environment, not only locally
- Polling is deliberate about frequency and does not spam logs
