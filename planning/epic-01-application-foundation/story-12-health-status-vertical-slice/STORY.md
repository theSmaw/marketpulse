# Story 1.12 — Health & Status Vertical Slice

**Status:** Not started
**Epic:** [Epic 1 — Application Foundation](../EPIC.md)
**Depends on:** Stories 1.5, 1.7, 1.8
**Epic scope covered:** epic exit criterion — backend health/status viewable from the frontend

## Description

The story that closes the epic: prove the whole foundation works end to end by having the frontend display real backend status. Small in scope, but it exercises configuration, routing, layout, the API contract, error handling and deployment together.

It also establishes the connection-state pattern that Epic 3 reuses for the live market feed.

## Conventions from Story 1.1

Story 1.1 is complete, and these four bind this story. They are stated in every Epic 1 story so each one can be read on its own; the full reasoning is in `docs/adr/0001-repository-structure-and-typescript-toolchain.md`.

- **`pnpm verify` is the acceptance command** — `build && lint && format:check && stories && env:check && test && test:process`, chained with `&&` so the first failure is the exit code. It took its fifth step in Task 1.4.5: `stories` fails if a component has no stories file, and `build` now also produces the Storybook bundle. It took its sixth in Task 1.6.6: `env:check` fails if `.env.example` and `CONFIG_VARIABLES` have drifted apart, which is what makes the documented variable set a checked claim rather than prose. It took its **seventh** in Task 1.10.5: `test:process` runs the backend's ten process-level tests against a spawned `dist/index.js`, which is why the chain building before it runs is load-bearing rather than incidental. This story passes it from the repository root. Prettier owns Markdown as well as code, so an unformatted planning document fails it too
- **Six verbs, identical in every package** — `dev`, `build`, `test`, `lint`, `typecheck`, `clean`. Only `test` and `dev` fan out with `pnpm -r`; the rest run their tool once from the root, because the reference graph and ESLint's project service already cover the workspace in one pass. Changing what a verb means in one package means changing it everywhere, or saying why not
- **Shared tooling lives at the workspace root; packages declare only what they actually import.** ESLint, Prettier and TypeScript are root-only devDependencies, and pnpm puts the root's `node_modules/.bin` on every package script's PATH. A library the code imports belongs in the package that imports it — `@types/node` in `apps/backend` is the counter-example that keeps the rule from being over-applied
- **The module setup is ESM-only and single-file-safe** — `"type": "module"`, `module: nodenext`, `isolatedModules`, `verbatimModuleSyntax`, and relative imports carrying `.js` extensions from `.ts` files (TS2835 without one). `packages/shared` is consumed as **built output**, so it must be built before any consumer can be typechecked; `tsc -b` orders that itself, which is why `typecheck` and `build` are the same command

## What that means for this story

- The health response type is exactly what `packages/shared` exists for — one definition, both sides compiling against it. This story is the first real payoff of creating that package in Story 1.1 rather than deferring it, and the first place the build-before-typecheck ordering has a genuine consequence: change the health shape and both apps must be rebuilt, which `tsc -b` handles and `--noEmit` silently does not
- **The type this story promotes now exists, with names.** `HealthResponse` and `HealthStatus`, exported from `apps/backend/src/routes/health.ts`. Two details worth not guessing at: the uptime field is **`uptimeSeconds`**, not `uptime` — the unit travels in the name so it survives the wire — and `HealthStatus` is a one-member union `"ok"`. So the healthy / degraded / unreachable distinction in the criteria below is **entirely client-side today**: "unreachable" is the absence of a response, which no server can report about itself, and nothing widens the union until Epic 3 adds market-feed state. The union exists so that is an addition rather than a breaking change
- **`apps/backend` declares `@marketpulse/shared` without importing it**, and promoting the health type there is what makes that manifest entry honest again. Worth saying so the dependency is not deleted as dead first. It also makes a latent deployment problem live: because nothing imports the package today, the pnpm symlink into `packages/shared` is never followed at runtime, so a copied package directory runs despite it. The first import from this story starts exercising it — a reason to land Story 1.11's `pnpm deploy` mechanism before, or alongside, rather than after
- ~~**CORS has not been considered by any task in Story 1.2**, deliberately … so this story starts from zero on that~~ — **Story 1.8 built it, and this story starts from a working allowlist rather than from zero.** `apps/backend/src/cors.ts` registers `@fastify/cors` 11.3.0 inside `buildServer()`, exactly where this bullet predicted it would go and alongside Story 1.7's error handling, with one origin from `CORS_ORIGIN`. What is left here is not attaching it but being its **first shipping consumer** — see the Story 1.8 hand-off below, including why `curl` cannot re-check it
- ~~**`/health` has no response schema**~~ — **it has one since Task 1.7.3, and it does more than validate.** Fastify serialises through `fast-json-stringify`, which **strips every property the schema does not declare**, and the schema's properties are declared `satisfies Record<keyof HealthResponse, JsonSchemaProperty>`, so a field added to the interface and not to the schema is **TS1360** rather than a field that silently vanishes from the wire. Copy that idiom for whatever this story adds. Two gaps stay open and are dated 2026-09-01: a declared property whose JSON type disagrees with the TypeScript one is **coerced silently**, and a `required` property the handler omits is a runtime failure rather than a compile error
- The frontend must reach the backend over HTTP without importing anything server-side. `apps/frontend`'s `types` array enforces that structurally — `process` does not typecheck there — so resist any convenience that requires weakening it. It reads `["vite/client"]` since Task 1.4.2 (2026-08-31) rather than `[]`, and the guard was re-measured after that change: `process` still fails `TS2591`. The explicit list is what keeps auto-discovery off; its contents are not what does the work. Note the shape this takes in practice: the browser's `fetch` is available through the `dom` lib, and **the frontend still has no environment-variable mechanism** — `import.meta.env` typechecks now that `vite/client` is in scope, but nothing uses it and there is no `.env` file. The backend's URL has to come from somewhere this story chooses

### What Story 1.3 hands this story

- ~~**There is a shell to put the indicator in, and it is one component.**~~ **Five since Story 1.4 (2026-08-31), and one of them is close to what this story needs — see the Story 1.4 section below.** `apps/frontend/src/App.tsx` is still a single stateless function, and this story adds the application's **first state, first effect and first network call** — which means it is also the first code the React Compiler rule set will have anything to say about. Fifteen of `eslint-plugin-react-hooks`'s 17 rules are at `error`, `exhaustive-deps` is a `warn`, and `lint` runs with `--max-warnings 0`, so a polling effect with a sloppy dependency array fails `verify` rather than merely warning
- **The CORS origin is settled and stable.** Task 1.3.3 adopted `strictPort: true` precisely for this: a busy 5173 exits 1 rather than quietly binding 5174, so an allowlist pinned to `http://localhost:5173` cannot be defeated by a port shifting underneath it. That failure would have surfaced as a browser CORS error naming neither the port nor the cause
- **Watch the loopback family.** The frontend dev server binds `[::1]` and the backend binds `127.0.0.1`, so a browser talking to `http://localhost:3000` is fine while a script pinned to one family may not be. It also means the two origins differ by port only, which is still cross-origin
- **The frontend dev server does not typecheck.** A type error in this story's client code — the most likely place for one, since it compiles against `HealthResponse` from a package built by something else — is applied as an ordinary hot update with no overlay and no console error. `pnpm verify` or the editor is what catches it, and `packages/shared` must be rebuilt before either says anything true
- **Nothing about the deployed half is easier than it was.** The frontend artefact is `dist/` with an **absolute** asset path and no runtime configuration, so "point the frontend at the deployed backend" is a build-time input rather than a deploy-time one unless this story makes it otherwise
- Closing the epic means `pnpm verify` passes and the slice works in the **deployed** environment, not only locally. Verifying against a running local pair is the thing this story exists to go beyond

### What Story 1.4 hands this story

- **The status indicator has a component already, and it is not an error indicator.** `FeedIndicator` renders `live` / `stale` / `disconnected` as a marker **shape** plus a word, taking its `FeedStatus` from `packages/shared`, with stories for each state. - **Colour is never the only signal.** Under greyscale this palette's red and green are 1.05:1 apart. The status this story displays needs a word and a shape as well as a colour; that is what `FeedIndicator` is for, and it is the reason not to reach for a bare coloured dot

- **This story is still the first stateful code in the tree** ~~unless Story 1.5 gets there first~~ — **Story 1.5 did not get there first.** Six modules and zero state; `Region`'s `useId()` is the first hook in the application and `useId` is not state. A backend-status indicator goes beside the feed indicator in that first region or into the reserved one — a decision, not a search

The comment there names this story as the one that decides whether the backend connection is that same fact or a second indicator beside it. Story 1.4 posed the vocabulary question — `FeedStatus` means the market feed and this story means the backend service — and Story 1.5 has now put the market-feed answer on screen, so the choice is visible rather than hypothetical: two indicators in one region, or one indicator whose meaning widens

- **A component test of anything in the chrome needs router context.** `AppHeader` uses `NavLink`, so it cannot render outside a router; the workshop solves this with a single `MemoryRouter` decorator in `.storybook/preview.tsx`. ### What Story 1.6 hands this story

The frontend reads **no** configuration today, and this story brings the first variable it will genuinely need: the backend's URL. Everything about how that variable behaves is already decided and measured.

- **It must be `VITE_`-prefixed or it silently never arrives.** `envPrefix: ["VITE_"]` is stated in `vite.config.ts` as a decision, and the enforcement is at the reference site: a non-prefixed read compiles to `void 0`, not to a runtime lookup. `pnpm env:check` fails on a non-prefixed name in `apps/frontend/.env.example` for exactly this reason. `VITE_API_BASE_URL` is the shape the boundary was measured with
- **Adding it means adding it in two places, and the check enforces the second.** The variable itself, and a line in `apps/frontend/.env.example` — which is currently deliberately empty of variables. `env:check` only requires the prefix on the frontend side today; if this story wants the stronger backend-style guarantee (every documented name read by something, every default in step), that is a small extension to `scripts/check-env-example.mjs` rather than a new mechanism
- **It is inlined at build time, so one artefact cannot be promoted across environments.** A different backend URL is a **rebuild**, not a setting — the same shape as `base`. If this story's deployment story needs one artefact against two backends, that is the reversal trigger for ADR 0006 §6 and it is a decision, not a workaround
- **A credential must never follow it.** The browser talks to the MarketPulse backend and never to Alpaca or a model provider. A `VITE_` prefix is a boundary against accidents, not a permission: prefixing a credential makes it a string literal in a file every visitor downloads
- **CORS is pinned to 5173, and that is why the frontend's ports are literals.** Task 1.6.4 closed the "should the frontend's ports be configurable" question against making them so, partly on this story's allowlist: a silently moved port fails as a browser error naming neither the port nor the cause, which is why `strictPort` is on. If this story needs a second origin, it is `loadEnv()` in `vite.config.ts` rather than `process.env`
- **The backend's URL is the first thing that will want to differ between environments, and nothing branches on the environment today.** ADR 0006 §4 made that a decision rather than an omission. Read it before adding an `APP_ENV`; the answer is very likely one more value, not a name for the environment

### What Story 1.8 hands this story

Story 1.8 is complete and `docs/adr/0008-*` records it. It is a dependency, and it was closed in a way that leaves this story with a working connection it cannot yet see.

- **The browser boundary is decided and built: real CORS on the server, not a Vite proxy.** `apps/backend/src/cors.ts`, registered **inside `buildServer()`** so Story 1.9's `app.inject()` instances get it, one origin from `CORS_ORIGIN` (default `http://localhost:5173`) and `exposedHeaders: [REQUEST_ID_HEADER]`. **A proxy was built and rejected**, and the deciding measurement is one this story should not lose: through a proxy `x-request-id` reads back with **no configuration at all**, because a same-origin response exposes every header. Under real CORS it does not — the safelist is short and `x-request-id` is not on it — so `exposedHeaders` is what makes the correlation id readable from JavaScript, and a proxy would have hidden both the allowlist and that fact. Re-verified from a browser: the headers visible to a page are exactly `content-length`, `content-type` and `x-request-id`
- **The criterion is met and it is invisible.** The probe that demonstrated it was removed before Task 1.8.3 closed, nothing calls the API until this story, and **`curl` cannot re-check it** — with a string origin the server asserts the allowed origin to every caller and the browser is the only party that compares, so an unlisted origin gets a 200 too. **The first thing this story writes is the first shipping consumer of that decision.** If it fails, the symptom is `TypeError: Failed to fetch` in the page beside a **200 in the server log** — the request is answered and the browser discards it — which names neither CORS nor the origin
- **The dev terminal's floor is 2 lines per request, not 12.** Task 1.8.2 took a rendered `GET /health` from 12 lines to 2 and a 404 from 14 to 3, with no field dropped, so the "polling does not spam logs" criterion is being judged against a six-times cheaper terminal than the one Story 1.8 was told to decide against. Budget accordingly: a poll every 5 s is 24 lines a minute
- **One reversal trigger is explicitly yours.** `reqId` was kept in the `pretty` rendering precisely because **this story is what makes requests interleave**. If they turn out not to, `ignore: "reqId,pid"` is the lever and it is worth **172 → 117 columns** — the difference between a request line wrapping and not
- **`VITE_API_BASE_URL` is yours and it is a build-time literal.** Story 1.8 deliberately added nothing to `apps/frontend/.env.example`, which still documents no variables. Know before writing it that frontend configuration is statically substituted at build time, so the API's address becomes a literal in the bundle and **one artefact cannot be promoted across environments** — the same shape as `base` and `basename`, and Story 1.11 owns the consequence
- **The half-pair is a state this story's indicator will actually meet.** A busy port 3000 leaves `pnpm dev` running and looking healthy with no backend behind it, and nothing exits non-zero. `pnpm ready` is the command-line answer; the on-screen answer is this story's status display, and "unreachable" is the state it will be in

### What Story 1.9 hands this story

Story 1.9 is complete (2026-09-03) and recorded in `docs/adr/0009-the-test-runner-conventions-and-coverage.md`. This story is the first one that will write tests against the conventions it set, so most of what it hands over is a shape to follow rather than a constraint.

- **The render helper is where your providers go.** `apps/frontend/src/test-render.tsx` is the **third and last** description of the application's context, after `App.tsx` and `.storybook/preview.tsx`. It wraps a `MemoryRouter` today; **every provider this story or Epic 2 adds lands there** rather than in each test file, which is the whole reason it is a module. If you change the `ApiError` shape, rebuild before either app typechecks or tests against the change

### What Story 1.10 hands this story

Story 1.10 is complete (2026-09-03) and recorded in `docs/adr/0010-continuous-integration-what-the-tick-certifies.md`. Most of it is about a pipeline this story does not have to think about; three things are not.

- **Every change you make is verified on Linux from a clean environment, through the pull request rather than the branch.** `push` is restricted to `main`, so **a branch with no pull request open runs nothing** — open the pull request early, or use `workflow_dispatch`. A `pull_request` run verifies the merge commit, which is what would land
- **A green tick certifies `pnpm verify` and nothing else — specifically not coverage.** This story adds the frontend's first asynchronous behaviour and the backend's first polled route, so it will move the coverage figures; nothing gates on them, there is no threshold, and the only thing the pipeline asserts about coverage is that both 0% entrypoints are still **present** in the report. Do not add an exclusion to make a number look better — that assertion exists precisely to catch it
- **Your new tests reach CI for free, and a new step would too.** The pipeline runs `pnpm verify` by name and defines nothing of its own, so a suite added to a package's `test` script needs no workflow edit. If this story ever needs a check CI runs that your machine does not, that is the signal it belongs in the chain instead — `stories`, `env:check` and `test:process` all arrived that way
- **If you write a process-level or socket-level test, it belongs in `apps/backend`'s second runner and its name is load-bearing.** `*.process.test.ts` runs under `pnpm test:process`; anything else runs in the fast suite, which must not become conditional on a build or able to bind a port. Nothing enforces the naming, and both mistakes are green
- **The health poll this story adds is the first thing that will make CI's log noise matter.** At `LOG_LEVEL=warn` a healthy server writes zero lines; the process suite's readiness helper polls `GET /health` at `127.0.0.1` explicitly rather than waiting on a log line, for four separate reasons written out in ADR 0010 §14. Reuse that shape rather than grepping output

## Acceptance criteria

- The frontend queries backend health and displays it in the application chrome
- Status distinguishes healthy, degraded and unreachable
- When the backend is unreachable the indicator reports it along with the last successful check time, and the rest of the interface remains usable
- Recovery is automatic when the backend returns — no page reload required
- Behaviour is verified against the deployed environment, not only locally
- Polling is deliberate about frequency and does not spam logs
