# Task 1.12.6 — Make all three states happen locally, prove recovery, and measure what the poll costs

**Status:** Not started
**Story:** [1.12 Health & Status Vertical Slice](STORY.md)
**Depends on:** Task 1.12.5

## Objective

Produce every state by a real cause rather than by a flag, watch recovery happen without a reload, and put numbers under "polling is deliberate about frequency and does not spam logs". Local only; the deployed environment is Task 1.12.7's.

## Work

- **Produce each state by a cause, and write down the cause beside the reading.** Unreachable: stop the backend, and separately hold port 3000 with a squatter — which is the state `pnpm dev` leaves you in while looking entirely healthy, sixteen log lines scrolled away behind Vite's banner and nothing exiting non-zero. Degraded: Task 1.12.1 defined it structurally and named two producible causes, so there are two readings to take rather than one — `not-ok-status`, by pointing `VITE_API_BASE_URL` at something that answers non-2xx, which reaches the client as **either** `api-error` or `http-error` depending on whether the body is the contract's own error shape and collapses to the same state either way, and `unreadable-body`, by pointing it at any static host, which answers `index.html` at **200** and is the `vite preview` trap this repository has measured twice. Healthy: the ordinary pair
- **A socket that accepts and never answers is a different failure from a refused connection**, and it is the one that hangs `fetch` forever without a timeout. Produce it — Task 1.8.4's squatter is the recipe — and confirm the indicator reaches a state rather than staying on the last one. **Wait at least `API_TIMEOUT_MS`**, which Task 1.12.2 set at 5 s and which the hook passes through unchanged: before that elapses the correct behaviour is indistinguishable from a slow answer. Note the next poll then starts 30 s after the deadline expires rather than 30 s after the request began, because Task 1.12.3 schedules on **settle** rather than on a clock — so a run of hung polls is one request every 35 s, not one every 30. **The state it must reach is `unreachable` and not `degraded`**: latency is deliberately not degradation, so a timeout means nothing arrived. That is an assertion rather than an observation, and it is the one that fails if the deadline was never wired
- **Watch recovery rather than inferring it.** Stop the backend, see the state change, start it again, and see the state return with **no page reload**. Prove it was not a reload the cheap way: `performance.timeOrigin` unchanged and exactly one `navigation` entry, which is the same check this repository uses for HMR
- **Confirm the last successful check time is right and survives.** It must not clear on a failed poll, must not advance on one, and must read as the time of the last _successful_ check rather than the last attempt. That is one line of code and the most likely thing in this story to be quietly wrong
- **Count the log lines rather than estimating them, and note the window has to be longer than a minute now.** The rendered floor is 2 lines per healthy request and 3 per 404 since Task 1.8.2. Task 1.12.3 set the interval at **30 s**, so a one-minute window catches about two polls and its error bars are wider than the thing being measured — take **five minutes** with one tab open, and again with several, and divide. The predicted figure to check against is 2 requests and 4 rendered lines a minute per visible tab. Record it beside the interval, so the choice can be re-read against evidence later
- **The tab has to be visible for any of that to happen, and this is the trap in this task rather than a footnote (2026-09-04).** Task 1.12.3 stops the loop entirely while `document.visibilityState` is `hidden` and polls immediately on return. So a measurement taken with the terminal in front and the browser behind it records **one** poll and then silence, which looks exactly like a broken loop; and an **automated tab reports `hidden` and cannot be foregrounded**, which is the same property every component timing in this repository is measured against, arriving somewhere new. Keep the page visible for the whole window, say in the record that you did, and take one deliberate reading of the hidden case too — switching away for several minutes and back should produce exactly one request on return, which is a behaviour worth confirming rather than assuming
- **Take the re-render cost against the real tree, because the unit measurement is already in and it is not zero.** Task 1.12.3 measured 4 polls producing 5 renders of the hook's caller — one initial and one per poll — because a successful poll writes a fresh `lastSuccessAt`, so the state object is new and React cannot bail out. `App` is the router's host, so unless Task 1.12.5 confined it, **every 30 seconds re-renders `AppHeader`, `<Routes>`, the current route, all four `Region`s and the render check's 36-row table.** Measure it where it actually lands rather than in a hook harness, and read it against the "no routine main-thread task >50 ms" target: at this size it should be invisible, and the number is worth having because Epic 3 inherits the shape at a much higher rate
- **Re-check the `ignore: "reqId,pid"` reversal trigger, because it is explicitly this story's — and note the evidence base moved under it.** `reqId` was kept in the `pretty` rendering precisely because this story is what makes requests interleave. **At a 30-second interval from one visible tab they largely will not**: two requests a minute, seconds apart from nothing else, is not interleaving, and the trigger was written when the interval was an open question. So the honest reading is either several tabs at once or the acknowledgement that the predicted condition did not arrive. Look at the terminal: if they do not in fact interleave, the lever is worth **172 → 117 columns**, which is the difference between a request line wrapping and not. Decide it on what the terminal actually looks like
- **Take the frontend's own cost.** ~~Whether the poll produces a re-render per tick regardless of whether anything changed~~ — **that half is answered and it does; see the bullet above, and what is left is measuring it against the real tree** — and whether the effect survives a route change without tearing down and re-establishing. The second is a genuine question with a specific answer to check: the effect's dependency array is `[intervalMs, timeoutMs]`, both of which are constants, and the hook is called from `App`, which is outside `<Routes>` — so a route change should re-render without re-running the effect, and a poll **should not** restart on navigation. Confirm it by counting requests across four navigations rather than reasoning about it, because a re-established effect is a request per route change and would be invisible except in the log
- Re-take the artefact figures. The frontend's bundle has moved once in seven stories and this story moves it again — modules, JavaScript bytes, CSS bytes, file count and the md5 of each. **Say which build produced them**: a default build and a deploy build differ in two files, the JavaScript by 72 bytes and `index.html` at an identical 1,101 B because it carries the hashed script filename, so a size comparison reports the document unchanged and it is not

## Done when

- All three states have been seen locally, each from a named cause, with the reading recorded
- Recovery has been watched happening, with `timeOrigin` and the navigation count proving it was not a reload
- The log-line cost of the chosen interval is a measured figure rather than an estimate, taken over a window long enough for the 30-second interval and with the page **visible** for all of it
- The hidden-tab behaviour has been seen once deliberately: no polling while away, exactly one request on return
- A route change has been shown not to restart the poll
- The `reqId` rendering question is decided on evidence and recorded
- `pnpm verify` passes and `pnpm ready` still answers correctly for both the healthy pair and the half-pair

## Approach note

Every state in this story is a client-side conclusion, so the server log will say the system is healthy through most of what this task produces — and in the cross-origin case it will say **200 with a full body** while the browser says `TypeError: Failed to fetch`. The browser is the only instrument that can see what this story built. Take every reading there.
