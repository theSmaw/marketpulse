# Task 1.12.3 — Poll the backend: the application's first state, first effect and first network loop

**Status:** Complete (2026-09-03)
**Story:** [1.12 Health & Status Vertical Slice](STORY.md)
**Depends on:** Task 1.12.2

## Objective

Add the polling behaviour behind Task 1.12.1's three states: an interval chosen on evidence, a last-successful-check timestamp, and automatic recovery. This is the first stateful shipped code in the repository and the React Compiler rule set's first real test.

## Work

- **Read what Task 1.12.2 actually shipped before designing the hook, because three of its decisions land directly on this one.** `apps/frontend/src/api-client.ts` exports `getHealth(options?)`, which returns a `Promise<ApiResult<HealthResponse>>` and **never throws in any branch** — so a failed poll is a value this hook stores rather than an exception it has to catch, which is what keeps an unreachable backend out of `ErrorBoundary` entirely (Task 1.12.5's second, invisible criterion). It takes `{ signal, timeoutMs }`, so the teardown abort below is a parameter rather than something to build
- **There are seven outcomes and they do not map one-to-one onto the three states — the mapping is this task's, and it is four lines of judgement rather than a rename.** `ok` → `healthy`. `unreadable-body` → `degraded` / `unreadable-body`. **Both** `api-error` and `http-error` → `degraded` / `not-ok-status`, because the client tells them apart only by whether the body carried a `requestId` a user could quote, which is not a distinction `BackendStatus` has. **Both** `timeout` and `unreachable` → `unreachable`, because nothing arrived in either case — that is Task 1.12.1's structural definition and not a convenience. And `aborted` maps to **no state at all**: it is a torn-down effect or a superseded request, it is not a fact about the backend, and writing it into state is precisely the "resolved-after-unmount response" bug this task's own bullet below warns about
- One hook, in `apps/frontend/src/`, owning the state and the effect. It returns the derived status, the last successful check time and — if the indicator needs it — the last successful payload. Nothing renders here
- **Delete `apps/frontend/src/health-probe.ts` and the `void probeBackendHealth();` line in `main.tsx` in this task and not before.** Both say in their own comments that they are meant to be deleted by this story; the deletion is the expected shape rather than a regression. It belongs **here**, with the thing that replaces the call — deleting it in Task 1.12.2 would leave a merge window in which the deployed frontend calls the deployed backend nowhere at all, which is Story 1.11's criterion regressing mid-story for no gain
- **Expect the React Compiler rules to have an opinion, for the first time outside a spike.** Fifteen of `eslint-plugin-react-hooks`'s 17 rules are at `error`, `exhaustive-deps` is a `warn`, and `lint` runs with `--max-warnings 0` — so a sloppy dependency array fails `verify` rather than warning. Task 1.5.1 already found `react-hooks/set-state-in-effect` failing at **error** on the obvious shape of syncing state from a URL. Derive rather than mirror; if a rule fires, read what it is objecting to before reaching for a disable, and record any disable with its reason
- **The interval has a hard floor now and it is not a cost argument: it must be strictly greater than `API_TIMEOUT_MS`, which Task 1.12.2 set at 5 s.** At or below it, a hung request is still outstanding when the next poll starts and the two overlap forever — the exact failure the deadline exists to prevent, arriving from the other side. **Nothing checks this ordering**; it is stated in `api-client.ts` beside the constant and it is this task's to honour. The two numbers can be re-taken together, but they cannot be chosen independently, so if the cost argument below wants something faster than 5 s the deadline moves first and `unreachable` moves with it
- **Choose the interval deliberately and write the reason in the code, because there are now three costs and only one of them is log noise.** The dev terminal's floor is **2 rendered lines per request** since Task 1.8.2 (a `GET /health`; a 404 is 3), so a poll every 5 s — now the floor rather than a candidate — is 24 lines a minute in the shared `pnpm dev` terminal. The deployed backend writes **16 log records a minute at idle** from the three platform probes against a probe-only baseline of **1–4 requests per 30 s**, and a 5 s poll from a single tab adds 12 requests a minute **from every open tab**. And the Consumption plan's **idle billing rate** — the difference between ~$9.21 and ~$19.04 a month — has among its conditions that the replica receive **less than 1,000 bytes per second**; platform probes are not billable and these polls are. Whether continuous probing breaks that condition could not be answered in Story 1.11 and is not this task's to settle, but the interval must be chosen with it in front of you
- **Decide whether the interval is a literal or a `VITE_` variable, and say why.** The frontend's ports are literals as a stated decision; if this becomes a variable it is the story's **second**, and a variable is declared in three places now — `apps/frontend/.env.example`, `apps/frontend/src/vite-env.d.ts` and `.github/workflows/deploy.yml` — with **nothing checking the pair**. `scripts/check-env-example.mjs` reads the example and has no view of the declarations. Extending it is the obvious move and is owed by whichever task adds the second variable
- **Stop polling when nobody is looking, or state why not.** A background tab polling forever is the cost above multiplied by every tab a user forgot. `document.visibilityState` is the lever; note that an automated tab reports `hidden` and throttles React's scheduler, which is why every component timing in this repository is measured hidden against hidden
- **Recovery is the criterion most likely to be met by accident and least likely to be tested.** The state has to return to healthy on the next successful poll with no reload, and the last-successful-check time has to survive the failure that made it interesting — a failed poll must not clear it
- Abort the in-flight request when the effect tears down, and do not let a resolved-after-unmount response write state. The mechanism exists: pass an `AbortController`'s signal to `getHealth({ signal })`, which composes it with its own deadline via `AbortSignal.any()` rather than replacing it, and returns `{ outcome: "aborted" }` — read that outcome and write nothing. **Do not read the rejection to find out which signal fired**; the client already did, off the signals themselves, because a `DOMException` name is a string comparison against a value from another realm
- Tests beside the subject, through the conventions in Story 1.9. `apps/frontend/src/test-render.tsx` is where a provider goes if this hook needs one — it is the **third and last** description of the application's context, and putting one in each test file is what it exists to prevent

## Done when

- The three states are produced by real conditions rather than by a switch: `healthy` from a successful poll, `degraded` from one of the two causes Task 1.12.1 named in `BACKEND_DEGRADED_CAUSES`, `unreachable` from a transport failure **or a timeout** — the hook derives `BackendStatus` from `packages/shared` and does not invent a fourth name for anything
- A failed poll leaves the last successful check time intact; a successful poll after a failure returns the state to healthy with no reload
- The interval and the visibility decision each carry their reason in the code, and the interval is **greater than `API_TIMEOUT_MS`**
- `health-probe.ts` and its call site are gone
- `pnpm lint` passes at `--max-warnings 0` with no new rule disabled without a written reason, and `pnpm verify` passes

## Approach note

Nothing shipped here has ever had state, so the rules have never fired on real code — that is a property of the tree rather than evidence of compatibility. Treat the first rule that fires as information about the shape being written, not as an obstacle: the whole reason `eslint-plugin-react-hooks` was taken whole in Task 1.3.2, at 17 rules and mostly Rules of React rather than hook ordering, was to have this conversation on the first stateful code rather than the fiftieth.

## What it shipped (2026-09-03)

`apps/frontend/src/use-backend-health.ts` — one hook, `useBackendHealth()`, owning the state, the interval, the visibility rule and the teardown. It renders nothing; Task 1.12.4 builds the indicator and 1.12.5 gives the value a consumer.

- **The interval is `HEALTH_POLL_INTERVAL_MS = 30_000`, a literal, with the reason in the code.** It clears the 5 s floor `API_TIMEOUT_MS` sets six times over, and the three costs decided the rest: 4 rendered lines a minute in the shared dev terminal against 24 at 5 s, 2 requests a minute per open tab against the deployed backend's existing 16 idle log records a minute, and the Consumption plan's idle-rate condition of under 1,000 bytes per second, which platform probes do not count against and these polls do. **A `VITE_` variable was rejected**: it would be the story's second, declared in three places with nothing checking the set — and, the deciding argument, this number is _coupled_ to `API_TIMEOUT_MS`, which is a literal, so making one of a pair configurable lets an operator invert an ordering nothing checks from a place where the other half is not visible.
- **The ordering is checked by a test rather than left stated.** `HEALTH_POLL_INTERVAL_MS > API_TIMEOUT_MS` is an assertion in `use-backend-health.test.ts` — the repository's own rule that a test beats an eighth `verify` step when the thing being checked is reachable from code.
- **Scheduling is a chain of `setTimeout`s rather than `setInterval`**, so the next poll is scheduled when the previous one _settles_ and two requests can never be outstanding at once. That makes the overlap the floor exists to prevent structurally impossible as well as arithmetically avoided; the floor is honoured anyway, so a future move back to an interval cannot silently reintroduce it.
- **A hidden tab does not poll, and a returning one polls immediately** rather than waiting out the interval. Two consequences recorded beside it: an automated tab reports `hidden`, so a browser-driven check of the poll (Task 1.12.6, Story 1.13) sees the first poll and then silence unless it makes the tab visible; and a tab hidden mid-flight lets that request finish and writes its result, because cancelling a request the backend has already been asked to serve buys nothing.
- **The seven outcomes collapse onto three states in four lines of judgement**, in `toBackendHealth`. Both `api-error` and `http-error` are `degraded` / `not-ok-status`, because the client tells them apart only by whether the body carried a quotable `requestId` and that is not a distinction `BackendStatus` has. Both `timeout` and `unreachable` are `unreachable`, because nothing arrived. `aborted` maps to **no state at all** and returns the previous state untouched — it is a torn-down effect, not a fact about the backend.
- **No fourth state name, and `hasChecked` is why one was not needed.** Before the first poll settles `status` reads `unreachable`, which is literally true and true for an uninteresting reason; the boolean beside it is how Task 1.12.4 tells "we have not finished asking" from "we asked and nothing came back" without leaking a client-lifecycle fact into a vocabulary defined entirely in terms of the wire contract.
- **Recovery and the surviving timestamp are structural rather than remembered**: every failing branch spreads the previous state, so `lastSuccessAt` and `lastSuccess` cannot be cleared by a failure, and the next successful poll returns the state to `healthy` on the same mounted hook. Both are tested.
- **There is no `try`/`catch` anywhere in the loop and its absence is deliberate.** `getHealth()` never throws, so a rejection here would be a bug in the client rather than a backend that is down, and swallowing it is how that bug would stay invisible. It is also what keeps an unreachable backend out of `ErrorBoundary` entirely.
- **`health-probe.ts`, its test and the `void probeBackendHealth()` line in `main.tsx` are gone**, and `App` calls `useBackendHealth()` in the same change so the deployed frontend never stops calling the deployed backend. **The returned value is deliberately unused for exactly one task** — Task 1.12.5 gives it a consumer. The call is in `App` rather than `AppHeader` because the header sits inside its own `ErrorBoundary`: a header that throws would otherwise take the health check down at the moment it became most interesting. 1.12.5 should pass the value down, not move the call.

### Two findings the brief did not anticipate

- **The React Compiler rules said nothing.** Fifteen of the seventeen are at `error` and this is the first stateful shipped code in the repository, so the expectation was a conversation. There was none: `useState` plus a `useEffect` whose `setState` calls happen in async continuations and event handlers is not the shape `set-state-in-effect` objects to — that rule is about a synchronous update in the effect body, which is the _mirror_ shape Task 1.5.1's spike wrote. So the rules are still untested against anything they dislike; do not read this as compatibility.
- **What did fire was type-aware lint, and it is a real trap worth carrying.** `if (stopped) return;` after `await getHealth(...)` is `@typescript-eslint/no-unnecessary-condition` at error — _"value is always falsy"_ — because TypeScript narrows a `let` from an enclosing scope and does **not** widen it again across an `await`: the only assignment to `true` is in the teardown closure, which the analysis cannot see running. It is not always falsy; it is exactly the case teardown produces. Reading the flag through a one-line function closes it, because a call expression is never narrowed — no assertion and no disabled rule. **The general form: a lint error saying a guard is dead is not always evidence the guard is dead.**
