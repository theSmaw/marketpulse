# Task 1.11.7 — Make a failed deployment visible, and prove it does not take the environment down

**Status:** Complete (2026-09-03)
**Story:** [1.11 Deployment Pipeline & Development Environment](STORY.md)
**Depends on:** Task 1.11.6

## Objective

Meet the criterion that a failed deployment is visible and leaves the running environment intact, by making deployments fail on purpose in more than one way rather than by reading the platform's description of itself.

## Work

- **Fail it at least three ways, because they fail at different points and only one of them is the interesting case.** A **build failure**, which never produces an artefact and so never reaches the environment at all — the easy case, and worth doing first to confirm the gate. **Task 1.11.6 did exactly that and the result is not the shape this bullet assumed.** A deliberately unformatted Markdown file was merged to `main` with admin bypass; `verify` run `33732058463` failed at `format:check` and deploy run `33732126041` was **created and `skipped`**. So the first failure mode is done, and what it produced is a _skipped_ run rather than a failed one or an absent one — the gate leaves a visible record of itself, which is a better shape than the silence this task would otherwise have had to distinguish from a broken trigger. **Re-run it if you like, but do not re-derive it, and do not go looking for a red deploy run: a red `verify` produces a grey one.** A **deployment that builds and does not start**: the cheapest real one is an invalid required value, since `config.ts` reports every bad key, throws, and `index.ts` writes a plain stderr line and exits 1 — an out-of-range `PORT` does it. And a **deployment that starts and fails its health check**, which is the case that distinguishes a platform that keeps the old version from one that has already replaced it. **The middle one is already done and its worry is resolved.** Task 1.11.3 caused exactly this failure with an out-of-range `PORT`. A configuration failure does exit before the logger exists and writes a plain stderr line and **zero structured records** — that half is confirmed. But the fear that it would therefore be invisible at the log destination is **wrong**: Container Apps collects stdout and stderr **together**, so `F PORT must be an integer between 1 and 65535, received "0"` reaches both the console stream and Log Analytics. It is visible; it is simply not queryable as structured data. This task's remaining value in the middle case is the **frontend** half and the rollback, not rediscovering the backend's
- **The running environment must survive all of them, and that is checked by request during and after, not inferred.** Poll the deployed `/health` and the deployed frontend throughout each failed deploy, and record what the old version was doing at the moment the new one failed. A platform that swaps first and checks afterwards will produce a window in which the criterion is false, and that window is worth knowing about even if it is accepted
- **The frontend's failure mode is a different shape and is worse — and Task 1.11.4 already answered the question this bullet asked, in the unwelcome direction.** A partial upload is not a failed deploy: it is a **broken application with no failure anywhere**, `index.html` referencing a hashed asset that was not uploaded. That is exactly why the fallback is not a catch-all — a blanket rewrite answers the missing asset with HTML and the browser reports a MIME-type error naming nothing, whereas the shipped `exclude: ["/assets/*"]` makes it a 404 that names the file. **What 1.11.4 found is that this platform produces that state by itself on every deploy, not only on a partial one.** Polled continuously across two deploys, the ordering is: the incoming asset appears (harmless), then **the outgoing asset is withdrawn while the outgoing `index.html` is still being served** — about **1.5 seconds** of documents whose `<script>` is a 404 — and only then does the incoming `index.html` appear. Propagation is not even monotonic; the old asset flicked back to 200 after the new document went live. So **uploads are not atomic and there is no flag that makes them so**, and this task's job is no longer to find that out. It is to (a) re-run it and confirm the window on the shipping deploy path, (b) say what stands in for atomicity, and (c) note who is actually affected — nobody already on the page, because their assets are fetched and `index.html` is `no-cache` so their next navigation revalidates; only a **cold load landing inside the window**
- **Name where a failure is visible, and to whom.** Three candidates and they are not equivalent: the workflow run's own conclusion, which is only visible to somebody looking at the repository; the platform's own deployment status; and an actual notification. Take the decision explicitly — for a repository with one maintainer, "the run is red and the platform shows the failed deployment" may well be enough, and Story 1.10 declined comment bots and reporting services on exactly that argument. Declining is fine; not deciding is not
- **There are two rollbacks, they work differently, and the cheap half is the slow one.** The backend keeps **revisions**: a rollback is shifting ingress traffic to the previous revision, needs no build and no repository, and revision label FQDNs (`<APP_NAME>---<LABEL>.…`) let the old revision be addressed directly while it is being decided. The frontend has **no revision history on the Static Web Apps Free plan**, so its rollback is re-running the deploy from the previous commit — which needs the repository, the pipeline and a green `verify`. **Execute both**, and note the asymmetry in the write-up, because the intuition is exactly backwards: the static site is the half that looks trivially recoverable and is the one that takes minutes. **Task 1.11.4 performed the frontend's mechanism without calling it a rollback and the timing is a usable lower bound**: it deployed a synthetic artefact and then restored the real one, and the restore was a full `swa deploy` of a directory that already existed locally — no build, no pipeline, no `verify`, and the site was correct within a couple of seconds of the upload completing. **That is the optimistic case and it is not the rollback this criterion is about**: a real rollback starts from a commit rather than from a directory somebody still has on disk, so it needs a checkout, a `pnpm build` and the deploy. Time the real one; do not quote 1.11.4's.
- **A configuration rollout takes 20–25 seconds and the old revision serves the old values throughout, measured three times in Task 1.11.5.** Revisions `0000005`, `0000006` and `0000007` each took that long to start serving, `/health` answered 200 on every poll across all three, and — the part that matters for a check written against a deploy — **the old revision kept answering with the old `CORS_ORIGIN` until the new one actually took over**. So a probe run immediately after `az containerapp update` returns is reading the previous revision, and a check that does not poll will confirm whatever was there before. That is the third sighting of Task 1.11.3's traffic-weight finding and the cheapest one to trip over.

- **The ~4-minute failure window this task was written around no longer exists, and that is Task 1.11.3's doing.** The figure came from the platform's **default TCP** readiness probe — failure threshold 48 at a 5-second period. 1.11.3 replaced all three probes with HTTP probes against `/health`, and the readiness probe is now **3 failures at a 10-second period, so the window is about 30 seconds rather than four minutes** — roughly 8x shorter. Read the probe configuration off the deployed app before timing anything here; do not use either number from memory. The startup probe now carries the long grace (30 failures at 2 s = 60 s), and it governs a revision that never comes up at all rather than one that comes up unhealthy.
- **The platform documents zero-downtime deployment, and Task 1.11.3 already tested it once — so this task re-runs it rather than discovering it.** In single revision mode "Container Apps automatically switches between revisions to support zero downtime deployment". What 1.11.3 measured, deploying a deliberately invalid `PORT=0`: `/health` answered **200 on all 19 polls** across the failed deploy and the recovery; the bad revision crash-looped (`terminated with exit code '1' and reason 'ProcessExited'`) and was deprovisioned without ever serving; and — **the part that reads backwards from the API** — the _failing_ revision held `trafficWeight: 100` while still `Activating`, while the old revision at `trafficWeight: 0` was what actually served. **Traffic weight is not what serves**, so a check written against traffic weight reports the opposite of the truth.
- **Task 1.11.6 created a failure surface this task was written before, and it is the deploy workflow itself.** The deploy is now eight steps that can each fail — the OIDC login, the registry login, the image push, `az containerapp update`, the revision wait, `pnpm build`, the token fetch and the upload — and **the backend is deployed before the frontend, deliberately**, so that a new API is live before a page that needs it. The consequence is a failure mode neither half has on its own: **a merge that half-deploys.** A failure anywhere from `pnpm build` onwards leaves the backend at the new commit and the frontend at the old one, with a green `verify`, a red deploy run, and a site that works. Make it happen — the cheapest way is a step that exits 1 between the two halves — and answer the two questions it raises: whether a half-deployed environment is _broken_ (it is not today, because `/health`'s contract has not changed, and that is a property of this commit rather than of the arrangement), and whether re-running the deploy is safe (it should be, because both halves are idempotent updates rather than creates — **verify that rather than assuming it**).
- **The "starts and fails its health check" case now has a step written to catch it, and that step is unproven.** `deploy.yml` waits for the new revision to reach a `Running*` state, bounded at 300 s, and treats `*Failed*`, `Degraded` and `Stopped` as a red deploy. **Only the success branch has ever executed.** Task 1.11.3's crash-looping `PORT=0` revision predates that step, so nobody knows what `runningState` actually reads while a revision crash-loops, whether it ever reaches a state that pattern matches, or whether the step simply burns its whole 300-second deadline. That is this task's most valuable single measurement: it is the difference between a failed deployment being _visible as a red run_ and being visible only to somebody who goes looking at the platform. Read the state off the app during the failure rather than trusting the pattern, and fix the pattern here if it is wrong.
- **A backend rollback is undone by the next merge, silently, and nothing warns.** Shifting ingress traffic to the previous revision is a change to the app; the next merge to `main` runs `az containerapp update --image <the new commit's digest>` and puts the broken image back. So the backend's rollback is **not durable** — it buys time, and the durable fix is a revert commit through `verify` and the deploy. Say that where somebody reaching for the revision shift will read it, because the revision shift is the one that looks like the real rollback and is the one that expires.
- **`workflow_dispatch` on `deploy.yml` is a re-deploy, not a rollback, and the distinction matters.** It checks out `main`, so dispatching it after a bad merge deploys the bad merge again. It exists for the frontend's genuine use — re-uploading an unchanged `main` after a partial upload — and it is exactly the button somebody will press in an incident. **The frontend's real rollback is a revert commit**, which needs `verify` (~90 s) and then the deploy (~2 min 50 s), so about **4 min 20 s** from pressing merge. Time the real one; Task 1.11.4's couple-of-seconds figure is a local `swa deploy` of a directory somebody still had on disk, and this task's own note above already says not to quote it.
- **Roll back once, for real.** Document the path and then execute it, because a documented rollback that has never been run is the same class of claim as a check that has never failed. Record how long it took and whether it needed the repository at all — a rollback that requires a green pipeline is not a rollback
- **State what is still not covered.** Nothing checks the deployed application _after_ the deploy step returns successfully, unless a post-deploy smoke check is added; decide whether to add one and what it would assert. Note the honest limit if it is declined: a deploy that succeeds and produces a working-looking environment with, say, a wrong `CORS_ORIGIN` is green everywhere and broken in a browser. **Task 1.11.5 did not merely measure that shape — it produced two independent instances of it, and the second one is created by Task 1.11.6 rather than inherited.** The first is the wrong `CORS_ORIGIN`: the browser gets `TypeError: Failed to fetch` while `curl` with the same `Origin` gets a **200 with a full body** and the log records `statusCode: 200`, so every server-side signal says healthy. The second is a **frontend build with no `VITE_API_BASE_URL`**, which does not warn, does not fail, and ships a page dialling `http://localhost:3000` that an HTTPS page blocks as mixed content. So the decision this bullet asks for now has a concrete specification rather than a vague one: **the only check that would catch either is one that loads the deployed page in a browser and asserts the cross-origin call succeeded** — a status code is not enough, and `curl` is structurally incapable of it. That is a real cost (a headless browser in the pipeline) against a real gap, and it is a decision worth taking explicitly. Declining is fine; declining without naming what stays uncovered is not. **Since Task 1.11.6 there is a concrete place to put it and a concrete thing it would have to do**: a final step in `deploy.yml`, after the upload, that loads the deployed page and asserts the cross-origin call succeeded — and it would have to poll, because the frontend's upload is not atomic for ~1.5 s and the backend's rollout takes 20–25 s, so a check that fires once immediately after the deploy step can fail for a reason that is not a fault. Note also what the deploy already asserts and what it does not: it waits for the **revision** to be running, which is the platform's view, and nothing anywhere loads the page
- **There is a fourth failure mode, already characterised, that this task does not have to reproduce but should name.** Task 1.11.2 measured what a start command that does not `exec` does: PID 1 is a shell, `SIGTERM` is swallowed, the platform waits out its **30-second** grace and then `SIGKILL`s, with no `signal received` and no `shutdown complete`. That is a successful-looking deploy whose every revision change costs 30 seconds per replica and reads as slowness rather than as an error — a failure with no failure anywhere, the same shape as the frontend's partial upload above. It cannot happen from the current `Dockerfile`, so reproducing it here is optional; naming it as the regression to watch for is not.
- **Record the platform's own restart behaviour beside this**, because it blurs the boundary: an instance that crash-loops after a successful deploy is a failed environment produced by a successful deployment, and whether that is visible anywhere is the same question one step later

## Done when

- Three failure modes were made to happen: no artefact (**already done in 1.11.6** — a red `verify` left a **`skipped`** deploy run; re-run it, do not re-derive it), artefact that will not start (**already done once in 1.11.3** — re-run it, do not re-derive it), and instance that starts and fails its health check, which is the one genuinely untested case and the one the HTTP probes changed the behaviour of
- **`deploy.yml`'s revision-wait step was watched during a failing rollout**, its `runningState` read off the live app rather than assumed, and its failure-state pattern corrected if it does not match — this is the step that decides whether a failed deployment is visible as a red run at all
- **A half-deployed merge was made to happen** — a failure between the backend and frontend halves — and both questions it raises are answered: whether the environment is broken, and whether re-running the deploy is safe
- **The two rollback traps are recorded**: a revision traffic shift is undone by the next merge, and `workflow_dispatch` on `deploy.yml` re-deploys `main` rather than rolling anything back
- The zero-downtime claim was re-tested against the **HTTP** probes 1.11.3 configured, with the failure window read off the deployed app rather than assumed — about 30 seconds now, not the four minutes this task was written around
- The previously running environment answered `/health` and served the frontend throughout each, checked by request
- The frontend host's upload atomicity is **re-confirmed rather than discovered** — Task 1.11.4 established it is not atomic and measured a ~1.5-second broken window on two deploys — and what stands in for atomicity is decided, including a deliberate decision to accept it if that is the answer
- **Both** rollbacks were executed rather than described — the backend's revision traffic shift and the frontend's re-deploy — with each one's duration and prerequisites recorded, and the asymmetry stated
- Where a failure is visible is decided, including a deliberate decision not to notify if that is the answer
- Whatever remains unchecked after a green deploy is written down — **including the two measured instances of a green-everywhere-broken-in-a-browser deploy** (a wrong `CORS_ORIGIN`, and a frontend build with no `VITE_API_BASE_URL`), and whether a browser-based post-deploy check is adopted or declined

## Notes

Story 1.10's habit is the one to copy here: it made four failure classes happen on the runner rather than reasoning about exit codes, and one of them taught something the plan had not anticipated — a chain reports its first failure and nothing after it, so a probe has to be surgical or it proves the wrong step. Expect the same here, and expect the ordering of a deploy's steps to matter for the same reason.

## Outcome

**Complete, 2026-09-03.** Four failure classes were made to happen against the live environment, the running pair was polled by request throughout each, and both rollbacks were executed. The full record is in [`HOSTING.md`](HOSTING.md) under _What making the deployment fail measured (Task 1.11.7)_; this section is the summary and the answer to each _Done when_.

**One file changed** — `.github/workflows/deploy.yml`, whose revision-wait step is now a step that has had both of its branches executed. No dependency was added and `pnpm verify` is untouched.

### Against the criteria

- **Three failure modes made to happen.** _No artefact_ stands from Task 1.11.6 (a red `verify` left a **`skipped`** deploy run) and was deliberately not re-run — it costs a red `main` and an admin-bypass merge for a result already recorded. _Artefact that will not start_ was re-run here with `PORT=0`, and the plain stderr line reaches Log Analytics as an unstructured `Log_s`. _Starts and fails its health check_ — the genuinely untested one — was produced with `PORT=3001` against probes pinned to port 3000, three times.
- **The revision-wait step was watched during a failing rollout and its pattern corrected.** The pattern was **right** and the deadline was **wrong**: a failing rollout sits at `Activating` for **10 min 03 s** before becoming `ActivationFailed`, and the old 300-second deadline expired **4 min 09 s** too early to ever match it. The step now also reads the **replica**, which carries the truth from ~75 s in, taking a failing deploy from a 300-second silent timeout to **94 s** naming the cause (**36 s** for a container that will not start). Both branches executed before the text landed; the healthy case produces no false positive.
- **A half-deployed merge was made to happen**, and both questions answered. The backend moved and the frontend did not — `main` no longer held the probe marker and the served bundle still did — and **the environment was not broken**, which is a property of that commit rather than of the arrangement. **Re-running is safe but is not a no-op**: the same commit rebuilt to a different digest, so a new revision rolled out, and the commit-SHA tag has now pointed at two different digests.
- **Both rollback traps recorded, and both executed.** The revision shift is undone by the next merge — watched happening, with nothing warning — and `workflow_dispatch` re-deploys `main` rather than rolling anything back.
- **Zero downtime re-tested against the HTTP probes**, with the window read off the app: `Activating` throughout, the failing revision holding `trafficWeight: 100` while the old one at weight 0 served.
- **The previously running environment answered throughout each**, checked by request: no request ever returned a non-200 status and `uptimeSeconds` never reset.
- **Upload atomicity re-confirmed**, **Scoped by Task 1.12.7 (2026-09-04): this window is a property of the artefact _changing_, not of deploying — a docs-only merge that rebuilt byte-identically showed zero broken states across 174 CDN samples. Not a refutation: it was not re-measured on a changing artefact. See `docs/adr/0011-*` §17.** and it is **worse than recorded in one respect**: the ~2-second window contains **two** broken states, and the second — the incoming document served before the incoming asset exists — was not in Task 1.11.4's reading. Accepted deliberately; there is no flag.
- **Both rollbacks executed with durations and prerequisites**: backend **43 s** from a digest alone, frontend **3 min 42 s** through `verify` and the pipeline. The asymmetry is ~5x, and the fast half expires.
- **Where a failure is visible is decided**: the run's conclusion and the platform's own state, **no notification**, with what that costs stated.
- **What stays unchecked after a green deploy is written down**, including both measured green-everywhere-broken-in-a-browser shapes, and the browser-based check is **declined** with a reversal trigger.

### Four things it found that the brief did not anticipate

1. **The backend's documented rollback does not exist on this app.** `az containerapp ingress traffic set` is refused outright — traffic splitting belongs to **multiple** revision mode and this app is deliberately in **single** mode. The revision-label FQDNs this story offered as the mechanism are unreachable without first reconfiguring the thing that is already misbehaving. `az containerapp update --image <previous digest>` is what actually works.
2. **The image is not bit-reproducible across runs.** The same commit through the same `pnpm image` invocation produced a different digest and a different layer total (60,247,138 B against the recorded 60,247,220 B), so a re-run of a failed deploy rolls out a new revision rather than doing nothing.
3. **`runningState` returned an empty string** on one poll of an otherwise healthy rollout — a state that matches neither the success nor the failure pattern.
4. **A deployment check that runs from one machine over one link cannot distinguish its own network from the environment it is checking.** A 65-second "outage" during a failing rollout was the laptop: a three-host control reproduced the same drops with nothing deploying, and the backend's own Log Analytics records show it answering 9 requests per 30 s through the window against a probe-only idle baseline of ~~1–4~~ **a precise and explainable 4** per 30 s — liveness at `periodSeconds: 30` is 1 and readiness at `10` is 3 (refined by Task 1.12.7, 2026-09-04). The server-side record was the only tiebreak, and it is a measured argument against the single-shot smoke check this task had to decide on.
