# Task 1.11.6 — Deploy automatically on a merge to `main`, gated on `verify`

**Status:** Not started
**Story:** [1.11 Deployment Pipeline & Development Environment](STORY.md)
**Depends on:** Tasks 1.11.3, 1.11.4

## Objective

Turn the two manual deploys into one automatic consequence of merging, without giving the repository a second definition of what "verified" means.

## Work

- **Both manual deploys have been done and both sets of commands are recorded, which is this task's actual input.** Task 1.11.3 created the registry, the environment and the app by hand and Task 1.11.4 created the static web app and deployed to it, both writing the resulting facts and the exact commands into [`HOSTING.md`](HOSTING.md). **Neither half is a `create` any more, and that is the shape both deploy steps have to take.** On the frontend, the static web app exists, so a deploy is a **content upload into the existing `production` environment** — `npx -y @azure/static-web-apps-cli@2.0.10 deploy apps/frontend/dist --env production`, where `--env production` is the decision in the line, because the CLI's default is a preview environment and omitting it deploys somewhere nobody is looking. On the backend, a deploy is `az containerapp update --image <ref>` rather than a `create` — the ingress, the probes, the scale rule, the env vars and the managed identity are all already set and must not be re-specified by a deploy step, or the deploy becomes a second definition of the app's configuration in exactly the way Story 1.10 forbids for the build. And **the `AcrPull` role assignment already exists** on the app's system-assigned identity, so CI needs credentials to _push_ to the registry and to _update_ the app — it never needs registry pull credentials at all, which is the payoff of the ACR decision.
- **Decide where the deploy lives: a job in `verify.yml` or a separate workflow keyed on `workflow_run`.** Both have consequences worth stating rather than discovering. A job in `verify.yml` reuses the checkout, the toolchain and — if it is the same job — the build that just ran, and it is one file; but the workflow's name is what the badge reports, so a failed deploy turns the tick red for something the tick's paragraph in `README.md` says it does not certify, and the required status check keys on the **job** name, so a new job is not the required one unless the ruleset is edited. A separate workflow is a second file with its own triggers and its own concurrency group, and it has to be told what to check out. Take one, name the other
- **The platform's own GitHub integration re-defines the build, so the trap below is a near-certainty rather than a hypothetical.** Azure Static Web Apps generates a workflow when a site is created from GitHub, and that generated workflow takes an `app_location` and an `output_location` and **builds the site itself on the deploy side** — which is exactly "a platform that builds from source on its own side is the same problem wearing a different hat". The deploy action takes a flag that turns the build off (`skip_app_build`) so the step uploads what the chain already produced; **take that shape deliberately, and if the generated workflow is used as a starting point, say what was changed and why.** **One concrete trap to check rather than assume, because Task 1.11.4 tripped it with the CLI:** the SWA client **globs the working directory** for `staticwebapp.config.json` and reported finding `apps/frontend/storybook-static/staticwebapp.config.json` — the workshop's copy, not the one in the directory being deployed — because `.storybook/main.ts` reuses `vite.config.ts` and therefore inherits its `publicDir`. It was harmless only because the two files are identical bytes. Verify which copy the action picks up, and if it is the wrong one, the fix is on the Storybook side rather than in the workflow. The same question has a different answer on the backend: the image is built and tagged by Task 1.11.2's recipe and pushed to a registry, so the deployed artefact is identified by a digest and the provenance question is answerable rather than argued. **Task 1.11.3 settled which digest**: the image is an OCI _index_ carrying the `linux/amd64` manifest plus a buildx attestation at `platform: unknown/unknown`, the attestations are kept deliberately, and **the index digest is the provenance record** — it is what the platform pulls, it is the only one of the two that covers the attestations, and the platform manifest digest stays reachable from it. Pin and print that one. Its stated cost applies here: the index digest moves when attestation content moves even if the image bytes do not, so it identifies the _build_ — if this task wants to answer "did the image change", read the platform manifest digest instead.
- **Building the image on the runner is cheaper than it was locally, and the tag needs one decision.** `pnpm image` passes `--platform linux/amd64`, which on this Apple Silicon machine emulates and on `ubuntu-latest` is native, so the 45.3 s cold build Task 1.11.2 measured is an upper bound rather than a forecast. The trap is the tag: on a `pull_request` event `actions/checkout` gives the **merge commit**, so an image built in a pull-request job would be tagged with a SHA that never exists on `main`. Deploying only on `push` to `main` avoids it; a validation build in a pull request does not, and 1.11.2 already produced one mis-tagged image locally for the adjacent reason. **Task 1.11.3 settled the rule and built the door for this task rather than leaving it as a warning**: `pnpm image` is now `scripts/build-image.mjs`, a commit-SHA tag means the tree **is** that commit, a dirty tree gets a `-dirty` suffix and a line saying not to push it, and **`MARKETPULSE_IMAGE_TAG` overrides the computation entirely**. So the pipeline sets that variable from the commit it was triggered for — `github.event.after` on a push to `main` — rather than letting the recipe read whatever `HEAD` resolves to inside a checkout step. Do not invent a second rule here, and do not let a `-dirty` tag reach the registry: on a clean CI checkout it cannot arise, so one appearing is a signal that a step wrote into the working tree before the build.
- **The backend has no artefact fingerprint and the frontend has had one since Task 1.10.4, which is an asymmetry this task can close cheaply.** Every run already prints the frontend's files with sizes and md5s into the job summary, as a **record and not a check** — **four of them since Task 1.11.4**, and it needed no workflow edit because the step walks whatever `dist/` holds rather than naming the files, and that is what made "the artefact is byte-identical on Linux" provable. The backend's equivalent figures — image digest, compressed size, `/app` size, `dist/` file count — exist only as prose in Task 1.11.2's write-up, which is the gap this repository keeps finding on the expensive side. Decide whether the deploy job prints them the same way; it is a few lines and it is the difference between a doubling being visible and being discovered.
- **Nothing here may re-define the build.** The pipeline runs `pnpm verify` by name and defines nothing of its own, which is the whole of Story 1.10's argument and the reason its reversal cost is one file. A deploy step that runs its own `tsc` and its own `vite build` is a second definition of the artefact; a platform that builds from source on its own side is the same problem wearing a different hat. Decide explicitly whether the deployed artefact is the one CI built or a rebuild, and if it is a rebuild, say what makes the two the same — the frontend's four-file fingerprint is already printed into every job summary and is the ready-made comparison
- **A red `verify` must not deploy, and this needs to be seen once.** Say what enforces it: job `needs:`, a `workflow_run` conclusion check, or an `if:`. If the mechanism is a step condition, remember the `continue-on-error` trap Story 1.10 recorded — a step marked that way reports `conclusion: success` however it exited, and the real result is in `outcome`. Never write a deploy gate against a `continue-on-error` step's `conclusion`
- **Push is restricted to `main` and a pull request is verified through its own event**, which is already the trigger shape here. A deploy on `pull_request` would publish an unmerged branch to the development environment; a deploy on `push` to `main` is what the criterion asks for. If preview deployments per pull request are wanted, that is a decision with its own cost — more environments, more origins in an allowlist that takes exactly one — and it should be taken deliberately or declined here. **Task 1.11.4 turned that cost from a prediction into a measurement**: it deployed a preview environment and deleted it, and the origin was `red-smoke-029583a0f-previewprobe.eastus2.5.azurestaticapps.net` — a different origin from production, with the environment name **normalised** so it cannot even be derived from a branch name by substitution. So **every preview environment is a page that loads perfectly and cannot call the backend**, failing with the `TypeError: Failed to fetch` that names neither CORS nor the origin. The Free plan allows three of them and `stagingEnvironmentPolicy` is `Enabled` on the app today, so declining them is an action rather than a default
- **Automating the frontend deploy makes a measured transient happen on every merge, and that is worth deciding rather than inheriting.** Task 1.11.4 reproduced it on two deploys: the outgoing hashed asset is withdrawn while the outgoing `index.html` is still being served, so each frontend deploy has a **~1.5-second window in which a cold page load is broken**, and there is no flag on this platform that removes it. By hand that is a window somebody chose to open; automated it is one per merge to `main`. The honest options are to accept it (which a development environment reasonably does), to deploy the frontend only when `apps/frontend` actually changed, or to state it and move on — Task 1.11.7 owns the write-up, but **this task is what changes how often it happens**
- **Concurrency is not the same question it was for `verify`.** Superseded runs are cancelled everywhere except `main`, deliberately, because a cancelled run leaves a commit on `main` with no verdict. A cancelled _deploy_ is worse than that: two merges in quick succession must not interleave two uploads or two rollouts, so the deploy needs a concurrency group of its own with cancellation off, or the platform's own queueing has to be shown to serialise them
- **The credential's shape was decided in Task 1.11.1 and any departure from it is a divergence to record.** A **federated identity credential (OIDC)** scoped to this repository with a role assignment on the resource group, rather than a long-lived service-principal secret or a per-service deployment token — the same argument that pins every action to a commit SHA. Static Web Apps' default integration issues a long-lived **deployment token** instead, and if that is what ends up being used it goes into `HOSTING.md` as a divergence with its reason, **not** adopted silently because the portal offered it. **That divergence already exists once and is already recorded, which sharpens this bullet rather than settling it.** Task 1.11.4's hand deploy used the app's deployment token — fetched with `az staticwebapp secrets list` at the moment of use, passed through one command's environment, `--no-use-keychain` so nothing was stored, and no repository secret created. Two things follow. The federated identity credential is **still owed by this task and by nothing else**, so a future reader finding no OIDC credential should read that as unfinished rather than decided. And **the path of least resistance here is precisely the shape this repository has now declined three times** — pasting that token into an `AZURE_STATIC_WEB_APPS_API_TOKEN` repository secret is what every example does. **Establish first whether the Static Web Apps deploy action accepts an OIDC login at all**; if it genuinely requires a token, that is a real constraint and a recorded divergence with a reason, and it is a different thing from taking the token because it was easier.
- **There are now two identities to arrange, not one, and only the first was in this brief.** The deploy credential above authenticates _GitHub_ to Azure. Separately, **the container app authenticates itself to the registry**, and that is the whole reason Task 1.11.3 chose ACR over the free GHCR: a **managed identity on the container app with the `acrPull` role** on the registry, so there is no pull password in the app's `secrets` array. That role assignment is a resource that exists in nobody's tree and belongs in `HOSTING.md` beside the federated credential's subject. If the deploy ends up using an admin-user password or a stored PAT instead, the registry decision has been silently reversed and lost its only argument — record that as a divergence rather than letting it happen in a portal.
- **Secrets are repository secrets and nothing else.** A platform token never enters the tree and never enters a frontend build — the substitution rule means anything the frontend build can see is downloadable. Record which secrets exist, what they authorise, and how to rotate them; that is another piece of configuration no file here can hold
- **Pin any new action to a commit SHA, and re-count the pins.** There are four today — checkout, setup-node, cache and upload-artifact — and that count has been wrong once, so **count them out of the file** rather than copying this sentence. Every one is bumped by hand, because a SHA does not follow security releases, and Dependabot is declined for now with a fifth action as its stated reversal trigger. A deploy action would be the fifth — and on this platform it is likely to be the fifth **and sixth**, since a login action and a deploy action are two, and the frontend and backend may not share one. **So this task probably trips the stated Dependabot reversal trigger**, and the honest move is to take that decision here rather than let the count drift past its own trigger unremarked: either enable Dependabot for `github-actions` (a `.github/dependabot.yml`, which is a file rather than the repository setting Task 1.10.7 assumed) or re-decline it with the new count stated
- **If a deploy job should gate a merge, it has to be added to the ruleset.** Ruleset `main`, id 22160620, requires a pull request and the `verify` check on the default branch, with admin bypass retained. Nothing in the tree records it and nothing will show its absence. Most likely a deploy should _not_ gate a merge, since it runs after one — say so either way

## Done when

- A merge to `main` deploys both halves with no human action, observed on a real merge
- A red `verify` was seen not to deploy, made to happen rather than reasoned about
- The deployed artefact's provenance is decided and stated: CI's build, or a rebuild with a stated equivalence
- Whether the backend image's fingerprint is printed into the job summary beside the frontend's is decided either way
- The deploy has its own concurrency behaviour, and two rapid merges were shown not to interleave
- The image is tagged through `MARKETPULSE_IMAGE_TAG` from the commit being deployed, and no `-dirty` tag can reach the registry
- The container app pulls by managed identity with `acrPull`, or the departure is recorded in `HOSTING.md` with its reason
- Secrets are named, scoped and rotatable, and none is in the tree
- The action pins are re-counted from the file and any new one is on a SHA, and the Dependabot decision is re-taken against the new count rather than left at Task 1.10.7's
- The deploy credential is a federated identity credential, or the departure from that is recorded in `HOSTING.md` with its reason
- If the platform's generated workflow was used, what was changed in it — and specifically that it no longer builds the site — is recorded
- Whether the deploy participates in the merge gate is recorded either way

## Notes

The rule this task is most likely to break is the one Story 1.10 spent eight tasks protecting: **the pipeline runs `pnpm verify` by name and defines nothing of its own.** A deploy is the first thing that legitimately has to do something the chain does not — the correct shape is a step that consumes what the chain produced, not one that reproduces it.
