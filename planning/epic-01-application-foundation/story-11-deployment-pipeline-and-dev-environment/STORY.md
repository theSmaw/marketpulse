## Conventions from Story 1.1

Story 1.1 is complete, and these four bind this story. They are stated in every Epic 1 story so each one can be read on its own; the full reasoning is in `docs/adr/0001-repository-structure-and-typescript-toolchain.md`.

- **`pnpm verify` is the acceptance command** — `build && lint && format:check && stories && env:check && test && test:process`, chained with `&&` so the first failure is the exit code. It took its fifth step in Task 1.4.5: `stories` fails if a component has no stories file, and `build` now also produces the Storybook bundle. It took its sixth in Task 1.6.6: `env:check` fails if `.env.example` and `CONFIG_VARIABLES` have drifted apart, which is what makes the documented variable set a checked claim rather than prose. This story passes it from the repository root. Prettier owns Markdown as well as code, so an unformatted planning document fails it too
- **Six verbs, identical in every package** — `dev`, `build`, `test`, `lint`, `typecheck`, `clean`. Only `test` and `dev` fan out with `pnpm -r`; the rest run their tool once from the root, because the reference graph and ESLint's project service already cover the workspace in one pass. Changing what a verb means in one package means changing it everywhere, or saying why not
- **Shared tooling lives at the workspace root; packages declare only what they actually import.** ESLint, Prettier and TypeScript are root-only devDependencies, and pnpm puts the root's `node_modules/.bin` on every package script's PATH. ## What that means for this story

Deployment is where the workspace stops being invisible, and both of these are easier to plan for than to debug on a hosting platform.

Story 1.1 chose a pnpm workspace with `apps/backend` depending on `packages/shared` as a `workspace:*` dependency, consumed as **built output**. Two consequences land here and both are easier to plan for than to debug on a hosting platform:

- **You cannot deploy `apps/backend` alone.** Its `node_modules/@marketpulse/shared` is a symlink into the workspace, and `packages/shared/dist` must exist. `pnpm deploy --filter @marketpulse/backend` exists for exactly this and produces a self-contained directory; a platform that runs `npm install` in a subdirectory will not work
- **The build has to happen before or during deploy, in dependency order.** `pnpm build` is a single `tsc -b` over the root solution and handles the ordering itself — use it rather than per-package builds
- Pin the toolchain in the deploy environment the way CI and local machines do: Node 24.x from `.nvmrc` (`engineStrict` refuses other majors) and pnpm from `packageManager` via Corepack. A platform that supplies its own pnpm will fail the install rather than warn
- The frontend deploys as static assets; the backend as a long-lived process — **both now confirmed by measurement rather than assumed; see the Story 1.3 section below.** The hosting note in the open decisions above matters more than usual because of the persistent WebSocket and long-running agent requirements, so settle it against those rather than against today's health endpoint

### What Story 1.4 changed for this story

One thing, and it is a second artefact rather than a change to either of the two above. `pnpm build` now also emits **`apps/frontend/storybook-static/`** — 59 files and 9.3 MB on disk (Task 1.7.7; it was 52 files and 9.2 MB through Story 1.6, and the 50 files and 7.4 MB originally recorded here were wrong, 7.4 MB being the apparent size), none of it part of the product. Decide it deliberately, in one place, with 1.10.

### What Story 1.2 measured for this story

The backend now exists, and five of this story's assumptions were checked against it rather than left as plans. Details in `docs/adr/0002-backend-framework-and-server-composition.md`.

- **The deployable unit is the package directory, and that is measured rather than argued.** `dist` + `package.json` + `node_modules`, copied entirely outside the workspace, starts, serves `/health` with the manifest version, and exits 0 on `SIGTERM`. `dist/` alone dies at import time — first on `fastify`, and then, once `node_modules` is reachable, on the health route's read of `../../package.json` one directory above `dist/`. Both are `ERR_MODULE_NOT_FOUND` before `listen`, and **the first error hides the second**, so fixing the obvious half does not produce a working artifact. `pnpm deploy --filter @marketpulse/backend` produces the shape that works, so this story's named mechanism is confirmed. What it still owns: the base image, the **working directory**, which the manifest read depends on, and whether `packages/shared` is bundled or symlinked once something imports it
- **One half of that is currently latent.** Nothing in the emitted tree imports `@marketpulse/shared` — the complete runtime import set is `fastify`, `node:process`, `./server.js`, `./routes/health.js` and `../../package.json` — so the pnpm symlink into `packages/shared` is never followed at runtime and a copied package directory works despite it. Story 1.12's first import from that package is what makes it live, which is an argument for landing this story's `pnpm deploy` mechanism before or alongside 1.12 rather than after
- **The `pnpm start` wrapper is signal-transparent, so the question is whether to keep it, not whether it works.** `pnpm run` forwards `SIGTERM` to the child, **waits** for it to finish stopping (3.002s against a stand-in that took 3s), and propagates its exit code. Both routes were tested separately — `SIGTERM` to the pnpm process, which is what an orchestrator does, and `SIGINT` to the process group, which is what Ctrl-C does — and both exit 0 with the port released. So a container `CMD` of `pnpm start` would not swallow the signal or truncate the drain. It still adds a process, a package manager and a resolution step to a production image for no benefit once the artifact is built, so choose `node dist/index.js` deliberately — as a preference, not as a bug avoided
- **The remaining container-signal question is narrower than it was, not settled.** Signal handling was proved against a process started directly, which still says nothing about a container delivering `SIGTERM` to PID 1: a shell-form `CMD` or a wrapper script that does not `exec` will swallow it, and the symptom is a 10-second pause and a `SIGKILL` rather than an error
- **The shutdown ceiling is 5 seconds and the orchestrator's kill timeout has to be larger.** It was chosen to sit inside Docker's 10s stop grace and Kubernetes' 30s `terminationGracePeriodSeconds`; this story picks the orchestrator, so it owns the comparison. Both ends of the ceiling are exercised: a request finishing inside it exits 0, one exceeding it exits 1 with a `shutdown timed out, forcing exit` record
- **Fastify's startup log is not evidence of the bound interface.** It rewrites `0.0.0.0` to `127.0.0.1` in its `Server listening at` line, so a container that _is_ listening on all interfaces logs as though it is not — confirmed twice with `lsof`. `HOST` is a variable specifically so a container can set `0.0.0.0`; the host-binding question has to be answered by checking the socket, not by reading the log
- **`/health` reports whatever `version` the deployed manifest carries.** Free version reporting if the release process sets it, a permanently `0.0.0` health endpoint if it does not. A decision to make rather than default into

### What Story 1.3 measured for this story

The frontend now exists, and its deployable unit is **the opposite shape to the backend's**. That asymmetry is the useful part: this story ships two artefacts whose only shared property is that they came out of one `pnpm build`.

- **The frontend's deployable unit is `dist/` alone, and this is measured.** ~~Two files~~ **three since Task 1.4.2 (2026-08-31)** — `index.html`, one hashed `assets/*.js` and one hashed `assets/*.css` — with no `package.json`, no `node_modules` and **zero bare imports left in the bundle**, re-verified from a clean build in Task 1.4.6 at 193 modules, 300.09 kB of JavaScript and 7.21 kB of CSS — **stale by four stories, and rebuilt rather than cited on 2026-09-02: it is 271 modules, 343,658 B of JavaScript and 10,926 B of CSS**, still three files, and Story 1.8 moved none of it. Copied outside the workspace and served by `python3 -m http.server`, it renders in a browser with a clean console. Compare the backend, where `dist/` alone does not run at all and the package directory is the unit: one artefact needs a runtime and a dependency tree, the other needs a file server, and `pnpm deploy --filter` is the answer for one of them and meaningless for the other
- **The emitted asset path is absolute, so a subpath deployment is a rebuild — but it is now exactly one edit.** `base` defaults to `/`, so `index.html` references `/assets/index-<hash>.js`. Hosting the app at `https://host/marketpulse/` requires setting `base` in `vite.config.ts` and **building again** — it is not a hosting setting, a rewrite rule, or something fixable after the fact. Decide the public path before the build, or accept that the artefact is path-specific. **Task 1.6.5 removed the second edit this used to need:** `<BrowserRouter basename>` reads `import.meta.env.BASE_URL`, which Vite sets from `base`, so setting `base` moves the router with it and the two cannot desynchronise. Verified at `base: "/marketpulse/"` on a plain static host — all four routes and the not-found state render correctly under the subpath, every header link is prefixed, and the default `/` build is unchanged at three files
- **Rebuilding `packages/shared` does not reach a built frontend.** The shared code is inlined at bundle time and the workspace symlink is not part of the artefact — verified by perturbing shared, rebuilding it alone, and finding the built frontend byte-identical. So the frontend has no runtime equivalent of the backend's latent symlink problem, and instead has a staleness problem: a deploy pipeline that rebuilds shared without rebuilding the frontend ships the old copy silently
- ~~**The host's SPA fallback behaviour has to be stated rather than discovered.**~~ **It is no longer a cheap decision to make early — it is now this story's, and two of Story 1.5's acceptance criteria are waiting on it; see the Story 1.5 section below.** The original wording follows, because it was right about the mechanism and wrong that nothing needed it yet. `vite preview` has one and a plain static server does not, and the difference is not only about unknown routes: preview answers a **missing asset** with `index.html` and a 200, which reaches the browser as a MIME-type error rather than a 404 naming the file. There is no router yet (Story 1.5), so nothing needs fallback today — which makes this the cheap moment to decide it deliberately rather than the expensive one

### What Story 1.5 hands this story

There is a router now, and Task 1.5.5 (2026-08-31) deliberately did **not** tick two of Story 1.5's acceptance criteria, because neither can be met inside that story. Both are the same hosting property and both are this story's to close.

- **Deep-linking is a history-API fallback, and it is yours.** Measured rather than assumed: `apps/frontend/dist` served from outside the workspace by `python3 -m http.server` answers `/investigations`, `/securities` and `/replay` with **404**, while `vite preview` and the dev server answer all three — and every unmatched path, and `/assets/nope.js` — with the same 1101-byte `index.html` and a 200. Passing locally is therefore evidence of nothing. Hash routing was considered and rejected in Task 1.5.5: it needs no host support and puts `/#/` permanently into every URL a user copies or files in a ticket, which is a product cost paid to avoid one line of hosting configuration
- **The unknown-route criterion is the same property, and it is easy to think it is already met.** `NotFound` is a real route and renders correctly — _given_ that the host served `index.html` for the address that matched nothing. Without a fallback the user sees the host's own 404 page and the application never boots. Whatever this story picks has to be checked against a made-up path, not only against the four real ones
- **Three constraints on whatever mechanism is chosen.** It must serve `index.html` with a **200** rather than a redirect, because a 302 to `/` discards the path and defeats the purpose. `base` is `/`, so a subpath deployment remains a `base` change and a **rebuild** — a fallback is exactly where somebody will try to fix that cheaply and it will not work. And **the rewrite must not be a blanket catch-all**: one that answers every unmatched path with `index.html` answers a _missing asset_ that way too, which is the `vite preview` trap reproduced in production — a partial upload then looks like a broken application with no error naming the missing file. Scope the fallback to paths outside `/assets/`, or let `/assets/*` 404 explicitly, and verify it by requesting an asset that does not exist. **Task 1.6.5 built and measured the smallest correct version of this**, which is worth reading before configuring the real one: a fallback scoped to the subpath that declines to rewrite anything whose last segment contains a dot. Against the `base: "/marketpulse/"` artefact it gives 200 on `/marketpulse/`, `/marketpulse/replay`, `/marketpulse/securities`, `/marketpulse/investigations` and `/marketpulse/nonsense`, and **404** on `/marketpulse/assets/nope.js` and on `/other/` — deep links and the not-found route both work, and a missing asset still names itself. The same task also closed the second edit the subpath case used to need: `basename` now derives from `base`, so this bullet's warning about the router is discharged
- **Route splitting was measured and rejected, so the artefact this story deploys is still three files.** Task 1.5.5 built it both ways: splitting takes `dist/` from 3 files to 12, adds 1.44 kB of JavaScript, and moves 105 kB out of the eager chunk and straight into the landing route's own chunk — a second round trip on the page the product opens on. The decision has a stated reversal trigger (Epic 4 replacing Story 1.4's render check), so **this story should not assume three files forever**; the properties that would change are the ones already listed above — more absolute hashed paths, and a partial upload becoming a broken application rather than a stale one
- **The build is reproducible across checkouts.** Two clean builds and a separate clean clone with a cold pnpm store produced the same content hash and the same md5 (~~`e3fa3b5e…`~~ — a figure from Story 1.3, long superseded, and **`cba2825c…` today**), while the property it demonstrates has been re-confirmed byte-for-byte four times: Task 1.4.6, Task 1.7.7, and Tasks 1.8.6 and 1.8.7 from two separate clean clones with an empty pnpm store. So a deploy artefact can be compared against a local build, and a hash that differs means an input differed
- **Nothing has been served by a real static host.** `python3 -m http.server` proves the artefact is self-contained and proves nothing about caching headers, compression, redirects, or fallback on whatever this story picks. Cache policy in particular is untouched: the JS and CSS filenames are content-hashed and `index.html` is not, which is the shape that wants immutable caching on `assets/` and no caching on `index.html` — a decision this story owns

### What Story 1.6 hands this story

Story 1.6 is complete and recorded in `docs/adr/0006-configuration-and-the-secrets-boundary.md`. It discharged the `base`/`basename` warning above and it added no mechanism, but it does change what one of this story's acceptance criteria can mean.

- **"Environment configuration is managed by the hosting platform, not committed" is true of the backend and cannot be true of the frontend.** The backend reads its environment at run time through `apps/backend/src/config.ts`, so a hosting platform's variable panel is exactly the right place for its values. The frontend's configuration is **statically substituted at build time** — measured against the artefact, a prefixed value is a string literal in the bundle and a non-prefixed read compiles to `void 0` — so there is no run-time lookup for a platform to fill. **One artefact therefore cannot be promoted from a development environment to a production one; each environment is its own build.** Read the criterion as met when the backend's values come from the platform and the frontend's come from the build that produced that environment's artefact, and say which is which in whatever this story documents
- **Whether a rebuild per environment is acceptable is this story's decision, and the reversal has a stated trigger.** ADR 0006 §6 records why no run-time configuration mechanism was built: it would have been a mechanism with no consumer, designed against a deployment nobody had chosen. If the hosting this story picks makes a rebuild per environment genuinely painful, the answer is a small run-time config endpoint or a generated `config.js` fetched before the application boots — not widening `envPrefix`, and not `define`
- **The first credential belongs in `apps/backend/.env` and on the backend's platform, never in the frontend's.** Epic 2 brings the Alpaca key. A `VITE_` prefix is a boundary against accidents, not a permission — prefixing a credential makes it a string literal in a file every visitor downloads. Note this applies to `storybook-static/` too, which `pnpm build` also produces and which serves from a dumb static host exactly as `dist/` does; that is a second reason the bullet above about not deploying it by accident matters
- **`pnpm verify` is six steps now and `env:check` needs `build` to have run**, because it imports the backend's built `dist/config.js`. Anything here that runs a subset of the chain, or runs it against a tree it has not built, gets ``run `pnpm build` first`` rather than a pass

### What Story 1.7 hands this story

Story 1.7 is complete and `docs/adr/0007-*` records it. Five things land here, and the first is a trap rather than a decision.

- **At `warn` and above the server never prints `Server listening at …`.** Nothing in a normal run emits above `info`, so at `LOG_LEVEL=warn`, `error` or `silent` a server that starts, serves and shuts down cleanly writes zero lines to stdout and zero to stderr. **Anything waiting on that line to decide the process is up will hang, not fail.** Readiness is the port or `GET /health`
- **Logs are JSON on stdout and there is no file destination, deliberately.** `LOG_FORMAT=pretty` exists for a terminal and starts a worker thread; production wants `json`. The one thing to get right is that **stdout is the whole story** — Task 1.7.5's entire point was that Node's default put a crash on stderr while every other record went to stdout, so a deployment collecting only stdout lost exactly the record it most needed. Collect both, or know why not
- **There is no production-detail switch, and adding one would be a regression.** No `ERROR_DETAIL`, no environment branch: a 5xx never carries the thrown message, the stack is in the log beside the correlation id the client was handed, and withholding is free because of that id. This is the same shape as the rejected `redact` — a setting whose misconfiguration leaks silently, outward
- **`NODE_ENV` is still read nowhere, and that has now survived two tests.** The three environments differ in where values come from, not in how the application behaves. Introduce an environment variable only when something has to _behave_ differently rather than be configured differently
- **The operator needs to know about the third failure experience before reading a log with it in.** A crash detached from the request that caused it answers **200 with a valid `x-request-id`** and then dies, so the id the user quotes points at a record correctly saying their request succeeded, and the level-60 record beside it carries no id at all. A crash _with_ a request in flight is worse for the user and easier to read: `curl: (52) Empty reply from server`, **no body and no headers**, so not even an id to quote. "Quote the id and find the entry" is a rule with a stated exception, not a guarantee

### What Story 1.8 hands this story

Story 1.8 is complete and `docs/adr/0008-*` records it. It is not a dependency, and it hands this story two obligations and one worked example.

- **You must set `CORS_ORIGIN`, because the default is not safe by omission.** The backend now enforces a real allowlist (`@fastify/cors` 11.3.0, one origin from configuration) and it **defaults to `http://localhost:5173`** so that a clean clone works with no `.env`. A deployment that never sets it therefore lets somebody's local dev server call production. Small — `credentials` is off and there is no cookie to ride along — and real. "Required in production" is deliberately not expressible here (ADR 0007 §1, unchanged after two more tests), so a documented default that `pnpm env:check` keeps honest is what replaces it, and setting it explicitly is **this story's job**
- **Two things about that allowlist that will otherwise be misdiagnosed.** With a string origin the server asserts `access-control-allow-origin` **unconditionally** — an unlisted origin and a request with no `Origin` at all both get a 200 carrying the allowed origin, and the **browser** is the only party that compares. So **`curl` cannot test this**, there is correctly no `Vary: Origin` on a simple request, and **CORS is not this API's access control**; the router and the error handler are. And `@fastify/cors`'s `methods` defaults to **`GET,HEAD,POST`**, so the first route taking a `PUT` or `DELETE` is refused at preflight while answering `curl` perfectly
- **The API's address is a build-time literal, so one artefact cannot be promoted across environments.** Story 1.12 gives the frontend `VITE_API_BASE_URL`, and frontend configuration is statically substituted at build time — the same shape as `base` and `basename`, and the same consequence: **each environment is its own build**. That is already annotated on the criterion below; Story 1.8 confirms the second variable will land in the same shape rather than finding a runtime mechanism
- **A readiness check is a script now, and it is the shape a container probe should copy.** `scripts/check-ready.mjs` polls rather than greps, for four reasons that all apply to a probe: the `warn`-and-above silence above; Fastify rewriting `0.0.0.0` to `127.0.0.1` in its startup line, so that line is **not evidence of the bound interface**; the line arriving second in a race; and its clock format having changed. It dials a wildcard `HOST` as `127.0.0.1` for exactly the first reason. Note also that **Node's `fetch` tries both address families and `curl` does not**, which matters for whatever a container healthcheck is written in
- **A worked host fallback already exists.** Task 1.6.5 built the smallest correct one for a subpath deployment — scoped to the subpath, declining to rewrite anything whose last segment contains a dot — and Story 1.5's constraint stands: the rewrite must **not** be a blanket catch-all, or a missing asset reaches the browser as a MIME-type error instead of a 404

### What Story 1.10 hands this story

Story 1.10 is complete (2026-09-03) and recorded in `docs/adr/0010-continuous-integration-what-the-tick-certifies.md`. This story inherits more from it than any other, and most of it is not about CI.

- **A clean-environment build on Linux is now proved rather than hoped.** Every run builds from nothing — no `dist/`, no `storybook-static/`, no `.tsbuildinfo` is ever cached, deliberately — and the toolchain comes from `.nvmrc` and `packageManager` with no version literal anywhere. The install is **397 packages on Linux against 398 on macOS**, the one package being `fsevents` (`os: [darwin]`, via Vite), so a package-count difference between a laptop and a container is expected and is not evidence of a broken install. Exactly one Rolldown binding installs, `@rolldown+binding-linux-x64-gnu@1.2.6`, and the workflow asserts it by name and count
- **The frontend artefact is byte-identical across platforms, all three files.** 343,658 B / md5 `cba2825c…`, 10,926 B / `f98519e3…`, 1,101 B / `eab270a4…` — 355,685 B over three files, from Linux and from macOS. So a deployed bundle that differs from a local one is a real difference and not a platform artefact. Every run prints that fingerprint into its job summary; it is a **record and not a check**, so nothing will fail when this story's `base` change moves it
- **`CORS_ORIGIN` must be set explicitly by this story, and the default is not safe by omission.** It defaults to `http://localhost:5173`, so a deployment that never sets it lets somebody's local dev server talk to production. Small — `credentials` is off — and real
- **The readiness rules apply to a container probe exactly as they do to CI.** `pnpm ready` is deliberately **not** a pipeline step, because `verify` runs with no servers up; the rules behind it are what transfer. At `LOG_LEVEL=warn` a healthy server writes **zero** lines, `Server listening at …` included, so a probe that greps a log line **hangs** rather than fails. Fastify rewrites `0.0.0.0` to `127.0.0.1` in that line, so it is not evidence of the bound interface. A socket that accepts and never answers hangs `fetch` forever, so every attempt needs its own timeout rather than one overall deadline. And Vite's dev server never 404s, so no HTTP status can judge a frontend — content type is the discriminator
- **The process half is tested now, which is the thing this story depends on.** `pnpm test:process` is ten tests spawning a real `dist/index.js`: both signals drain and exit 0 releasing the port, a second signal during a drain exits 1, the ceiling forces an exit at 1 with a level-50 record, `EADDRINUSE` exits 1, and both crash handlers write one level-60 record and exit 1. The shutdown behaviour this story deploys against is no longer verified only by hand-run measurements. **One correction to carry**: completing a held request after `close()` gets a **503**, not the 200 Task 1.7.5 recorded — what holds a drain open is the connection, not a request in flight
- **A coverage figure and a test are two claims.** `apps/backend/src/index.ts` reads **0%** and has ten tests, because V8 coverage instruments the runner's own process and that suite's subject is a spawned child running built output. Do not read that cell as untested
- **`storybook-static/` is not uploaded as a build artefact and that is not the site question.** Task 1.10.4 declined the upload at 9.3 MB per push; **whether the workshop is published as a site is this story's decision**, and it is still open
- **The gate this story's deploys will pass through is a repository ruleset, not a file.** Ruleset `main`, id 22160620: a pull request plus the `verify` check on the default branch, admin bypass retained. Anything this story adds that should also gate a merge has to be added there, and nothing in the tree will show it. If a deploy job is added to `verify.yml`, remember the required check keys on the **job** name

## Acceptance criteria

- Merging to the main branch deploys automatically
- A development environment is reachable at a documented URL
- Deployed backend `/health` responds successfully
- The deployed frontend communicates with the deployed backend
- Environment configuration is managed by the hosting platform, not committed — **for the backend. The frontend's is build-time and cannot be; see the Story 1.6 section above**
- A failed deployment is visible and does not take down the running environment

## Tasks

Tackled in order. The story is complete when all eight are done.

1.11.1 decides and deploys nothing, deliberately — the same shape as Task 1.10.1 installing and stopping, so the first failed deployment in this repository's history has one possible cause. 1.11.2 is entirely local: it produces the backend artefact and runs it outside the workspace, because a platform failing on an artefact that was never correct is the most expensive failure to read. 1.11.3 and 1.11.4 are the two deploys, and they are separate tasks because the two halves share almost nothing — one needs a runtime, a probe and a variable panel, the other needs a fallback and a cache policy — and 1.11.4 is where two of Story 1.5's acceptance criteria are finally closable. 1.11.5 needs both to exist, and it is the only task here that touches application code; the scope it takes from Story 1.12 is a decision it has to state. 1.11.6 automates what 1.11.3 and 1.11.4 did by hand. 1.11.7 makes deployments fail on purpose, which is why it comes after the automation rather than being folded into it. 1.11.8 closes the story.

Each task leaves the repository installable, typechecking and passing `pnpm verify`, and — since Story 1.10 — leaves the pipeline green. This story adds a third clause from 1.11.3 onwards: **each task also leaves the deployed environment up.** The three are not the same claim, and the last one is the only one nothing in this repository can check for you.

**Three things this split deliberately does not do.** There is **no task that changes what `pnpm verify` means**, and no task that adds a CI-only check — both would fork the definition of "verified", which is the property Stories 1.1 and 1.10 built. There is **no task that builds a run-time configuration mechanism for the frontend**: ADR 0006 §6 records why one was not built, and the reversal trigger is a rebuild per environment turning out to be genuinely painful, which is a finding 1.11.5 might produce rather than an assumption this split may make for it. And there is **no task for a production release** — the criterion is a _development_ environment at a documented URL, and everything about promoting one is Epic 15's.
