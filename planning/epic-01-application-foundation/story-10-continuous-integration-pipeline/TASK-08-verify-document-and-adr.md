- **Re-take the runner figures against a known spread, not against a single reading — and the spread got wider, not narrower.** Task 1.10.2 measured the same commit at **31,075 ms** and **21,989 ms** on two runners; Task 1.10.3 added seven more readings of one tree and the range is **18,589–32,210 ms, a 13.6 s spread**, against installs of 4,455–6,127 ms uncached (n=8) and 3,895–4,597 ms on a cache hit (n=4). So three readings are the minimum for any claim about a total here, the per-step split is still the durable half, and **the cache's ~1.6 s is a quarter of the noise it sits inside**. A single slower run after Tasks 1.10.3–1.10.5 is not evidence of anything, and specifically is not evidence the cache stopped working — for that, read `cache-hit` and pnpm's `reused`/`downloaded` counts.

  **That whole range is a SIX-step chain and the chain is seven steps now**, so it cannot be quoted against a current run without saying so. The seven-step chain's first runner reading is **43,263 ms** — build 8,925 / lint 8,756 / `format:check` 6,882 / `stories` 554 / `env:check` 545 / `test` 7,352 / **`test:process` 9,199** — with an install of 5,169 ms. Take at least three of these before writing a new spread. One finding in that split is worth carrying into the ADR rather than re-deriving: **`test:process` is the least runner-sensitive step in the chain**, 9,199 ms against 7,600 ms on the laptop — **1.21×**, where every other step runs 2.2–3.5× — because five of those seconds are `SHUTDOWN_TIMEOUT_MS` elapsing in wall-clock time and a faster machine cannot shorten them. So the seventh step both raises the total and _compresses_ the relative spread, and a runner-versus-laptop ratio taken over the whole chain now means less than it did

- **Re-check the cache categorically rather than by timing, on the shipping workflow.** An exact hit is `cache-hit: true` with `reused N, downloaded 0`; a miss is `reused 0, downloaded N`. The restore-key path was exercised once with a throwaway devDependency that was then reverted, so **the shipped workflow's restore-key branch has not run since** — if any task between 1.10.3 and here changes the lockfile, that is a free re-proof and worth capturing rather than a run to skim past

It is now printed into the job summary by a fingerprint step on **every** run, so this task reads it off a run rather than rebuilding by hand; a difference is worth understanding before it is written off. One cross-platform difference is already known and is not a fault: the runner installs **397 packages against macOS's 398**, the one package being `fsevents` (`os: [darwin]`, via Vite). Expect the package counts to differ and the artefact not to
- **Update the documentation, in the three places that have to agree.** `README.md` gains the badge and the CI section; `CLAUDE.md`'s Current state and Commands sections gain the pipeline and lose nothing that is still true; the ADR carries the reasoning. Keep the split this repository already uses — `CLAUDE.md` is the operational summary, the ADR is the record of _why_ — and remember Prettier owns Markdown, so an unformatted document fails the very pipeline this task is closing
- **Write `docs/adr/0010-*` from the facts, not from the task files.** It follows 0001–0009 and the numbering convention in `docs/adr/README.md`. The decisions worth a numbered section, each with its rejected alternative and its consequence:
  - The provider, and the one-file cost of reversing it
  - **The pipeline runs `pnpm verify` and defines nothing of its own** — the story's central decision, and the one most likely to be "improved" by someone splitting it into steps. The corollary worth its own paragraph: **per-step visibility was bought by deriving the split from the chain's own output**, so the workflow names no step and a seventh one appears without a workflow edit — and that split is diagnostics rather than a check
  - **The trigger set**: `push` restricted to `main`, `pull_request` unrestricted, `workflow_dispatch` kept. Both halves of the reasoning — the duplicate run, and the fact that a `pull_request` run verifies the merge commit while a push run verifies the branch tip — plus the stated cost, that a branch with no pull request open is not verified, and the mechanism behind it: the trigger is read from the workflow file **on the pushed ref**
  - **Cancelling superseded runs, and `main`'s exemption** — a run on the default branch is the record of what that commit does
  - Toolchain pinning: `.nvmrc` plus `packageManager` via Corepack, with `engineStrict` making a wrong Node a hard failure, and no separate pnpm install
  - **Caching the store and not the build**, with the stale-`dist` measurement as the reason and Task 1.10.2's number beside it — caching the build moves exactly one step, `build` 6,010 → 3,477 ms, so the whole prize is ~2.5 s against a 13.6 s spread. Three further things belong in this section or they will be re-derived: the **store cache's honest value** (~1.6 s on a median install, with the warm and cold ranges overlapping — kept because it is categorically provable and costs one pinned action, not because it moves the clock); **`--trust-lockfile`, rejected**, which would remove the dominant line of a cold install (pnpm 11's supply-chain check, 2.5–4.5 s over 492 entries, uncacheable because it verifies the lockfile rather than the store) and which this runner is precisely the machine meant to run; and the **cache's ref scoping**, which means a `workflow_dispatch` run cannot see a `pull_request` run's cache
  - **The `cache: pnpm` ordering**, and what keeping Corepack after `setup-node` cost: a third pinned action, against the alternative of pinning pnpm to whatever Node the runner image ships for the length of one step
  - **Coverage outside the chain, where it runs, and the threshold decision** — all three, because the second is the one that will be re-argued. It is a **step in the `verify` job** and not a second job: a second job is a second runner with its own checkout, setup, install and, unavoidably, its own `pnpm build`, since `packages/shared` is consumed as built output; as a step it cost 8,279 ms on the runner against 2.60–3.06 s locally. A second **workflow** was never a candidate, since the triggers and the concurrency group are properties of the workflow. It is `continue-on-error`, which is what makes "the green tick certifies 113 tests and not coverage" structural rather than documented — **count them from the chain, not from this sentence, which said 103 until Task 1.10.5** — with the consequence that a step's `conclusion` reads `success` however it exited and the evidence of a failure is the annotation. **No threshold**, with all three reasons and the measurement behind the third: excluding just `apps/backend/src/index.ts` takes the package 64.33% → 91.08%. ~~The reversal trigger is Task 1.10.5's denominator~~ — **that trigger fired and produced no movement, which the ADR should record as the outcome rather than as a pending question.** 1.10.5 gave `index.ts` ten tests and the package is still **64.33% with that file at 0%**, because V8 coverage instruments the runner's own process and the suite's subject is a spawned child running built output. So one of the three reasons is spent, and the argument is stronger without it: a threshold here would be a threshold over a number that is provably not a measure of what is tested. The live reversal trigger is now a **merged-coverage mechanism** (`NODE_V8_COVERAGE` per child plus a merge, weighed and declined) or a package where the figure and the testing are the same claim
  - **The one invariant the pipeline enforces that `pnpm verify` does not**: both 0% entrypoints are asserted **present** in the coverage report — presence rather than a percentage, so the task that makes `index.ts` reachable does not fail it
  - `pnpm ready` deliberately not a step, and why the obvious instinct is backwards
  - **The process-test suite (Task 1.10.5)** — and it needs more than the one line this bullet used to be, because six of its decisions have a rejected alternative behind them. What it covers; **why it is a seventh `verify` step rather than a CI step** (the workflow runs `pnpm verify` by name, so a CI-only suite is a second definition of "verified") **and rather than part of `pnpm test`** (the 49 injected tests must not become conditional on a build); the **port strategy**, including `PORT=0` being rejected by `config.ts` and the range deliberately not widened for a test's convenience, and the probe's race being answered by watching for the child's _exit_ so a held port is a diagnosis rather than a hang; **why crashes are injected through a `node -e` wrapper** rather than through the temporary throwing route Tasks 1.7.5 and 1.9.3 both added; **why a drain is held open by a connection with an incomplete request** and not by an idle keep-alive one; and the **staleness check that was built and removed** when `tsc -b`'s content-hash rebuilds were measured against file mtimes. Two corrections belong in the same section: completing a held request after `close()` gets a **503**, not the 200 Task 1.7.5 recorded against a slow route it had added; and the chain's cost went **11.78 s → 21.30 s** locally for it
  - **That a spawned child is invisible to the runner's instrumentation, as a decision rather than a surprise** — this is the story's most transferable finding and it deserves its own numbered section rather than a clause inside the coverage one. Ten tests against `src/index.ts` moved that file's coverage by **zero**; the process suite run under the backend's own coverage settings reports **0% of 354 statements**. So **the coverage figure and the testing are two claims**, and `index.ts` at 0% means "no runner instruments it" rather than "nothing tests it" — which is the exact misreading a reader arrives at from the table alone
  - **And that the workflow's presence-not-percentage assertion was written for a prediction that turned out to be wrong, and is still right.** Task 1.10.4 checked for the _presence_ of `apps/backend/coverage/src/index.ts.html` specifically so 1.10.5 would not fail it by making the file reachable. 1.10.5 did not make it reachable, so the assertion never came under the pressure it was designed for — the comment beside it in the workflow gives that expectation as its reason and should be re-read for whether the reason still reads honestly. The assertion stands either way: it is the answer to "a stated invariant that quietly stops being enforced"
  - **What is published, at what size and for how long, including what was declined**: the three `coverage/` directories at 211,427 B for 7 days; `storybook-static/` declined at 9.3 MB per push, with publishing it _as a site_ left to Story 1.11; `apps/frontend/dist/` declined in favour of a fingerprint in the job summary, on the argument that an upload would be downloaded to answer the question the fingerprint already answers; and a coverage-reporting service declined outright
  - The five things `pnpm verify` does not cover — the fifth being a half-gap, since Prettier formats the workflow file and nothing checks its schema
  - **What a workflow assertion can and cannot catch.** Task 1.10.1's wrong-Node probe went green through `setup-node` _and_ through the workflow's own version assertion, because `.nvmrc` and the installed Node agreed with each other; `engineStrict` is what failed the install. An assertion catches a runner that disagrees with the pin, never a pin that is wrong — which is the toolchain-level form of this story's own "a green run means every check passed, not that every claim holds"
