- **Write `docs/adr/0007-*`**, following 0001–0006: the decisions, the alternatives rejected, the measurements behind each, and the reversal triggers. The ones that must be in it:
  - **The log format, and the environment concept surviving its first real test.** `LOG_FORMAT=json|pretty` as a value set by `scripts/dev.sh`, with `NODE_ENV` and the `dev.sh` pipe rejected for stated reasons. This is the section most likely to be re-litigated later, because "surely this is what `NODE_ENV` is for" is the obvious thought
  - **`pino-pretty` as a `dependency` rather than a `devDependency`**, and the general rule it refines: the house test keys on _resolution at runtime_, not on the `import` keyword. That generalises past this story
  - **The correlation id: a UUID rather than Fastify's counter, an inbound `x-request-id` honoured but validated, and `requestIdHeader` deliberately unused.** All three are re-litigation candidates. The counter looks cheaper until you notice it collides across restarts; Fastify's own `requestIdHeader` looks like a simplification until you notice it adopts the header with no validation at all (and defaults to `false` in 5.12.1, so nothing was being honoured before); and a W3C `traceparent` looks like the standards-compliant answer until you notice trace context is a whole propagation model Epic 10 should adopt entire rather than by its header alone. Record the raw-socket forging attempt as the evidence for the validation pattern, and record that a failing id is dropped rather than repaired
  - **The request record's field set, and the reason `remoteAddress` went.** The privacy argument is the obvious one and it is not the deciding one: behind Story 1.11's proxy those fields become the proxy's address, so they would be _wrong_ rather than absent. That generalises to every field this application ever logs about its caller
  - **The wire contract, which is the section with the most rejected alternatives in it.** `ApiError` is flat rather than `{ error: { … } }`, and the deciding question was where `requestId` goes — it is a property of the response and not of the failure, so a wrapper misfiles it. RFC 9457 `application/problem+json` was rejected for the same reason `traceparent` was: its discriminator is a `type` **URI** meant to dereference to documentation, and the field names without the URIs are the shape of the thing without the thing — that pairing is worth stating once as a general habit rather than twice as two coincidences. `code` is a union rather than a free string, `details` is `readonly string[]` rather than an object because an open-ended record is the field a leak arrives through, and `statusCode` and `timestamp` are deliberately absent. Record also that the contract shipped **unused** and 1.7.4 was what constructed it
  - **`REQUEST_ID_HEADER` living in `packages/shared` while the generator and the validation stayed in `apps/backend`** — and the rule it settles, which generalises past this story: shared means both sides depend on the same fact, not "shared is where types go". Story 1.6 declining to put the configuration type there is the contrast that makes the rule legible
  - The response-schema choice and the argument for why Story 1.6's rejection did not transfer — with the measurement, since the reason is the serialiser and not validation: an undeclared `secret` field was **stripped** from the wire with a schema in place and serialised verbatim without one
  - **The `satisfies Record<keyof T, JsonSchemaProperty>` guard as this repository's answer to a silent-failure class, which is the part most likely to be lost.** The other three — the misspelled CSS Module class, the missing `.js` import extension, the unchecked router path — are all recorded as accepted. This one was **closed**, for three lines and no dependency, and the ADR is where the next person adding a route learns that copying the idiom is the convention rather than decoration. Say what it does not close, known and dated 2026-09-01: a JSON type disagreeing with the TypeScript one is coerced silently, and a `required` property the handler omits is a 500 at runtime
  - **The error handlers, and the fact that there are two of them.** `setErrorHandler` never sees an unmatched route; registering only it leaves "API errors use a single consistent shape" false the first time somebody mistypes a URL. Record the two defaults that were replaced, including that their **field order differs**, because that is the visible evidence they came from different places
  - **`BAD_REQUEST`, and the measurement that justifies it**, which is the section most likely to read as arbitrary later. The union's test is a member per failure that can be _produced_. With a single `GET /health` route and nothing in the tree accepting a body, a malformed JSON body on `POST /health` is a **400** and a 2 MB body is a **413**, because Fastify's content-type parser runs before its not-found handler — while an unparseable content type resolves to a **404**, so a 415 is not reachable and got no member. Record why one member covers both 400 and 413 (a client branches the same way; the status line keeps the difference) and what would reverse that
  - **The production-detail mechanism, and the finding that reframed it.** There is no `ERROR_DETAIL` variable and no environment branch — it is the same shape Task 1.7.1 rejected `redact` for, a switch whose misconfiguration leaks silently outward, and the correlation id makes withholding free. The finding worth writing down is that **the stack was never the whole risk**: Fastify's default already withheld the stack and returned the thrown _message_ verbatim, so a generic 5xx message was the change that actually closed criterion 6. Note this is the second time in this story that Task 1.6.3's "nothing branches on the environment" decision held under pressure — the first was `LOG_FORMAT`, and two consecutive tests is what makes it a rule rather than a survival
  - **Criterion 6 has two mechanisms and only one of them is universal**, which is the structural point. `apiError()` builds an object with four slots and no fifth, so it covers every path; the response schema strips undeclared fields but is **per-route and opt-in**, and `setNotFoundHandler` is not a route and can therefore never carry one. Record the isolated measurement — a decorated body reaching the wire as four fields on a route declaring `500: apiErrorSchema` and with `stack` and `cause` intact on one that did not — and the end-to-end one, where a thrown error's `cause` DSN and `query` reached the log record and not the response
  - **Log levels by error class, and why they are Fastify's own split rather than a new one.** 5xx at `error`, 4xx at `info`. The interesting half is that `info` is chosen over `warn` to preserve a property from Task 1.7.1: at `LOG_LEVEL=warn` a healthy server is silent, and **a server answering 404s is healthy**. State the cost with it — at `warn` a 404 leaves no trace at all
  - **The 404 message does not reflect the request URL and Fastify's did**, on the argument that the client already knows what it asked for while the log record has the method and url beside the same id. Small, and it is the general habit worth naming once: unvalidated input does not go back out in a response body for a benefit the caller already has
  - **Two crash handlers, and the thing they replace being a _stream_ rather than a silence.** Node 24 already printed a stack for both events and already exited 1; what it did not do is put that stack in the log stream — raw stderr, no level, no timestamp, no pid, while every other record goes to stdout as JSON, so a deployment collecting stdout lost the crash and kept everything else. Record also that Node's two defaults are **indistinguishable from each other** (since Node 15 an unhandled rejection is thrown and prints exactly like an uncaught exception), which is what the `event` field exists for. The handlers live in `index.ts` and not in `buildServer()` for the same reason the signal handlers do, and they log through `app.log` because a process handler is handed an error rather than a request — which is the mechanical reason a crash record has no `reqId`
  - **A crash ignores `LOG_LEVEL`, and the exception is exactly one record wide.** The rule in two clauses — **ordinary traffic obeys the level; the process dying does not** — with Task 1.7.4's 4xx-at-`info` as the other half of it. The part that must not be lost is _why the record is restored_: the first implementation left `app.log.level` at `fatal` and silently lost `shutdown complete` from a crash-during-drain run, and the ceiling's level-50 `shutdown timed out, forcing exit` would have gone the same way. Record the detail that made the loss look selective — Fastify's per-request child loggers keep the level they were created with, so request records carried on while the root logger's went quiet. Record too why the level is mutated rather than a stderr line hand-rolled: one rendering of a log record, same serialisers, `pretty` still pretty
  - **A crash does not drain, deliberately.** `app.close()` on a process of unknown state serves remaining requests from a program that has already proved it is not the program you thought, and stacks a second failure on the one being reported. So in-flight requests are dropped on purpose — a decision, not an oversight — and the 5-second ceiling covers only the signal path. A crash _during_ a shutdown reuses `shuttingDown` and lets the existing drain finish; measured against a deliberately slow route, exit 0 with the in-flight request answered
  - **Three failure experiences, not two — and the table is the artefact worth carrying into the ADR whole.** A contained 5xx (`ApiError`, `x-request-id`, level 50 under that `reqId`, process lives); a crash with a request in flight (`curl: (52) Empty reply from server` — **no body and no headers at all**, so not even an id to quote, which is the one hole in the shape Task 1.7.4 made universal); and a crash detached from the request that caused it (**200 with a valid `x-request-id`**, then death, so the id points at a record correctly saying the request succeeded). The third is the one Story 1.11's operator needs before reading a log with it in, and it is the reason "quote the id and find the entry" is a rule with a stated exception rather than a guarantee
  - **The boundary placement — three boundaries, and the region's one is _inside_ the `<section>`.** Task 1.5.5's blank-`<main>` measurement is the evidence for not stopping at the outlet, and the inside/outside decision has its own: a boundary outside the section replaces the heading along with the contents, so a failed box loses its name, its landmark and its place in §9's grid. The header's boundary is the one that reads as optional and is not — without it a throwing `AppHeader` leaves `#root` with **zero children**, measured by removing it. Record its cost too: the fallback replaces the `<header>`, so a broken chrome takes the banner landmark and the navigation with it
  - **The contained/uncontained split, stated once for both halves of the stack — and note the two halves resolved it differently.** The backend added `process.on("uncaughtException")` because the default put a crash on the **wrong stream**; the frontend declined the equivalent `window` listener because a browser has no second stream — an uncaught error is already in the console with its stack, which is where a report would go, so a listener would repeat it while catching every extension on the page. Same analysis, opposite answer, because the deciding fact was the destination and not the mechanism. Story 1.12's server endpoint is the reversal trigger. Two mechanisms on each side for the same reason is a better ADR section than four unrelated decisions
  - **Hand-rolled over `react-error-boundary`, and the bytes are not the argument.** +932 B is close to free. What decided it is that the library's `resetErrorBoundary()` clears the error state **without remounting**, exactly like clearing a flag, so a real reset still means supplying `resetKeys` with a counter you increment — it is a well-tested wrapper around a `key`-based remount you still have to write, plus a second vocabulary beside four props. Record that the boundary keeps a **boolean and not the error**, which makes "the fallback never shows the error" structural in the same way `apiError()`'s four slots are, and is the frontend's instance of criterion 6's habit
  - **Two of this story's own written-down warnings were disproved by measurement, and an ADR that quietly drops them teaches the wrong lesson.** The `StrictMode` double-report did not happen — one `onCaughtError` per caught render error in development, because the first constructor call aborts that render pass. And the landmark conflict did not happen: `landmark-unique` keys on role **and accessible name together**, so it fires on landmarks that are indistinguishable rather than on landmarks that repeat, and three differently-named regions in one permutation grid pass it. That narrows Task 1.5.3's general rule, which was stated too broadly — the grid and landmark uniqueness only conflict for a component whose landmark has **no name**
- **Re-check the two accepted schema gaps rather than copying them forward.** Task 1.7.3 dated both to 2026-09-01 on a tree with one schema'd route; Task 1.7.4 adds the error responses, which is where the coercion gap would first cost something real. Confirm the guard is actually present on every schema in the tree — a route that declared a schema without it is the failure the convention exists to prevent, and nothing in `pnpm verify` checks for one. Task 1.7.4 made that confirmation cheap by moving `JsonSchemaProperty` into `apps/backend/src/json-schema.ts`, so the check is `grep -rn "satisfies Record<keyof" --include="*.ts"` and the expected answer is **two** sites: `routes/health.ts` and `errors.ts`. Note the gap that grep does **not** close, which is the more interesting one — nothing checks that a route which _can_ fail declared `500: apiErrorSchema` at all, and a route with no schema entry has no serialiser and therefore no stripping. Decide whether that joins the known-and-dated list below or is worth closing
- **Check the gaps list is still accurate, and it is now understated.** `CLAUDE.md` records two files no tool reads (`scripts/dev.sh` and the `rm -rf` fragments in two `clean` scripts). Task 1.7.1 did **not** put a pipe there — it added `export LOG_FORMAT="${LOG_FORMAT:-pretty}"` — but that is still a change in kind: `scripts/dev.sh` now carries a **configuration value**, and it is the only variable in the application that `pnpm env:check` cannot see, because that check reads `CONFIG_VARIABLES` and `.env.example` and has no view of a shell script. A typo there is a silent fallback to JSON in the dev loop. Decide whether that is worth closing or is another known-and-dated acceptance, and update the note either way
- **Confirm the clean-clone path still works**, the way Tasks 1.1.8, 1.3.5, 1.4.6, 1.5.6 and 1.6.7 each did: fresh clone, cold store, `pnpm install`, `pnpm verify`, then run the pair. **The Ctrl-C half of that has a harness trap Task 1.7.5 fell into**: sending `SIGINT` to pnpm's own pid rather than to the process **group** orphans `node dist/index.js`, which keeps port 3000 and looks exactly like the orphaned-process regression this check exists to catch. Signal the group, and count survivors in it rather than trusting the supervisor's exit. Note what a clean clone still does not prove — the stale-`dist` trap and the nested-worktree problem have no evidence there
