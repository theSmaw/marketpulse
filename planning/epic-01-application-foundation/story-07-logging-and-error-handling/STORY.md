# Story 1.7 — Logging & Error Handling

**Status:** Complete
**Epic:** [Epic 1 — Application Foundation](../EPIC.md)
**Depends on:** Story 1.2
**Epic scope covered:** logging, basic error handling

## Description

Structured logging and a consistent error contract across the stack. PRODUCT_SPEC.md §36 requires that failures degrade locally rather than collapsing the application, so the error handling established here sets the pattern for every later partial-failure state.

## Conventions from Story 1.1

Story 1.1 is complete, and these four bind this story. They are stated in every Epic 1 story so each one can be read on its own; the full reasoning is in `docs/adr/0001-repository-structure-and-typescript-toolchain.md`.

- **`pnpm verify` is the acceptance command** — `build && lint && format:check && stories && env:check && test`, chained with `&&` so the first failure is the exit code. It took its fifth step in Task 1.4.5: `stories` fails if a component has no stories file, and `build` now also produces the Storybook bundle. It took its sixth in Task 1.6.6: `env:check` fails if `.env.example` and `CONFIG_VARIABLES` have drifted apart, which is what makes the documented variable set a checked claim rather than prose. This story passes it from the repository root. Prettier owns Markdown as well as code, so an unformatted planning document fails it too
- **Six verbs, identical in every package** — `dev`, `build`, `test`, `lint`, `typecheck`, `clean`. Only `test` and `dev` fan out with `pnpm -r`; the rest run their tool once from the root, because the reference graph and ESLint's project service already cover the workspace in one pass. Changing what a verb means in one package means changing it everywhere, or saying why not
- **Shared tooling lives at the workspace root; packages declare only what they actually import.** ESLint, Prettier and TypeScript are root-only devDependencies, and pnpm puts the root's `node_modules/.bin` on every package script's PATH. A library the code imports belongs in the package that imports it — `@types/node` in `apps/backend` is the counter-example that keeps the rule from being over-applied
- **The module setup is ESM-only and single-file-safe** — `"type": "module"`, `module: nodenext`, `isolatedModules`, `verbatimModuleSyntax`, and relative imports carrying `.js` extensions from `.ts` files (TS2835 without one). `packages/shared` is consumed as **built output**, so it must be built before any consumer can be typechecked; `tsc -b` orders that itself, which is why `typecheck` and `build` are the same command

One thing that is true today and will not be forever: until Story 1.9 lands, **`pnpm test` passes because there are no tests** — all three `test` scripts are `echo` placeholders that exit 0, and they are now the only placeholders left. The companion note about both apps' `dev` scripts being placeholders is **no longer true** — Stories 1.2 and 1.3 made all three real.

## What that means for this story

- The error shape is the first genuinely shared contract between the two apps, so it belongs in `packages/shared` — which is consumed as **built output**. Editing it means rebuilding shared before either app typechecks against the change; `pnpm build` and `pnpm verify` do that, a bare `tsc --noEmit` in an app does not and will pass against the previous shape
- A logger is a library the backend imports, so it is declared in `apps/backend`. The frontend's error boundary is a React concern and belongs to `apps/frontend`; neither is root tooling
- **`exactOptionalPropertyTypes` is on**, which matters here more than anywhere else so far: an error object with `cause` absent and one with `cause: undefined` are different types. The domain reason is the same one that put the setting there — a missing field and an explicitly unknown one are different states, and this story is where that first shows up in real code
- ~~**The backend already logs, at Fastify's defaults, and this story replaces that rather than introducing it.**~~ **Backend complete.** Task 1.7.1 added the configurable level and the rendering; Task 1.7.2 replaced the inherited request record with a chosen one and got the correlation id out of the process as an `x-request-id` header. Task 1.7.3 defined the error shape and closed the schema question, and Task 1.7.4 wired it: both of Fastify's failure paths are replaced, and every failure the server produces — a 404, a thrown 500, and the 400 and 413 the content-type parser reaches before routing — answers in that shape with the correlation id in the body. Task 1.7.5 then took what escapes the request lifecycle entirely — both process-level handlers, logging a level-60 record where Node wrote raw stderr, with the one deliberate exception to `LOG_LEVEL` in the application. Task 1.7.6 built the frontend half against the same contained/uncontained split, and declined the browser's version of the second mechanism for a stated reason. **Every criterion is now met; what is left is Task 1.7.7 — verify, document, ADR 0007**
- **`NODE_ENV` currently changes nothing about the logs, and that is a baseline rather than a permanent fact.** Task 1.2.5 ran the built server with `NODE_ENV=production` and got a stream identical to the default run, line for line — same level, same request logging, same shutdown records. Fastify's default logger reads nothing from it that matters here. This story is the one likely to introduce a difference (a `LOG_LEVEL`, pino-pretty in development and JSON in production), so make that difference on purpose knowing nothing was doing it beforehand
- **The health route deliberately carries no JSON response schema, and it is now unambiguously this story's.** Task 1.2.3 deferred the choice because a schema approach is entangled with this story's error shape and Story 1.6's configuration validation; the deferral is recorded at the registration site in `apps/backend/src/server.ts` so it is not mistaken for an oversight. **Story 1.6 closed without taking it, and took a decision that bears on it**: Zod and Valibot were both spiked to full parity for configuration and both thrown away, on the specific ground that a schema over `process.env` is a schema over strings. That argument does **not** transfer here — a JSON response body is already typed data, which is the case a schema library is actually good at — so this story should weigh Fastify's own JSON Schema support and a library on their merits rather than reading 1.6's rejection as a workspace-wide precedent. ADR 0006 §1 says so explicitly and names Epic 11's `WorkspaceCommand` validation as the standing reversal trigger
- ~~**The crash handlers this story installs have to coexist with a shutdown already in progress.**~~ **Closed by Task 1.7.5, and the flag was reused as intended.** A crash while `shuttingDown` is true writes its record and returns; the drain keeps its ceiling and finishes on its own. Exercised rather than reasoned about — a rejection thrown mid-drain against a deliberately slow route gave `shutdown complete`, exit 0, and the in-flight request answered 200. The interaction that was _not_ anticipated is the one that bit: overriding `LOG_LEVEL` for the crash record silently swallowed the rest of the drain's logging until the override was made one record wide
- `*.log` is already gitignored. Logs go to stdout as structured JSON, not to files in the repository

### What Story 1.3 hands this story

This story depends on Story 1.2 alone and its backend half is unblocked today. The frontend half now has code to attach to — and one ordering problem worth seeing before it is discovered.

- ~~**"Contains a failure to the affected region" has no regions yet.**~~ **Resolved on 2026-08-31 by Task 1.5.4 — there are four, and they are named landmarks; see the Story 1.5 section below.** The original wording follows because the ordering problem it describes was real for two stories. `apps/frontend/src/App.tsx` is one stateless component; layout regions arrive in Story 1.5. The criterion is satisfiable today only in the degenerate sense of wrapping the whole application, which is the thing it exists to rule out. **Deliver the backend half whenever this story runs, and either sequence the frontend half after 1.5 or accept that "region" means "root" for now** — a note in the delivery order rather than a change to the dependency, since the backend half genuinely does not wait
- **An error boundary is a class component, and React 19 has not changed that.** There is still no hook equivalent, so this would be the codebase's first class component — worth deciding on purpose, including whether a small library is preferable to hand-rolling one. Check it against the installed React (19.2.8) rather than against memory: React 19 also added root-level `onUncaughtError` / `onCaughtError` / `onRecoverableError` options to `createRoot`, which are a **reporting** hook rather than a containment one and complement a boundary instead of replacing it. `main.tsx` passes no options today
- ~~**`StrictMode` is on, and it double-invokes render, effects and state updaters in development.** Anything this story writes that counts, reports or logs an error will see it twice locally and once in production.~~ **Measured by Task 1.7.6 and it did not happen.** A render throw caught by a boundary produced **exactly one** `onCaughtError` report in development with `StrictMode` on: the constructor does run twice, but the first throw aborts that render pass and React reports the failure once. So no de-duplicator was written. The warning still stands for anything counting _renders_ — it does not stand for reporting an error, which is what this story actually wrote
- **Do not mistake Vite's failure surface for the product's.** The dev server does not typecheck: a **type** error is applied as an ordinary hot update with no overlay and no console error, while a **syntax** error fails the transform loudly and leaves the page on its last good render. Neither is something an error boundary catches — a boundary catches exceptions thrown during render, not build-time failures. The overlay is a development affordance and the boundary is a product state
- **The frontend has nowhere to send a log.** The backend writes structured JSON to stdout; a browser error boundary has no destination at all, and this story's criteria do not ask for one. Note also that the correlation-id criterion only reaches the client half once the frontend actually makes a request, and it makes none until Story 1.12 — so "a user-visible error can be traced to a log entry" is a backend-side capability this story builds and a later story consumes

### What Story 1.4 hands this story

Story 1.4 did not move this story's dependency and did not build an error state. What it did was decide how one has to look, and the decisions are narrower than "use the tokens".

- **There is one red, and error and price-down share it.** `--status-error` and `--price-negative` resolve to the same value. What separates "this failed" from "this fell" is **presentation, not hue**: a failure is a titled block carrying a message, a price move is a bare signed figure in a column. So the error region this story designs is a shape before it is a colour, and reaching for a distinct error red would break the one-red rule rather than help
- **A degraded feed is not an error, and it already has a component.** `FeedIndicator` (`live` / `stale` / `disconnected`) is built and takes its `FeedStatus` from `packages/shared`. It is achromatic apart from the amber on `stale` — deliberately, because PRODUCT_SPEC.md §36 makes a dropped feed a product state rather than a failure. The "displaying data through 10:42:17" case this story's pattern is meant to generalise is therefore **not** an error boundary's job; do not style it as one
- **Colour is never the sole encoding, and an error state is the easiest place to forget that.** Under greyscale this palette's red and green differ by 1.05:1. An error region needs a word — a heading, a label, a message — carrying the state, exactly as the anomaly bands carry their name inside the fill
- **Whatever this story renders is a component, with a component's obligations.** `src/components/<Name>/` with a stylesheet and a stories file, one story per discrete state plus an `AllPermutations` grid; `pnpm stories` fails the build without the file. An error boundary's fallback has states worth a story each — that is the one place in this story where the permutation rule is doing real work rather than bookkeeping
- **The workshop reports accessibility and fails nothing.** `@storybook/addon-a11y` runs axe per story and never breaks a build, and Task 1.4.6 found it returns `color-contrast` as _inconclusive_ on non-text content. An error state that relies on an icon is exactly the shape axe declines to judge, so check it rather than trusting a green panel

### What Story 1.5 hands this story

The frontend half of this story was the one waiting, and it is no longer waiting. Story 1.5 built the regions the containment criterion is written against, and Task 1.5.5 measured what happens when a boundary is drawn at the wrong level — so the shape of the answer is evidence rather than preference.

- **There are four region landmarks and they are the containment boundaries.** Market topology, unusual activity, market breadth and current investigations, on the landing route only, each a `region` landmark with `aria-labelledby` pointing at its own heading. The criterion "contains a failure to the affected region" now has a literal referent: a boundary goes around a region's contents, and the other three regions plus the chrome keep rendering. The other four routes are deliberately a single area, so on those routes "region" still means the outlet — say which one a fallback is standing in rather than assuming they are the same
- **The wrong placement was measured, not argued.** Task 1.5.5 put a `<Suspense fallback={null}>` at the router and served the build from a host delaying each chunk: `AppHeader` renders perfectly and the **entire** `<main>` — four named landmarks and the 70vh grid — goes blank underneath it. A boundary at the router blanks the page body; a boundary at a region blanks a box. That is the same failure an error boundary at `<Routes>` would produce, and it is the degenerate case the criterion exists to rule out
- **`AppHeader` is outside `<Routes>` and eager**, so a route-level failure leaves the chrome intact by construction. That is what makes a header-mounted status indicator (Story 1.12) survive the thing it is reporting on, and it also means a failure _in the chrome_ has nothing above it — decide deliberately whether the header gets its own boundary or whether a broken header is allowed to take the page
- **The region grid takes a `height`, not a `min-height`, and an error state inherits that.** Each region scrolls its own overflow, so a fallback rendered inside one cannot push its neighbours around or change the grid's proportions — which is exactly the property "degrade locally" needs and is easy to lose by giving a fallback its own layout. Anything this story renders inside a region should fit the box it is given
- ~~**`Region` lives in `src/routes/` and owes no stories today; this story is what moves it.**~~ **Half right, and Task 1.7.6 measured the other half wrong.** It did move — a region now renders its contents or a fallback where its contents should be, which is two states worth seeing side by side, so it lives in `src/components/Region/` with a stories file. **The landmark conflict predicted alongside it does not exist.** Three `region` landmarks in one permutation grid report 0 violations and `landmark-unique` is in the _passes_ list; the disable was written before it was measured and then removed. The rule keys on role **and accessible name together**, so it fires on landmarks that are indistinguishable rather than on landmarks that repeat — `AppHeader`'s six banners were six copies of one anonymous thing, while a grid reviewing regions gives each cell a different name because that is what a region is. Task 1.5.3's general statement was too broad: **the permutation grid and landmark uniqueness only conflict for a component whose landmark has no name**
- **The React Compiler rules have still never fired on shipped code.** Story 1.5 added six modules and zero state; `Region`'s `useId()` is the first hook in the application and `useId` is not state. An error boundary is a **class component** and the rules have nothing to say about one — so the first real test of those 15 error-level rules is still this story's recovery affordance or Story 1.12's polling effect, whichever lands first

### What Story 1.6 hands this story

Task 1.6.3 closed the environment question by deciding there is **no environment variable** — see the note in `TASK-03-environments-and-env-file-loading.md`. Two consequences land here.

- **This story owns `readEnum`, and it owns the first enum variable.** `apps/backend/src/config.ts` has `readString` and `readInt` and deliberately no third reader, because nothing has an enum-valued variable yet. `LOG_LEVEL` is the obvious first one, and building it here means adding `readEnum(env, key, allowed)` beside the other two, with the message shape they already use — `KEY must be one of a, b, c, received "x"` — plus an entry in `CONFIG_VARIABLES`. Do not re-derive the reader signature; Task 1.6.1 measured it and Task 1.6.2 built the two that had callers
- **If this story wants pino-pretty in development and JSON in production, it is introducing the environment concept, not inheriting one.** Task 1.6.3 measured that a `.env` file, a real environment variable and a container all reach the same readers by the same precedence rule, and concluded that distinguishing environments by _values_ needed no variable naming the environment. A log format is the first thing that plausibly needs to branch on the environment rather than on a value, and that is a decision to take deliberately here — `LOG_LEVEL` alone may well cover it, which would keep the concept unbuilt for another story

## Acceptance criteria

- Backend emits structured (JSON) logs with configurable levels
- Every request is logged with a correlation id, method, path, status and duration
- The correlation id is returned to the client so a user-visible error can be traced to a log entry
- API errors use a single consistent shape
- Unhandled errors and promise rejections are caught and logged rather than crashing the process silently — **met by Task 1.7.5, with the wording annotated rather than accepted**: the process never crashed _silently_, it crashed onto raw stderr outside the log stream while every other record went to stdout as JSON. The change is the stream, and the evidence is that stderr is now empty on a crash
- Stack traces and internal detail are not exposed to clients in production
- The frontend has an error boundary that contains a failure to the affected region and offers recovery, rather than replacing the whole screen — **met by Task 1.7.6, and "the affected region" means three different boxes in three places**: one of the landing route's four `region` landmarks, the route outlet on the four routes that are deliberately a single area, and the chrome. Demonstrated rather than asserted — one region shows its fallback while the other three and the header render normally, and recovery is a remount with `performance.timeOrigin` unchanged. The half the wording does not cover is what a boundary cannot catch: nothing thrown in an event handler, a `setTimeout` or a promise callback reaches one, measured

## Open decisions

These are the choices this story has to take deliberately. Each has a task that owns it, and each has a recorded decision elsewhere in the repository bearing on it — so none of them starts from nothing.

- ~~**Whether prettified development logs introduce the environment concept**~~ — **closed by Task 1.7.1, and the concept stayed unbuilt.** It is `LOG_FORMAT=json|pretty`, an ordinary value read by the same module with the same precedence as `PORT`, and `apps/backend/scripts/dev.sh` exports `pretty` because that script _is_ the development loop. Nothing in the application branches on which environment it is in, so Task 1.6.3's decision holds. `NODE_ENV` was rejected as a reversal buying nothing over a value; the `dev.sh` pipe was rejected because a pipeline's exit status is the last command's, which breaks the propagation Task 1.2.5 verified, and because it costs the `trap` its foreground process
- ~~**Whether responses carry a JSON schema**~~ — **closed by Task 1.7.3: yes, Fastify's built-in JSON Schema, declared per route, no new dependency.** The reason is the serialiser rather than validation: `fast-json-stringify` **strips every property the schema does not declare**, measured — a `secret` field added to `/health`'s body vanished from the wire with a schema in place and went out verbatim without one. The hazard in the same feature was closed rather than accepted: the schema's properties are declared `satisfies Record<keyof HealthResponse, JsonSchemaProperty>`, so a field on the type and not in the schema is TS1360 naming it. Two smaller gaps are known and dated 2026-09-01 — a JSON type disagreeing with the TypeScript one is coerced silently, and a `required` property the handler omits is a 500 at runtime. `/health` is the first application, and Task 1.2.3's comment in `server.ts` now records the decision instead of the question
- ~~**How "not in production" is enforced with no environment variable**~~ — **closed by Task 1.7.4: nothing is exposed, in any environment, and no variable turns it on.** Safe by construction beat safe when configured correctly, on Task 1.7.1's own `redact` reasoning — a switch whose misconfiguration leaks silently outward is the shape to avoid. It costs nothing, because the stack is already on the log record carrying the correlation id the client was handed. The finding that made it easy: Fastify's default never leaked the stack anyway, it leaked the thrown **message**, so a generic 5xx message was the change that mattered. Task 1.6.3's decision therefore held for the second time in this story
- ~~**Whether an inbound correlation id is honoured**~~ — **closed by Task 1.7.2: it is honoured, validated against `^[A-Za-z0-9_-]{1,128}$`, and a failing value is dropped rather than sanitised.** The pattern excludes whitespace, control characters, quotes and commas, so an id cannot carry structure into whatever reads a log line; a raw-socket attempt to close the JSON object and forge a record was rejected by the pattern rather than by the client. A W3C `traceparent` was rejected as a propagation _format_ whose model Epic 10 should adopt whole, alongside this header rather than instead of it. Note Fastify's own `requestIdHeader` is **not** used and defaults to `false` in 5.12.1 — it adopts the header with no validation at all
- ~~**Hand-rolled error boundary or a library, and where the boundaries go**~~ — **closed by Task 1.7.6: hand-rolled, and three boundaries.** `react-error-boundary` 6.1.4 was installed and built before it was rejected — **+932 B and +1 module** over hand-rolling, which is close to free and is not what decided it. What decided it is that the library's `resetErrorBoundary()` has exactly the limitation the hand-rolled reset does: it clears the error state without remounting, so a real reset still means supplying `resetKeys` with a counter you increment yourself — the same `key`-based remount the hand-rolled version does in two lines. Plus a second vocabulary (`fallbackRender`, `resetKeys`, `onReset`, `useErrorBoundary`) beside four props, for a component this repository needs one of. The boundaries go around `AppHeader`, around the route outlet, and **inside** each `Region` — inside, so a failed region keeps its heading, its name and its landmark. All three root options are wired, to one `report-error.ts`, and providing them _replaces_ React's default console message rather than adding to it
