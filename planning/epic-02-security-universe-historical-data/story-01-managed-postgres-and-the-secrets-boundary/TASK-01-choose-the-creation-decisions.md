# Task 2.1.1 — Choose the four irreversible decisions, and the credential shape, provisioning nothing

**Status:** Complete
**Story:** [2.1 Managed Postgres Provisioning & the Secrets Boundary](STORY.md)
**Depends on:** nothing

## Objective

Settle every decision this story cannot revise later, and record it in the shape `HOSTING.md` uses, before a single `az` command runs. The point is the same as Task 1.11.1's: the first failed provisioning attempt in this repository's history should have one possible cause.

## Work

- **Take the four creation decisions, each with its reason: tier, networking mode, region, Postgres major version.** Two of them are already constrained rather than open — `HOSTING.md` names Burstable **B1MS** to stay inside the free account's 12-month offer, and East US because that is where the backend, the registry and the eventual database were placed — so the work on those two is confirming the constraint still holds and writing down what would break it, not re-opening it. The version is genuinely open and is a **twelve-month decision**: a major upgrade on a flexible server is not free, so read what Azure currently offers and pick the version Story 2.2's migrations and Story 2.7's ingestion will still want in a year
- **Networking mode is the single most expensive decision in this epic and it gets its own argument.** Public access with a firewall rule cannot be converted to VNet integration afterwards, and private access costs the Container Apps environment a custom VNet that cannot be retrofitted under the running environment either — so both directions are one-way. Read the trap the story names rather than trusting the cheap path's price tag: a Consumption-plan Container App's outbound IPs are **not stable**, so "allow this one IP" is not on the menu and the realistic public rule is **"allow Azure services"**, which admits every Azure tenant's compute, not just ours. Write down what that actually allows, what the password then has to be worth, and what would make the VNet worth its cost later
- **Decide authentication: password, or Microsoft Entra with the container's managed identity.** The second is the shape this repository has already chosen twice — `acrPull` on a system-assigned managed identity, and OIDC for the deploy, where the recorded win is that **there is no repository secret at all** — and its payoff here is identical: no secret exists to leak, to rotate, or to keep out of a log. Its costs are real and belong in the record: token acquisition inside the connection path, a token that expires and therefore a pool that has to renew rather than hold one credential forever, and a local-development story that cannot use the same mechanism. Whichever way it goes, **Story 2.6 places the Alpaca key through the path this decision creates**, so the record has to say what that path is for a value that is genuinely a secret and not an identity
- **Decide storage size and backup retention against Story 2.7's arithmetic rather than against the offer's ceiling.** The offer is 32 GB of storage and 32 GB of backup; the number to write down is what daily bars for the tracked universe actually cost, with the assumption stated, so a later reader can see whether growth or a bad estimate spent it. Note whether storage can be grown later and whether it can be shrunk — those are usually different answers
- **Say what a database changes about the cost estimate before it exists.** Epic 1 closed on **$9.21/month at the idle rate and $19.04 at the active rate against a $20 budget with alerts at 50/80/100%** — a budget that already sits _above_ the active-rate total. A B1MS is free under the offer and its storage and backup may not be; write the arithmetic down here as a prediction, so Task 2.1.8 can check it against a real bill rather than re-derive it
- **Record the account facts a future reader cannot recover from the tree** — server name, resource group, admin login (the name, never the value), which identity may connect, and who can delete it — in the same table `HOSTING.md` uses for the Container App, because that table already exists and a second location is how records rot
- **Provision nothing.** No server, no database, no firewall rule, no secret. The output of this task is a document

## Done when

- Tier, networking mode, region and version each have a decision and a stated reason, and the two one-way doors are named as one-way in the text
- The "allow Azure services" allowlist is characterised in words rather than adopted as a default
- The authentication decision is taken, with its cost to the connection path and to local development stated, and with what Story 2.6 inherits written down
- Storage and backup retention are chosen against an ingestion estimate whose assumption is visible
- The cost prediction is written down as a prediction, with the current budget re-read
- Nothing exists on Azure that did not exist before the task started

## Notes

The two decisions the story calls irreversible are the reason this task exists separately at all. Everything after it is implementation; this is the only place a wrong answer is expensive rather than annoying.

`HOSTING.md` is the destination rather than a new file, unless the material genuinely outgrows it — Epic 1's habit is one document per subject with the reasons in it, and a `DATABASE.md` that repeats the account facts is a second copy waiting to disagree with the first.

## Outcome

**Settled 2026-09-04 and recorded in full in [`HOSTING.md`](../../epic-01-application-foundation/story-11-deployment-pipeline-and-dev-environment/HOSTING.md), under _The database — the creation decisions_.** Nothing was provisioned: no server, no database, no firewall rule, no secret, and not even the resource-provider registration the first create will need. Every `az` call was a read.

- **The region decision was taken away rather than taken, and it is the headline.** `HOSTING.md` said East US and Epic 2 inherited it; **East US returns zero Postgres editions and zero versions for this subscription**, with the reason `"Provisioning is restricted in this region"` and the mechanism named in the response's own feature list as `OfferRestricted: Enabled`. Seven other US and Canadian regions read `Disabled` and offer 11–18 with B1MS. **It is East US 2**, where the frontend already sits inside the East-US resource group — a measured precedent in this very subscription — and the price is **identical in both regions** on all three meters, so the move costs nothing. Moving the backend instead was rejected: a Container Apps environment cannot change region, so it means a new FQDN, `VITE_API_BASE_URL`, `CORS_ORIGIN`, a frontend rebuild and both deployed addresses. **The backend-to-database round trip is now cross-region and has not been measured — Task 2.1.5 owns that.**
- **The brief's list of four irreversible decisions is wrong in both directions, and the corrected list is in the document.** Exactly **one** of the four is genuinely irreversible (**networking mode**); version is forward-only; region is irreversible in practice; and **tier is fully reversible** — `--tier` and `--sku-name` are arguments of `az postgres flexible-server update`. Meanwhile **three irreversible decisions were not on the list at all**: storage **type**, backup **redundancy**, and the data encryption key. **Authentication turned out to be the most reversible decision in the set**, not the most expensive, because both auth flags exist on `update` too.
- **Networking is public access with the `0.0.0.0` rule, and the allowlist is characterised in Microsoft's own words**: it "configures the firewall to allow all connections from Azure, **including connections from the subscriptions of other customers**". **"Allow this one IP" was disproved by measurement, not by citation** — the deployed backend reports **321 distinct outbound IPv4 addresses across 58 /16 prefixes**, identical across two readings three minutes apart, and the environment's `staticIp` is not among them because it is the inbound address. A stable outbound IP and private access are the **same** project — re-creating the Container Apps environment, which has no VNet and cannot gain one — so it is the whole Reversal-cost list spent on an empty database. Two permanent consequences are recorded: **every restore is public forever**, and the server's own outbound access "can't be restricted".
- **Authentication is Microsoft Entra only, with password authentication `Disabled` and no admin user created at all — so the platform ends this story holding no secret.** The firewall admits every Azure tenant, which makes the credential the entire boundary, and the strongest answer to "what if it leaks" is that there is none. **`EPIC.md`'s prediction that this epic is where ADR 0011's "nothing deployed holds a credential" expires is therefore wrong about the story: it expires in 2.6, not here** — the app's `secrets` array was re-read today and is still `null`. Creating no admin user also disposes of a sixth irreversible decision, since `--admin-user` "once set, cannot be changed".
- **The token mechanism has one trap that would have cost an afternoon**: Azure's own managed-identity-for-Postgres page is written for a VM and sends you to `http://169.254.169.254/...`, which **is not how a container app gets a token** — Container Apps uses `IDENTITY_ENDPOINT` with an `X-IDENTITY-HEADER`. Token lifetime for a system-assigned identity is **up to 24 hours**, so the pool refreshes at most daily. The identity's client id, the role-creation statement and the database it must be run on are all in the table.
- **What Story 2.6 inherits is not what Story 2.1 promised.** An Alpaca key is a bearer secret from a party with no Azure identity, so no identity mechanism can hold it and **the path does not transfer unchanged**. What transfers is the identity rather than the credential type; the recommended shape — Story 2.6's to decide — is a Container App secret sourced from Key Vault and read by this same managed identity.
- **Storage is 32 GiB because the floor and the offer's ceiling are the same number, and the real decision is autogrow, which is `Disabled`.** The CLI's `--storage-size` default is **128**, four times the offer. Autogrow's smallest step is a 2× jump to 64 GiB at **`$7.36`/month**, arriving with no prompt and impossible to undo. **Usable capacity is ~27 GiB, not 32**, because read-only mode triggers at under 5 GiB free. The ingestion arithmetic gives **~1.18 GB per year of minute bars** at an assumed ~120 bytes/row — about 24 years of headroom, or ~5 at five times the estimate — stated as a prediction for Story 2.7 to measure rather than as a substitute for measuring.
- **Backups are 7 days with geo-redundancy off**, because included backup storage is "up to 100 percent of your provisioned server storage" so 32 GiB is free regardless of the offer, retention is the one knob that moves freely both ways, and geo-redundancy is creation-only for data that is re-derivable from Alpaca.
- **The version is 18**, supported to **14-Nov-2030** against 17's 2029, GA on Azure for eleven months so not fresh, and **the extension question was checked and does not constrain the choice**: `timescaledb` is 2.24.0 on 15, 16, 17 and 18 alike. One correction to this brief: an in-place major upgrade carries **no fee** — what it costs is downtime, a precheck that can block, and no automated revert.
- **The prerequisite that would have failed the first create was found before it ran.** **`Microsoft.DBforPostgreSQL` is `NotRegistered`** on this subscription — Task 1.11.4's exact failure — and **the same asymmetry reproduced**: the name-availability check answered `"nameAvailable": true` from an unregistered provider, so the reassuring call succeeds while the one that matters would not. `az provider register` is Task 2.1.5's first command, recorded rather than run.
- **The cost prediction is `$0.00` inside the offer** — conditional on B1MS, 32 GiB and under 750 hours, which is unconditional at 744 hours in the longest month — and **`$16.09`/month outside it** (`$12.41` compute, `$3.68` storage, `$0.00` backup, all re-read from the Retail Prices API). Against Epic 1's re-derived `$9.21`/`$19.04` that is `$25.30`/`$35.13` once the offer expires around **2027-09-03**, both above the budget. **The budget was re-read (`$20`, alerts at 50/80/100%, all enabled) and the recommendation is to leave it there**, because while the offer holds a database-attributable alert _is_ the signal that an offer condition broke, and a budget raised to accommodate that cost cannot report it.
- **The cost question is still refused and the lag explanation no longer covers it.** `az consumption usage list` returns `[]` at exit 0 and the budget reports `currentSpend` `0.0` — the same shape Task 1.12.7 found — but the environment is now **~30 hours** old against a documented 8–24 hour lag. Task 2.1.8 inherits a sharper question than "wait longer".
