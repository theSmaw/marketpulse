# Task 2.5.3 — The calendar as data: holidays, half days, provenance and staleness

**Status:** Not started
**Story:** [2.5 Trading Calendar & Market Time Handling](STORY.md)
**Depends on:** Task 2.5.1

## Objective

Get the actual holidays and early closes into the tree, in the shape Task 2.5.1 chose, with
a stated provenance and a **failure mode for the day it goes stale** — which is acceptance
criterion 4 and is the half most calendar implementations skip.

## What the user can see when this lands

**Nothing yet.** The data exists; Task 2.5.4 is what makes it answer a question. It is worth
saying in the write-up that this task is one file of dates and one paragraph about what
happens when they run out, and that the paragraph is the hard part.

## Work

- **Write the table.** Full closures and early closes, covering the year range Task 2.5.1
  chose. Ten holidays: New Year's Day, Martin Luther King Jr. Day, Washington's Birthday,
  **Good Friday**, Memorial Day, Juneteenth, Independence Day, Labor Day, Thanksgiving,
  Christmas — plus the observance rule, because a holiday falling on a Saturday is observed
  on the preceding Friday and one falling on a Sunday on the following Monday, and getting
  that wrong is how you get a phantom session
- **Half days are the ones a naive list misses and they are not an edge case** — the day
  after Thanksgiving, Christmas Eve when it falls on a weekday, and 3 July when Independence
  Day falls on a weekday, all closing 13:00 ET. Story 2.8 will otherwise report three
  hours of missing bars a year as a data-quality failure
- **Follow `UNIVERSE.md` §11's provenance convention rather than inventing a second one.**
  Task 2.3.5 fixed this: the record carries the date the list was **last checked against a
  source**, stated in the file, and never `now()`. The same argument transfers exactly —
  a provenance date that is always today is a column that cannot report staleness. Name the
  source (NYSE's published holiday calendar is the authority; the SEC's and Nasdaq's agree),
  and note that this is a value **no instrument can check**, so it joins the list of things
  held by a written obligation rather than a test
- **Decide what happens outside the covered range, and make it loud.** This is criterion 4's
  real content. A date past the last covered year is not a normal input with a sensible
  default — a silent "no holidays that year" turns every one of them into a phantom trading
  session, and the symptom appears in Story 2.12 as a chart with a bar on Christmas. Prefer
  a refusal that names the range and the file to edit. Note the shape it does **not** take:
  the calendar cannot be trusted to fall back to "assume open"
- **Say how long the range is worth**, in years and in editing effort: one edit a year, in
  one file, with the next-edit-due date written where somebody will see it. The story
  already accepts this rate — record it rather than re-arguing it
- **Keep it a plain literal.** Task 2.3.8's measurement is directly relevant: a vocabulary
  declared as an array literal is tree-shaken out of the frontend bundle completely, and one
  built by _calling_ a constructor is not. A holiday table generated by mapping over a rule
  set at module load is the second shape and will ship into every visitor's bundle whether
  the chart uses it or not
- **Do not put this in the database.** It is worth one sentence explaining why, because it is
  the plausible wrong move: criterion 5 requires fast unit tests with no database, this data
  changes once a year, and a migration is the wrong mechanism for a table that gets
  **edited** — `migrations/README.md` §7 already fixes that a migration cannot be corrected
  after it is applied. The reversal trigger is a provider calendar being fetched and cached,
  which is Story 2.7's opportunity and not this story's

## Done when

- Every full closure and every early close for the covered range is in the tree, as data
- The observance rule for weekend-falling holidays is applied and Good Friday is present
- Provenance is recorded in the file, is the date the list was checked, and its obligation
  is written where the value is
- A date outside the range is a refusal that names the range, tested
- `pnpm verify` passes with no database running

## Notes

Two ways to check this list rather than trusting it. Cross-check the half days specifically
against a second published source — they are where lists disagree. And sanity-check the
count: a normal year has **252 trading days**, so a year in this table that produces 253 or
251 has a missing or invented holiday in it, which is a cheap arithmetic check Task 2.5.4
can assert once it can count sessions.
